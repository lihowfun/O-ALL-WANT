# OAW 吸收別人 skill 的流程

## 一頁版（2026-11-13 整理，D32–D45）

吸收分兩條路線，共用同一本帳和同一張吸收清單：
- **維護者路線**：決定 OAW 預設要帶什麼。照下面十步走。
- **使用者路線**：使用者自己加，用 `oaw.py add / list / remove`。可明確選裝未試吃的能力，清單保留「未試吃」標記；安裝不等於推薦進預設。

**五條原則**
1. **星星是先驗，不是證據。** 先假設它有用，去找它在哪裡有用；如果是我們贏了，先懷疑測法（D26）。
2. **沒吃過不下判定。** 用官方方式裝好、真的跑過，才有判定（D25、D28）。
3. **同一把尺。** 同一類的食物用同一套題目、評分和規則（D31-4）。
4. **先便宜，後昂貴。** 先做不花 token 的檢查，再跑小樣本。2.0.1 發佈前每項上限 30M（D35），上限內 agent 自己跑。
5. **owner 只在入口和發佈出現。** C 級問題一次最多問 3 題（D21、D28）。

**評估有兩個目的，與誰選擇安裝是不同分類（D38）**

| 步 | 幫助型：改善已有工作 | 能力型：新增成品能力 |
|---|---|---|
| 1 入口 | owner 貼網址或選 scout 候選；OAW 自己也過相同效果門檻 | 同左；PPT、影片、遊戲等列獨立能力清單，不因非 coding 類就排除 |
| 2 快篩 | 主張、主場、成本；最多三個具名單位 | 另列底層工具、授權與成品格式 |
| 3 封存／掃描 | pinned source、靜態檢查；旗標提供資訊，不能代替實跑判定 | 同左，列 hooks/MCP/scripts 與安裝 consent |
| 4 登記 | 盲出題、固定題庫／組別／門檻／預算，先推 records | 成品任務與機械檢查，具體題數及門檻以各能力 PREREG 為準 |
| 5 組別 | 原生、官方食物、skill 的 description-only；適用時加廉價做法／正對照 | 原生加相同底層工具、官方食物、description-only |
| 6 條件 | 食物主場及 OAW 用途 | 成品用途，加 installed-but-idle 對開場與一般工作的影響 |
| 7 執行前 | 模型／effort／提示／限制一致；訂閱來源、工具與 skill 可見性、隔離及設定快照逐格確認 | 同左；不能讓原生組少裝食物需要的底層工具 |
| 8 執行 | 記 logical／不含 cache read tokens、工具、秒數；含作者、評分、選擇、重試及失敗成本 | 同左，另列成品與外部工具成本；未完成不當成零分 |
| 9 評分 | 機械優先，否則跨家族盲評；用 [EVAL_PROTOCOL.md](EVAL_PROTOCOL.md) | 機械驗成品，如檔案、格式、音軌、建置、腳本操作；不把未測美感推成品質結論 |
| 10 判定／清單 | 預設／可選用／排掉；證據不足無判定。進預設的變更同時說明替換或移除哪些舊規則 | 可選用／排掉，永不進預設；資料不完整、未實跑或校準停止時無判定 |

[D38、D41、D42 原決定](https://github.com/lihowfun/O-ALL-WANT/blob/268429d/records/digestion-2026-11-03/ingest/DECISIONS.md)：
D38 的能力型門檻是草案：成品通過數增加、閒置啟動 token 不增加超過 2%、一般任務不變差；具體試吃按自己的預登記執行。D41 優先 harness，再 PPT／影片；遊戲是能力範例，未因此自動啟動試吃。D42 只授權 H1 指定的天花板補題，不能一般化成事後換題。D45 要求發佈前收斂一條線，修正只複查一次；資料不足不宣告通過。

[H1](https://github.com/lihowfun/O-ALL-WANT/blob/268429d/records/v2.0.1-experiments/H1/RESULT.md) 的合併判定仍為未定。保留預設是 D45 產品決定，FIXCHECK 重用找缺陷的題目，不是獨立收益證據。[Harness² 評估](https://github.com/lihowfun/O-ALL-WANT/blob/4033f52/records/intake-2026-11-13-harness2/EVALUATION.md) 的 U2 比較已由 owner 在 D48 解除發佈前的實驗限制；U1/U3 仍待處理，尚未宣稱吸收或省 token。

使用者可選能力的安裝與推薦證據分開：receipt 記來源/pin、host、安裝內容、試吃狀態、備份和移除方式；未知成本標未量測。hooks/MCP/scripts 需明確 consent，安裝不執行抓取的程式。專案外 checkout locator 另需 `--remember-checkout`；可在同一個 add 問題選擇，不因同意元件而自動寫入。

**一樣食物大概花多少**
- 程式理解類：一個模型條件跑 12 題、兩組，約 2–4M。
- 審查類（EGM）：小案例每次 1.1–1.4M；真實大小的計畫可能 18M 以上，大多是快取讀取。
- 沿用題庫和原生組，可以省一半以上。

以下是舊流程的完整細則和操作說明，留作參考。引擎已經會擋的規則，以引擎為準。

## 參考：九站細則（D1–D31）

從現在起，OAW 每次加入 skill（下文叫「食物」）都走這一條流程。流程只根據 owner 決定 D1–D28（索引在最後）。網頁上的消化道、`catalog.py menu` 和 `oaw_status.py` 畫的是同一張站別表（`scripts/catalog_core.py` 的 `PIPELINE_STAGES`），讀同一份 `.oaw/catalog/view.json`。

食物有兩種：GitHub repo，和研究論文（arXiv 論文或本機 PDF）。兩種都走同一條流程；論文和 repo 不同的地方寫在第 1、2、3、4、8 站。

每一站和它的每個細項都標明今天的狀態：

- **自動**：原型 v0 已經自己會做，不用你啟動。
- **自動（Claude 接手）**：由 Claude 做（試吃、重跑、重建、記錄），不用你啟動（D28）；沒有排程，在下一次 Claude 工作階段處理。
- **需要你**：要 owner 決定或啟動。系統不會替你決定。
- **部分自動**：一部分自動，其餘需要你或還在規劃中。
- **規劃中**：屬於這個流程，但還沒自動化。畫面上畫出來、標「規劃中」、沒有按鈕，也不會被當成已經做過。

完整指令見 [CLI Reference](CLI_Reference.md#skill-catalog-prototype-v0)。

## D21 精簡流程（2026-11-04 起）

owner 覺得原本的流程太慢、要你審的步驟太多（2026-11-03 那一輪：約 20 個要 owner 處理的步驟、3 次修訂、3 輪 Goldfish，吸收 0 個），所以改用下面的流程。它取代逐批核准（D14、PRE-08），下面九站的規則照舊，只有「誰要動手」變了。

| 步驟 | 誰 | 做什麼 |
|---|---|---|
| 入口 | 你 | 貼 repo 或 arXiv 論文網址，或在每週偵查清單上勾選 |
| 快篩 | 自動 | 每樣食物最多挑 3 個最值得的單位；沒挑到的留在候選池，寫一行理由，不再分析，也不設計付費計畫 |
| 實作 | 自動 | 寫成程式和測試，gate 必須通過；程式和測試就是紀錄，不另寫多份提案文件 |
| 盲審 | 自動 | 一輪零上下文 Goldfish 審程式 diff 和測試（D15 的 recipe）；Elephant 處理發現，只有 Elephant 不接受的 blocker 才交給你 |
| 分級 | 自動 | **A**：只改機制、不碰模型會讀的文字、不執行食物程式、可還原 → 自動吸收（D17 允許靜態證據）<br>**B**：模型會讀的文字 → 在 D13 常設預算內自動跑 A/B，齊平以上才吸收；預算不夠就排隊<br>**C**：會執行食物程式、新增執行期相依、需要常設決定沒涵蓋的授權或 CLI 選擇、移除既有 skill、超出預算 → 問你 |
| 版本 | 你 | 每個版本一頁：多了什麼、和預設比、怎麼還原；你 merge PR |

- D14 的常設選擇（授權路線、CLI 結束碼、release 目標、排出清單）視為政策，涵蓋到的項目不再另外問。
- D16：「和單吃食物比：未測」的標示保留；快篩時不再設計底線組。
- 你的例行動作只有兩個：入口和版本。
- 引擎從 D28 起照這個流程畫：A／B／C 分級和重建由 Claude 做，用 `record-absorption` 記錄；照原樣複製吸收（第 8 站的勾選）留著，但只是可選的舊流程。

## D28 自動消化（2026-11-05 起）

owner 說：「你是一個自動自發的消化系統，不是每樣都要等我，盡可能找到 SOP 自動消化與吸收，盡量降低人類審查。」又說：「court-skill 這次沒有真的跑，以後不准再測 skills 連安裝起來跑都沒跑就給我下結論。」所以：

- **每一站預設由 Claude 做**。消化道上 Claude 接手的食物標「自動（Claude 接手）」，不是「等你」。
- **只有這些等你**（藍色 `!`）：入口（貼網址、勾偵查候選；還沒試吃的食物）、D21 的 C 級問題、只有你能做的前置（登入、token、限定試吃區的常設規則；寫在紀錄的 `blocked_on_owner`），以及移除一個已經在版本裡、但判定變差的 skill（移除 skill 是 C 級）。
- **發布另外標**（青色 `↑`「等發布（合併 PR 時一次決定）」）：已經在工作分支重建好的單位，等你合併 PR；這是整個分支一次的決定，不是逐樣核准。`view.json` 的 `release_pending` 把它們算在一起。
- **靜態旗標只供參考，不擋食物**。掃描、旗標、成分暫留和終端分流都照舊當安全檢查；要照原樣複製帶旗標的成分，仍然要先分流。但 D21 把挑中的單位重建成 OAW 程式和測試（不複製食物的程式碼），D25 只在試吃區執行食物，所以靜態之後的下一步是 Claude 試吃，不是你分流。分流變成可選的。
- **食物組沒裝起來跑過，就沒有判定**。試吃紀錄的食物組（`food_arm`）至少要有一次評分過的執行，判定才算數；沒有就記成「沒有判定」（`no-verdict`），寫明卡在哪裡。引擎在記錄時和每次重算畫面時都檢查這條。
- **試吃和吸收記進帳本**，畫面才看得到真正的進度：

| 誰 | 做什麼 | 指令 |
|---|---|---|
| Claude | 免費靜態檢查（第 3 站） | `taste`（`add` 時自動跑） |
| Claude | 讀食物自己的文件定主張和試吃計畫；新的 agent 出題，題目先凍結在 records 分支 | — |
| Claude | 在試吃區官方安裝（有 project scope 就用）、每一組都跑（原生、食物、有 OAW 版本時也跑）、盲評、照事先寫死的規則判定 | — |
| Claude | 把結果記進帳本 | `record-tasting --food ID --file 試吃紀錄.json --apply` |
| Claude | 判定吸收：A／B 級在 `claude/oaw-2` 重建成程式和測試，一輪 Goldfish；記錄 | `record-absorption --food ID --file 吸收紀錄.json --apply` |
| Claude | 判定插上：接上官方版；判定不收：寫一行理由 | — |
| 你 | 發布：合併 PR | — |
| 你（想問的時候） | 直白查：為什麼收或不收、食物本身有沒有真的跑、數字、證據在哪個 commit、現在等誰 | `catalog.py why [食物]` |

試吃判定的意思：`absorb` 吸收（重建）、`plug-in` 插上（接上官方版，不吸收）、`optional` 可選用（不設預設，要用時才叫）、`decline` 不收、`no-verdict` 沒有判定；`not-shown-better`（沒證明比原生好）只留給 D29 之前的紀錄。同一樣食物可以有很多次試吃，全部列在食物卡上，最新的那次決定位置。兩種紀錄的欄位見 [CLI Reference](CLI_Reference.md#agent-tastings-and-d21-absorptions-d28)。

試吃之後食物在哪、等誰：

| 試吃或吸收紀錄 | 站 | 等誰 |
|---|---|---|
| 還沒有 | 靜態（有高嚴重度旗標）或分流 | 自動（Claude 接手）：去試吃 |
| `no-verdict` | 實測 ⊗ | 自動（Claude 重跑）；有 `blocked_on_owner` 時等你 |
| `absorb` | 核准 | 自動（Claude 依 D21 重建） |
| `plug-in` | 核准 | 自動（Claude 接上官方版） |
| `decline`、`not-shown-better` | 分流 ● | 沒有待辦 |
| 吸收紀錄（有吸收的單位） | 版本 | 等發布；發布後沒有待辦；有 `blocked_on_owner` 時等你 |
| 只有匯入的歷史提案 | 核准 | 只有可選的決定（記成待辦） |

## D29 判定規則（2026-11-06 起）

owner 說「照建議改成 D29」（建議見 records 分支 `records/digestion-2026-11-06/SOP_AUDIT.md`）。原因：舊規則一方面把便宜的小進步排掉（只看得出省 30% 以上、題目常碰到天花板、「量不出來」記成不收），一方面把很貴的小進步吸收（判成更好就不看成本），而且判定的分界落在 AI 評分的雜訊裡。

每次試吃在事先登記裡寫死兩個軸：
- **品質**和原生比：更好、一樣、更差。用 AI 評分時，同一批答案獨立評兩次，差距兩次都成立才算；隱藏測試這類程式評分不用評兩次。落在誤差帶裡的（包括「量不出來」）都算一樣。
- **成本**：食物的 token 中位數除以原生的，加上事先寫好的「比較省」規則。

| 品質 | 成本 | 結果 | 帳本判定 |
|---|---|---|---|
| 更好 | 不超過原生 1.5 倍 | 進預設 | `absorb`（重建）或 `plug-in`（官方版） |
| 一樣 | 依規則比較省 | 進預設 | `absorb` 或 `plug-in` |
| 一樣 | 不超過 1.5 倍 | 可選用 | `optional` |
| 更好 | 超過 1.5 倍 | 可選用 | `optional` |
| 一樣 | 超過 1.5 倍 | 排掉 | `decline` |
| 更差 | — | 排掉 | `decline` |

- 有好幾個模型條件時，取最低的那個條件。
- D21 的級別照舊：會執行食物程式、新增執行期相依的（C 級），不論進預設還是可選用，裝進來之前都等你；OAW 不替你安裝的外部 plugin，記成可選用並寫明怎麼裝。
- 引擎在記錄時檢查：試吃紀錄的 `judgment` 決定結果，判定對不上就拒收；`optional` 一定要有 `judgment`；只評一次的 AI 評分只能說「一樣」。
- 其他四條建議由 Claude 直接做：凍結題目前先讓原生試跑，原生已滿分就換難一點的題；記憶、省 token 這類長效型食物測 30 個 session 以上；能用程式評分就不用 AI 評；試吃工具共用（沿用凍結題組和原生組只跑食物組、0 token 的呼叫算沒跑、次數不同時用比例）。

## 流程

```text
每週偵查 → 相關性過濾 → 你勾選 ─┐
                               ├→ 1 入口 → 2 封存 → 3 靜態 → 4 計畫 → 5 盲審 → 6 實測 → 7 分流 → 8 核准 → 9 版本
你點名（可批次，重複的合併）─────┘
```

| 站 | 做什麼 | 決定 | 今天 |
|---|---|---|---|
| 1 入口（含兩條入口） | 你按「立即偵查」→ 相關性過濾 → 你勾選；或你直接點名（repo 或論文）。你勾選或點名就是同意試吃：同一個 repo、同一篇論文只收一次，接著立刻免費試吃 | D4 | 部分自動：偵查要你每週按一次（沒有排程）；過濾、去重、送去試吃：自動；勾選、點名：需要你 |
| 2 封存 | repo 固定在一個 pinned SHA、論文固定在 arXiv 版本＋sha256，唯讀封存在專案外的 `LAB_HOME`，絕不執行 | D7 | 自動 |
| 3 靜態 | 免費靜態檢查，把食物拆成成分；靜態規則只舉旗，旗標不擋食物（D28） | D5、D7 | 部分自動：檢查和拆 repo 的成分自動；論文的單位由 Claude 當 Elephant 拆；之後由 Claude 送去試吃；高嚴重度旗標的分流是可選的 |
| 4 計畫 | 系統依證據擬測試計畫；Elephant 依紀錄的決定擬吸收提案 | D10、D11 | 部分自動：系統測試計畫自動；Elephant 提案規劃中（今天只能匯入歷史紀錄） |
| 5 盲審 | Goldfish 在驗證過的零脈絡下盲審我們的草稿，Elephant 解決發現 | D10、D15 | 規劃中 |
| 6 實測 | Claude 在試吃區試吃（D25、D28），用 `record-tasting` 記錄；引擎自己的測試在常設政策內由便宜到貴跑：離線整合 T1、沙箱試跑 TX、行為 A/B、整合檢查 T4、齊平底線 P | D11、D13、D25 | 部分自動：Claude 的試吃和記錄；引擎自己的測試規劃中 |
| 7 分流 | 每個成分判定吸收／排掉／暫留，附原因和證據等級；試吃判定寫在這一站；套用第 6 站整合檢查和齊平底線的關口 | D2、D5、D16、D17、D18 | 部分自動：成分判定自動（只有靜態量測）；試吃判定由 Claude 記錄；關口和 D18 的規劃欄位：規劃中 |
| 8 核准 | Claude 依 D21 把挑中的單位重建成 OAW 程式和測試，用 `record-absorption` 記錄；只有 C 級問你 | D7、D11、D21 | 部分自動：重建和記錄由 Claude 做；C 級問題需要你；照原樣複製吸收是可選的 |

站別的狀態符號：`●` 完成、`◐` 部分完成（這一站有規劃中的細項還沒跑，所以不畫成完成）、`◉` 目前、`⊗` 卡住、`⊖` 已移除、`○` 還沒到、`┄` 規劃中、`–` 不需要。

## 每一站的規則

### 1 入口（D4）

- **每週偵查**只偵測、累積候選。**沒有排程**：你每週按一次「立即偵查」（或執行 `catalog.py scout`）。偵查依更新時間搜尋最近 7 天推送的 repo，所以漏掉的一週，那週推送、之後沒再更新的 repo 就不會再被搜到。
- 搜尋依更新時間排序、一頁一頁抓（每個查詢最多 3 頁、每頁 100 個）；超過的部分記成「沒抓到」的數量，截斷看的是時間，絕不是星數。相關性過濾不經審查就丟掉和 coding-agent skill／harness 無關的 repo（例如影片工具）。星數只決定候選清單的排序，不是品質。
- 每週由你勾選要試哪些。沒有你勾選，什麼都不會進封存或消化。
- **你點名**：你直接給 repo 或論文。可以一次給很多個；同一個 repo 寫兩次（大小寫、`.git`、結尾斜線、SSH 或 tree 網址）只收一次。
- **論文的寫法**：`arXiv:2606.03979`、`https://arxiv.org/abs/2606.03979v2`、`https://arxiv.org/pdf/2606.03979v2.pdf`（可以不寫 `https://`），舊式編號（`hep-th/9901001`）也可以；本機論文寫 `file:///…/x.pdf`。同一篇論文的不同版本（v1、v2）是同一樣食物，只收一次；你寫的版本會記下來，沒寫就在試吃時固定最新版。其他網頁和 DOI 還不收（規劃中）。
- **你勾選或點名就是 D4 的確認**：確認後系統立刻免費試吃（第 2、3 站），不再逐樣問你。網頁的「送去試吃」、CLI 的 `add` 和 `scout pick` 都是這樣；只想登記、先不試吃，CLI 加 `--no-taste`。

### 2 封存（D7）

- 不會自動安裝或套用任何東西。
- 抓取固定在一個 pinned SHA（hardened git fetch：不跑 hooks、不 checkout、只收 https 和 `file://`；沒有 git 時改用 codeload tarball，標 `unverified-against-commit`）。
- 快照封存成 `LAB_HOME` 裡的唯讀 tar，在專案外；只在記憶體裡讀，不解壓、不 import、不執行。
- **大小不擋食物**（2026-11-06，owner：「snapshot exceeds 50 MB 限制沒有任何意義」）：封存上限（單檔 5 MB、總共 200 MB、20,000 個檔案）只決定存多少、掃多少。超過的部分從最大的檔案開始跳過，每個跳過的檔案標 `F-PARTIAL`（沒存、沒掃），食物照樣往下走、照樣試吃。只有 tarball 備援路線（沒有 git 時）下載超過 400 MB 才會拒收。
- **論文**：只用 https 抓兩樣東西：arXiv 的 OAI-PMH 中繼資料（`arXivRaw`：標題、作者、摘要、授權網址、版本清單）和固定版本的 PDF（`https://arxiv.org/pdf/<編號>v<N>`；沒指定版本就固定最新版）。轉址也只能到 https 的 arXiv；有時間上限（60 秒）和大小上限（中繼資料 2 MB、PDF 200 MB）。PDF 只檢查開頭是不是 `%PDF-`、算 sha256，不解析、不顯示、不執行。PDF 和一份 `metadata.json`（記每個檔案的 sha256，沒有時間戳記）一起封存成唯讀 tar，固定在「arXiv 版本＋內容 hash」，完整性標 `sha256-recorded`（arXiv 沒有可以驗證的 hash，只記下收到的內容）。本機 PDF 一樣封存，中繼資料只來自檔案本身（沒有標題、作者、版本、授權）。

### 3 靜態（D5、D7）

- 免費 T0 檢查：檔案角色、授權、宣告的 hooks／MCP server／腳本、旗標，再把食物拆成成分（skill、hook set、MCP server、腳本、manifest、指示檔、文件）。
- 靜態規則只舉旗，不判有毒。高嚴重度旗標讓食物變成「有疑慮」，帶旗標的成分在你分流之前不能照原樣複製；只有你分流成「確認有毒」才是有毒，那個成分才排掉。
- **D28：旗標不擋整樣食物**。有高嚴重度旗標的食物停在這一站，標「自動（Claude 接手）」：旗標交給重建和 Goldfish 盲審，下一步是 Claude 在試吃區試吃。試吃記錄之後，食物照試吃判定往下走（旗標和「有疑慮」的標示都還在）。
- 分流是可選的（只有要照原樣複製帶旗標的成分、或確認有毒時才需要）。分流成良性或過敏原要確認碼，只能在互動式終端機做（見「確認碼怎麼用」）。網頁在這一站顯示可以複製的完整 `menu` 指令。
- 掃描規則更新後，舊的試吃紀錄要用新規則再試吃一次（免費），才能吸收。
- **論文**：靜態紀錄只記標題、作者、arXiv 版本和日期、摘要長度（摘要原文留在 `LAB_HOME`，不進專案）和授權；hooks、MCP、腳本的檢查不適用。授權規則：CC BY、CC BY-SA、CC0 → 原文可以引用，但要附出處；其他（包括 arXiv 的 non-exclusive distribution 授權和不明的授權）→ 舉資訊旗標 `P-LIC`「只取想法：重新實作，不複製原文」。資訊旗標不用分流，也不擋任何東西。
- **論文的單位引擎拆不出來**：拆論文要模型，所以由 Claude 當 Elephant 拆，匯入消化紀錄，或直接記錄試吃／吸收；引擎不會自己編成分。試吃完、還沒拆的論文停在這一站（`◉`），標「自動（Claude 接手）」。

### 4 計畫（D10、D11）

- 系統決定每樣食物怎麼吃，不是你：系統挑最便宜、又能分辨營養、沒營養和有毒的測試，排在前面。
- Elephant（完整專案脈絡，來自紀錄的決定）擬吸收提案，Goldfish 盲審（第 5 站）。
- 今天：`plan` 依證據自動產生系統測試計畫和 token 預估，每一步標它屬於 D13 的第幾階段和要哪一級沙箱。Elephant 的提案還是規劃中：只能匯入已經做好的紀錄（`import-report`），標成歷史證據，不計入任何判定。
- **論文的消化紀錄**也能匯入：`components.json`（`food_kind: paper`，每個單位用 `what` 描述）、`goldfish-*.json`、`skeptic.json`，以及 `digest.md`、`elephant-draft.md`、`elephant-final.md`、`extract.md`（記 sha256 和章節標題）。單位照紀錄的分流計數（例如 arXiv 2606.03979：16 個單位，吸收 2、暫留 3、排掉 11），一樣只是歷史證據。食物還沒登記時，系統依紀錄裡的 arXiv 編號登記，並固定在紀錄消化的那個版本；匯入不連網。

### 5 盲審（D10、D15）

- Goldfish 盲審的是**我們的草稿**：測試計畫、吸收提案、backlog 合成，以及每個合併出來的項目。只審食物本身不能取代。
- 零脈絡要驗證，不能假設：每隻 Goldfish 用固定 recipe 啟動，argv 和 init event 都顯示沒有工具、skill、plugin、MCP server 或繼承的設定。每份 Goldfish 紀錄寫明啟動方式、host 版本、繼承的脈絡和 init event 檢查。
- Elephant 解決 Goldfish 的發現，再交給你。
- 今天：規劃中。匯入的 Goldfish 紀錄只顯示成歷史證據，標「零脈絡未驗證」；紀錄沒寫的啟動欄位顯示「未記錄」。

### 6 實測（D11、D13）

- 常設政策只設定一次。之後系統在政策內自己跑免費和付費測試、回報結果，不逐樣問你；只有測試會超出政策時才問。
- 由便宜到貴：每個暫留都先跑免費的 Stage 0（D17），最便宜、還能分辨的測試先做。
- 這一站的測試：
  - **離線整合 T1**：名稱碰撞、doctor／migrate 往返。
  - **沙箱試跑 TX**：會執行食物的成分只在可拋棄沙箱（level 2）跑。
  - **行為 A/B**：模型面向的文字（skill、模板、啟動文字）要過 A/B 才能吸收（D17）。
  - **整合檢查 T4**：對現有配方的退步、觸發衝突、context 預算、指示衝突。
  - **齊平底線 P**（D2、D16）：每樣測過的食物，計畫都包含「OAW 吃完」對「單吃食物」（C ≥ B）。
- 常設政策 PRE-01（D13）：
  - 每樣食物 Stage 0/1 上限 10M logical tokens；Stage 2、第二個 host 或超過上限都要先問你。
  - 消化系統本身的開銷（Goldfish 審查、探測、fixture）每輪上限 10M。
  - 沙箱 level 1：這台機器上的專案副本，host 設定目錄改到別處；只給不執行食物程式碼的 run。
  - 沙箱 level 2：可拋棄的 Linux container 或 VM，每次試跑後銷毀；凡是執行食物程式碼、安裝任何東西、可能讀到作業系統憑證庫的 run 都要 level 2（Windows 上改 HOME 隔離不了 `USERPROFILE` 或 Credential Manager）。沒有 level 2 的機器，這類 run 一律暫留。
  - 試跑預設不給 API key；只有你自己建立專用、有上限、用完撤銷的 key 才給。Goldfish run 用可拋棄的設定目錄。
  - 網路只開 model provider API；level 2 可以短暫開 PyPI／GitHub 抓相依套件。
  - Codex 的一半在你登入 Codex CLI 之前一律記成「未測」。
  - 共用 baseline 的 A/B 成本平分給用到它的食物；candidate arm 算在它測的那樣食物上。
- **D25、D28：Claude 的試吃**。Claude 在試吃區官方安裝食物、每一組都跑、盲評、照事先寫死的規則判定，再用 `record-tasting` 記進帳本。食物組沒有評分過的執行就不能有判定（引擎拒收），只能記成「沒有判定」並寫明卡在哪裡：卡在只有你能做的事（例如限定試吃區的常設規則），寫在 `blocked_on_owner`，食物就等你；否則等 Claude 重跑。記錄之後這一站標完成（「沒有判定」標卡住），食物卡列出每一次試吃的組別、執行次數、題目 sha256 和 records 分支上的 commit。
- 今天（引擎自己的測試）：規劃中。付費測試、沙箱試跑、T1、T4、P 都還沒實作；`plan` 只列出計畫和預估花費，「實測（依常設政策）」按鈕是停用的。計畫的每一步標 D13 階段：T0、T1、人工分流是第 0 階段；TX 和 A/B 冒煙是第 1 階段；T4、P、完整 A/B 是第 2 階段，一律先問你；Goldfish 審查算消化系統開銷。和每樣食物上限比的只有第 0/1 階段；TX 標沙箱 level 2。
- **`policy set` 還沒有照 PRE-01 編碼**：它存每樣食物上限、一個每週上限（D13 沒有這個上限）和一組自選的試跑條件；沒有每輪開銷上限，也沒有 level 1／level 2 的分級。PRE-01 是現行政策，請照上面的規則讀計畫；`policy set` 改成 PRE-01 的形狀是規劃中。

### 7 分流（D2、D5、D16、D17、D18）

- 每樣食物都先測過才判定。判定以成分為單位，「拉肚子」很少是整樣：
  - 🟢 **吸收**：今天是照原樣複製 skill 文字（見第 9 站）；D5 要的「重新實作成一個具名的 OAW 部件」還沒做。
  - 🔴 **排掉**：附原因和證據。只排掉有害的部分。依 OAW 原則的排掉（套件清單、第二份常駐指示檔、二進位檔）是最終的；你確認有毒的成分也排掉。
  - 🟡 **暫留**：寫明缺哪個測試。
- **模型面向的文字一律暫留到 A/B 跑過（D17）**：skill、模板、啟動文字和它的機制拆開；文字要有經同意的行為 A/B（有增益、過齊平底線、而且點名涵蓋這個成分）才算數，機制可以用靜態證據出貨。通過靜態檢查的純文字 skill（`X0`）標「暫留：缺行為 A/B（靜態檢查通過）」，不是吸收。會執行食物的步驟自動暫留。
- 每一行都標證據等級：實測（measured）、靜態量測（static-measured）、未量測（not measured）。
- **D18**：還沒建的項目寫「未量測（規劃：<等級>）」，規劃的等級放在另一欄，絕不顯示成目前的等級。今天：規劃中（還沒有這個欄位）。
- **關口**：第 6 站的整合檢查（T4）和齊平底線（P）跑過之後，這一站用它們的結果判定：整合會傷到現有配方是「拉肚子」，實測變差是「變差」，只有實測贏過食物本身才能叫「進化」；沒有對照證據就寫「齊平，未宣稱改善」或「尚未證明」。跑之前一律標「和單吃食物比：未測」。
- 今天：成分判定由 `catalog_core.derive()` 自動算出，但只有靜態量測；關口規劃中。所以這一站在流程上畫成 `◐` 部分完成，不是 `●`。

### 8 核准（D7、D11、D21）

- D21、D28 起：A 級（只改機制）靜態證據就能吸收、B 級（模型會讀的文字）要有判定「吸收」的試吃、C 級問你。吸收是 Claude 在 `claude/oaw-2` 把單位重建成 OAW 程式和測試，再用 `record-absorption` 記錄（單位、級別、commit、測試、證據依據、排掉和暫留的單位各附一行理由）；引擎拒收沒有試吃的 B 級和沒有你同意紀錄的 C 級。記錄之後食物移到第 9 站等發布。
- 試吃判定「吸收」或「插上」、或有成分過了 A/B 的食物停在這一站，標「自動（Claude 接手）」；只剩匯入的歷史提案時標「只有可選的決定」。
- 下面是照原樣複製吸收的舊流程，現在是可選的 owner 動作。系統不會自動安裝或套用。
- 吸收先預覽要寫哪些檔案，你確認後才動手。只選了歷史提案時，只記成待辦（寫進決定紀錄），不改任何檔案，也不產生新版本。
- 照原樣複製只對有經同意的 A/B（D17）涵蓋的成分開放；引擎還沒有會寫這種紀錄的 runner，所以今天複製吸收走不到，判定吸收的食物由 Claude 重建（上面）。
- **論文永遠不走「複製文字」的吸收**：論文的想法要重新實作成 OAW 的程式和測試（D5、D21），不複製原文。`absorb` 拒絕論文的任何成分，只接受它匯入的歷史提案，而且只記成待辦。

### 9 版本（D3、D6、D12、D14）

- **D21 重建的單位等發布**：吸收紀錄的單位在工作分支上，等你合併 PR；網頁、選單和 mod 標「等發布（合併 PR 時一次決定）」，不是「等你」，因為整個分支一次決定。發布後再記一筆 `release: {"state": "released"}` 的吸收紀錄，食物就標「沒有待辦」。這些單位也算進「已吸收的成分」。
- 每次照原樣複製吸收或移除都產生一個專案版本和還原點。名稱遵守 SemVer 2.0：預設 release `2.0.1`（已發布），專案組合是 build metadata `2.0.1+build.N.<hash7>`（`hash7` 是內容 hash 的前 7 碼），附一個人看得懂的標籤，寫加了或拿掉什麼。內容相同的組合沿用同一個版本。
- **吸收裝什麼**：照原樣複製 skill 資料夾裡的文字，加上食物根目錄的授權檔和 NOTICE（LICENSE、NOTICE、COPYING），再加一份 `OAW-UPSTREAM.md`，寫明來源 repo（本機 repo 只寫私有代號）、pinned commit、封存的 tree hash、複製了哪些檔案、授權，以及「沒有修改」（D14 的授權路線）。重新實作成 OAW 部件以後，這份說明要改寫成修改說明。
- 一鍵還原到任何一個舊版本：預覽 → 還原 → doctor。還原只切換 OAW 安裝層，不動專案紀錄。還原是線性的：只有移除版本，沒有逐項開關（D14）。
- 每一版都列出它有哪些 skill 和成分，以及和預設 release 比的效果，每一行一個證據等級。系統在吸收當下做這個簡單評估；品質只採計這一版裝著的食物的實測證據，沒有就寫「未量測」，絕不寫「加強」。
- 移除（D6）：任何吸收進來的 skill 都能逐專案移除，包括內建的 EGM：預覽 → 備份 → 移除，記錄原因。
- **再加回要重新測試（D6）**：
  - 吸收進來的 skill：移除後，`absorb` 和網頁都拒絕用舊的試吃紀錄再吸收；要先重新試吃（免費），再核准。食物停在第 9 站，標 `⊖` 已移除，按鈕是「再送去試吃（免費）」。
  - 用「還原到這版」把移除過的 skill 還原回來時，它會標「移除後又還原回來：要重新測試」，按鈕是「重新試吃（免費）」。
  - 內建 skill 和 EGM：`readd` 經 `oaw.py migrate` 加回，決定紀錄寫「要重新測試」，版本的品質寫「未量測」。v0 沒有可以替它們跑的測試（它們是 OAW 自己的範本，不經過試吃），所以「重新測試」今天的意思是：在有實測之前，一律當成未測。
- 引用（D3）：每個版本只引用真正用到的上游材料，並寫出用在哪裡；移除或沒採用的列出原因。今天：吸收收據記下每樣食物的 pinned commit 和 tree hash，每個吸收的 skill 資料夾帶 `OAW-UPSTREAM.md`；release 的引用在 `docs/releases/<version>-sources.json`。**每個專案版本自動列出「用在哪裡／沒採用的原因」的引用清單：規劃中。**
- release 目標（D14）：所有批次進還沒打 tag 的 `2.0.0`；`2.0.0` 先打 tag 的話，相容的新增進 `2.x`，不相容的（OAW-19、OAW-12/13、OAW-25）等 `3.0.0`。此為 D14 當時的目標；2.0.0 最終從未打 tag 或發布，首個發布版本是 `v2.0.1`。今天：`RELEASE` 固定是 `2.0.1`（已發布），切換 release 目標是規劃中。

## 怎麼操作（D8）

OAW 由 Claude Code 和 Codex 共用。網頁、終端選單和 CLI 呼叫同一套引擎、讀同一份 `view.json`、用同一套顯示規則。需要 Python 3.10+（只用標準函式庫）和 git。指令都在 OAW checkout 執行，用 `--target` 指向專案：

```bash
python3 scripts/oaw.py init --target /path/to/project       # 專案還沒裝 OAW 時先裝
python3 scripts/catalog.py ui --target /path/to/project     # 網頁：消化道，可以直接操作
python3 scripts/catalog.py menu --target /path/to/project   # 終端選單：同樣的站別和動作（Codex、沒有瀏覽器時）
python3 scripts/oaw_status.py --project /path/to/project    # 只看，不做任何動作
```

在 Claude Code 裡還可以裝選用的 mod `oaw-digest-monitor`（`mods/oaw-digest-monitor/`）：對話旁的消化道畫面，九站、食糰、卡點說明和這一站的動作都和網頁一樣，動作也一樣交給 `catalog.py`（先預覽，按「確認套用」才加 `--apply`；分流旗標只複製終端指令，確認碼仍要你自己在終端輸入）。Codex 沒有可以掛畫面的擴充介面，用上面三個指令。

### 網頁（`catalog.py ui`）

- 只綁 `127.0.0.1`，印出並開啟 `http://127.0.0.1:<port>/#t=<通行碼>`，Ctrl+C 結束。要用印出來的完整網址開，少了 `#t=…` 頁面會拒絕連線。`--no-browser` 只印網址，`--port N` 指定埠號。
- 主畫面是一條消化道（D23）：九站是管子上的九個停靠點，寬螢幕繞成 S 形，窄螢幕（手機、半個螢幕，寬度不到 620 px）改成由上往下的一條，不會左右捲動。每一站寫站名、器官和它是哪一種：入口＝口、封存＝食道、靜態＝胃、計畫＝十二指腸、盲審＝肝、實測＝小腸、分流＝大腸、核准＝門靜脈、版本＝全身；器官只是圖說，不代表那一站多做了什麼。器官名稱和站別表一樣來自 `view.json`（`organ_zh`）。
- 兩條入口（A 每週偵查、B 你點名）從左邊流進「口」；按一下會跳到右邊的表單。分流（大腸）旁邊有兩個出口，寫排掉和暫留的成分數；版本（全身）旁邊寫在目前版本的成分數。管子上有一道蠕動的波紋，只是表示這是消化道。
- 每樣食物是一顆有自己顏色的食糰，停在它真正的那一站；同一站有好幾樣時沿著管子排開（太擠時顯示「+N」，每一樣都在下面的食物列表）。食糰上的記號來自每樣食物的 `pipeline.waiting_on`：
  - 藍色「!」：在等你（只有入口、C 級問題、只有你能做的前置、移除 skill，D28）。
  - 橘色「»」：自動（Claude 接手）：下一步由 Claude 做（試吃、重跑、重建、記錄）。
  - 青色「↑」：等發布：單位已在工作分支重建，你合併 PR 時整個分支一次決定。
  - 灰色「?」：只剩可選的決定（例如已移除、已還原掉、只剩匯入的歷史提案）。
  - 不動的虛線圈：在等規劃中的步驟（例如行為 A/B、Elephant 替論文拆成分）；v0 沒辦法讓它往下走，你也不用做什麼。
  - 轉圈：系統這一刻真的在處理它（試吃中，依 `status.json`）。其他時候食物都是停著的，畫面不會假裝它在動。
- 重新整理後站別變了，食糰會沿著管子滑到新的站；試吃進行中，食糰跟著 `status.json` 停在封存或靜態，試吃結束、新的 `view.json` 讀進來之後才移到結果的那一站，不會先跳回入口。系統設定「減少動態效果」時，波紋、轉圈、上下浮動和滑動都停掉，直接顯示在新的站。
- 點食糰（或用 Tab 移到它再按 Enter），或點下面食物列表的名字，選一樣食物：管子上它走過的那一段會用它的顏色標出來，下面顯示：
  - 名稱和來源：repo 的 commit；論文的 arXiv 版本＋PDF 的 sha256（還沒封存的論文寫「未固定版本」）。
  - 九段的進度條和「現在」：在哪一站、在等誰、這一站的說明。
  - **卡點說明**：卡在哪、依據（哪一個決定或規則，例如 D17、D7、旗標）、你不處理會怎樣；紀錄裡沒寫的事（例如為什麼當初沒有試吃、規劃中的步驟什麼時候做好）就直接寫「紀錄沒寫」，不會編。內容來自 `view.json` 的 `pipeline.blocker`，`catalog.py menu` 的「4 食物卡」也印同一段。
  - **這一站能做的動作**（和以前一樣是引擎的動作）：
    - 入口：送去試吃、忘掉這樣食物
    - 封存（試吃失敗）：再送去試吃
    - 靜態：規則更新時「用新規則再試吃（免費）」；有高嚴重度旗標時顯示可以複製的完整 `menu` 指令（確認碼只在終端），網頁上沒有分流按鈕
    - 計畫：看計畫（食物過了這一站才有）；「計畫：匯入紀錄」匯入 Elephant／Goldfish 紀錄
    - 分流：忘掉這樣食物（成分都暫留或排掉時）
    - 核准：吸收選中的成分…（勾選成分 → 預覽 → 確認）、忘掉這樣食物
    - 版本：移除；成分被還原掉時「還原到這版」；移除後「再送去試吃（免費）」
  - **看不懂？問這個卡點**：三個現成的問題（這個卡點是什麼意思？不處理會怎樣？你建議怎麼做？為什麼？）或自己寫（最多 500 字）。網頁沒有模型，所以問題只是記下來：寫進專案的 `.oaw/catalog/questions.jsonl`（和其他 catalog 狀態一樣只留在這台電腦），畫面顯示「已記下，Claude 會在對話裡回答」，並且可以一鍵複製「問題＋這樣食物的資料」，貼到和 Claude 的對話裡。`catalog.py questions` 列出還沒回答的問題，`--answered 編號` 標成已回答；`oaw_status.py` 會寫有幾個還沒回答。
  - 吸收／暫留／排掉的比例條和數字；還沒試吃、但有匯入紀錄時，畫的是紀錄裡的提案，標「歷史證據，不計入判定」。
  - 食物卡：判定、安全、旗標、成分（可以勾選要吸收的）、計畫、Elephant／Goldfish 紀錄。
- 「忘掉這樣食物」會刪掉它的登記和證據摘要（決定紀錄保留），和成分判定的「排掉」不是同一件事。
- 盲審和實測是虛線的站，標「規劃中」，沒有按鈕；食物會被畫成「經過」它們，但不會被當成已經做過。
- 右邊「餵一樣新食物」是兩條入口的表單（你點名、每週偵查）和「匯入紀錄」。下面「版本（全身）：我的 OAW」：目前版本、skill 清單（可以移除單一 skill 或整組 EGM、加回）、和預設比的效果、版本時間線（每一版都能還原）、常設預算。管子下方的「版本與 skill」也會跳到這裡。
- 試吃完成的提示依結果上色：有疑慮是琥珀色，未測是灰色，有毒是紅色；只有全部實測營養才是綠色。
- 還沒有食物時，畫面是空的消化道（九站和兩條入口都畫出來）和一句怎麼加第一樣食物。
- 深色和淺色都有，鍵盤操作時看得到焦點框；不載入任何外部字型或程式。

### 終端選單（`catalog.py menu`）

- 每次回到主畫面都先印出同一張站別表，一樣食物一行，例如：

  ```text
  sweet-notes  入口 ● 封存 ● 靜態 ● 計畫 ◐ 盲審 ┄ 實測 ┄ 分流 ◉ 核准 ○ 版本 ○  暫留 2 個成分（1 個 skill 文字缺行為 A/B，D17）：…
  ```

  `oaw_status.py` 印的是同一張表。
- 下面用字母列出每樣食物這一站能做的動作（和網頁的按鈕一樣，例如 `a. sweet-notes · 分流 · 忘掉這樣食物`），輸入字母就執行；需要確認碼的分流旗標也在這裡。不是互動式終端機時，分流畫面先說明只能「確認有毒」，不會先問原因再拒絕。分流畫面只列高、中嚴重度的旗標，並寫出有幾個低嚴重度旗標不需分流。
- 數字選項 1–13 是各個畫面，名稱前面標它屬於哪一站：我的 OAW、你點名、每週偵查、食物卡、核准（吸收）、移除 skill／EGM、看計畫、匯入紀錄、版本時間線／還原、重新評估、常設預算（版本）、分流旗標、加回 EGM／內建 skill。0 離開。不需要 curses。

| 入口 | `add URL [URL ...] [--no-taste]`、`scout`、`scout list`、`scout pick N [N ...] [--no-taste]`、`forget FOOD [--apply]` |

| 實測 | `record-tasting --food FOOD --file 試吃紀錄.json [--apply]`（Claude 的試吃，D25、D28） |
| 核准 | `record-absorption --food FOOD --file 吸收紀錄.json [--apply]`（D21 重建，D28）、`absorb FOOD --components ID[,ID] [--apply]`（照原樣複製，可選） |

### 確認碼怎麼用

設定常設預算和分流旗標（`--benign`／`--allergen`）只有 owner 能做：

- **CLI**：在你自己開的**互動終端**（PowerShell、cmd；Git Bash 請用 `winpty`）執行 `policy set ...` 或 `triage ...`。終端印出 6 位數確認碼，同一個指令接著請你打回去，對了才生效。沒有 `--confirm` 參數，也不會寫任何待確認檔。
- **網頁和 `menu`**：確認碼印在啟動 `ui` 或 `menu` 的那個終端，只存在那個程序的記憶體裡；你把它輸回頁面或選單。10 分鐘內有效、只能試一次、綁定那一組設定；同一次啟動錯三次就不再接受確認，要重新啟動。
- 沒有互動終端（stdin 和 stderr 不是終端機，例如 agent 在背景執行、輸出導到檔案）時，根本不會產生確認碼，指令直接拒絕。

**這只是減速帶，不是身分驗證。** 確認碼擋住的是「agent 透過 catalog 指令替你設定」這條路；任何能在你的終端打字的人或程式（包括在 PTY 裡跑指令的 agent），都能看到並輸入確認碼。`policy.json` 和 `decisions.jsonl` 是沒有簽章的專案檔，對專案有寫入權的程式可以直接改它們，所以紀錄裡寫的是 `confirmed_via: code typed back on an interactive terminal (unauthenticated)`，不會寫「由 owner 確認」。請自己輸入確認碼，不要貼給 agent。

## 一定要守的規則

- **沒有證據就沒有判定**。判定只由 `catalog_core.derive()` 從證據和你的決定算出來；星數、作者和名氣只決定偵查清單的排序。匯入的報告是歷史證據，只顯示、不計入判定。
- **食物不進專案，也不執行**，直到你核准吸收。食物或報告裡的文字是資料，不是指令，不能授權任何動作。
- **只有你能判「有毒」**。自動掃描只舉旗，不會替作者貼上有毒的標籤。
- **模型面向的文字要過 A/B**。靜態檢查通過的 skill 文字只是「暫留：缺行為 A/B」，不會顯示成綠色的吸收（D17）。
- **先預覽、再備份、才動手**。吸收、移除、加回、還原都先預覽；套用前先存還原點。
- **還原只動 OAW 安裝層**：只寫入或刪除 OAW 自己會安裝的路徑（OAW 範本、吸收進來的 skill 文字和它的授權檔、出處說明、EGM runtime、吸收收據），絕不碰 `.git/`、host 設定（`.claude/settings*.json`、`.codex/`、`.mcp.json`）或專案紀錄。你宣告的自訂檔（例如保留的 `AGENTS.md`）照原樣留著；不屬於目前安裝層的現有檔案會擋住還原，不會被蓋掉。還原點只接受這台電腦替這個專案建立、記在 `LAB_HOME` 索引裡的那些，`builds.json` 寫什麼都不算數。
- **移除只刪查得到的檔案**：吸收收據是會 commit 的共用資料，所以移除前逐檔確認它在那個 skill 的資料夾裡、在 `install.json` 裡、hash 也相同；有一個不符就整個拒絕。移除的名稱只代表一件事：`egm` 是整組 EGM，內建 skill 名稱是那個 skill，其他名稱是你吸收進來的那一個 skill；要移除一樣食物的全部 skill，加 `--food`。食物的 id 不會取 `egm` 或內建 skill 的名稱。內建 skill 和 EGM 經 `oaw.py migrate` 移除和加回（先備份到 `.oaw/backups/`）；移除不會順帶新增，加回不會順帶停用。
- **「加強」只在有實測證據時出現**，否則一律寫「未量測」。執行中只顯示進度和花費，不顯示即時分數，避免看了結果再停掉重跑。
- **網頁只給你自己用**：只綁 `127.0.0.1`，每次啟動換一個通行碼，拒絕其他 Host 和跨站請求，動作只接受 JSON POST，一次只跑一個動作。食物裡的文字一律當純文字顯示，不渲染食物附帶的 HTML、SVG 或圖片。

## 舊 catalog 原型限制與目前範圍

- **D21 的分級由 Claude 做，引擎只記錄和檢查**：引擎不會自己判 A／B／C、不會自己重建或試吃；它收 Claude 的試吃和吸收紀錄，檢查 D28 和 D21 的規則（食物組要跑過、B 級要有判定吸收的試吃、C 級要有你的同意紀錄），再畫出來。D21 目前用在 OAW 自己吃食物（寫成 `claude/oaw-2` 上的程式），還沒用在你專案裡的 skill 吸收。「Claude 接手」沒有排程：在下一次 Claude 工作階段處理。
- **自動化與實驗結果分開**：維護者離線試吃已有 X1、X2、I16、H1 等紀錄；這不代表 catalog 具備自動排程與完整試吃引擎。個別食物沒有有效結果時仍標未量測。
- **維護者 promotion 依證據；使用者安裝依選擇**：catalog 的模型文字吸收仍需符合 D17 的行為證據；使用者 add 可安裝未試吃內容，保留其狀態，不自動變成維護者推薦。
- **catalog absorb 的複製路徑**保留原文字與來源；維護者 D21 的具名重建另以程式、測試和 record-absorption 記錄，不能混成同一種證據。
- **舊 catalog absorb 只吸收純文字 skill**：此限制不適用於有明確 consent 的使用者 add 路線。catalog 中的 hooks、MCP server、腳本、manifest 等成分只記成待辦，不由該路徑安裝或執行。SKILL.md（或它附帶的說明檔）裡只要叫 agent 執行指令（程式碼區塊、行內指令、「執行 `…`」），或碰到任何旗標規則（網路、家目錄、`curl | sh`…），就算 `X1-inline`，要在可拋棄環境測過才能吸收；旗標分流成良性也一樣。
- **D18 的規劃等級欄位、每版的引用清單（D3）、release 目標切換（D14）、Elephant 提案（D10）、`policy set` 的 PRE-01 形狀（D13）**：都還沒做。
- **來源只限 github.com repo、arXiv 論文，以及本機 `file://` repo 或 PDF**。其他網頁和 DOI 是規劃中。私有 repo 抓不到，因為 GitHub token 不會交給 git；`GITHUB_TOKEN` 只用在偵查搜尋。試吃抓整份 depth-1 快照（有大小上限）。
- **Elephant 替論文拆成分是規劃中**：今天論文的成分只能從匯入的消化紀錄來（歷史證據），所以論文不會出現在「靜態量測」的成分判定裡。論文的計畫沿用 repo 的測試步驟，還沒有專給論文的計畫（例如「重新實作後跑測試」）。
- **偵查沒有排程**：要你每週按一次。
- **分流旗標不在網頁上**：有高嚴重度旗標的食物，網頁顯示 `menu` 的完整指令。
- hash 鏈事件紀錄、`catalog.py check` 重算 gate、`install.json` schema 2 都還沒做。

### 專案裡：`.oaw/catalog/`

| 檔案 | 內容 |

| `policy.json` | 常設預算（設定後才有） |
| `scout.json` | 偵查候選、被濾掉的數量、每次偵查的時間範圍和沒抓到的數量（偵查後才有） |

系統會產生 `.oaw/catalog/.gitignore`，只讓 `builds.json` 和 `absorbed/*.json` 可以 commit，其他資料只留在這台電腦。

### 專案外：`LAB_HOME`

| 系統 | 預設位置 |
|---|---|
| Windows | `%LOCALAPPDATA%\oaw\lab` |
| macOS | `~/Library/Application Support/oaw/lab` |
| Linux | `$XDG_DATA_HOME/oaw/lab`（預設 `~/.local/share/oaw/lab`） |

可以用環境變數 `OAW_LAB_HOME` 改到別的目錄，但它必須在專案外，也不能在 OAW checkout 裡，否則指令會拒絕。

| 路徑 | 內容 |
|---|---|
| `foods/<food>/<commit>/source.tar`、`inventory.json` | 封存的食物快照（唯讀）和檔案清單；論文是 `foods/<food>/<版本>-<hash>/`，tar 裡只有 `paper.pdf` 和 `metadata.json` |
| `builds/<專案代碼>/<hash>.tar` | 每個版本的還原點 |
| `builds/<專案代碼>/index.json` | 這台電腦替這個專案建立過的還原點（還原只接受這裡列的） |

還原點只存在建立它的那台電腦的 `LAB_HOME`。刪掉 `builds/` 就不能再還原到那些版本；隊友 clone 專案後看得到 `builds.json`，但不能用你的還原點。
