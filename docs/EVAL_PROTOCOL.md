# 評估與試吃的量測規則（D32，2026-11-14 補上量法總覽）

吸收別人的 skill、或改 OAW 自己的預設之前，都照這一頁量。決定的出處是 `records` 分支的 `digestion-2026-11-03/ingest/DECISIONS.md`（D26、D29、D32、D35），證據在 `records/digestion-2026-11-07/validation/RESULT.md`。完整流程見 [SKILL_INTAKE.md](SKILL_INTAKE.md) 開頭的一頁版。

## 先選量法

要回答的問題不同，量法就不同。第一列的快速判定是 2026-11-14 新加的（D50），還沒有用在真的食物上；其餘四種是 OAW 到 2.0.1 為止實際用過、留下紀錄的。每一種都只回答自己那一題。

| 要回答的問題 | 量法 | 規則與工具 | 用過的紀錄（`records` 分支） |
|---|---|---|---|
| 一樣食物要不要吸收，要很快有答案 | **快速判定**：原生先跑 3 題，已經做得到就 NO；有漏才讓食物跑，補得上、沒弄壞、不太貴才 YES。沒有「未定」 | [FAST_SCREEN.md](FAST_SCREEN.md)；`scripts/fast_screen.py`；流程在 [SKILL_INTAKE.md](SKILL_INTAKE.md) 開頭 | `v2.0.1-experiments/JEV/`（判定模型的校準） |
| 一個 skill 或一個做法，值不值得進預設 | **試吃**：同一批題目，原生對官方安裝，兩家盲評，配對統計 | 這一頁「設計」以下；`scripts/eval_stats.py` | `digestion-2026-11-07/validation/` |
| 整包 harness，裝了有沒有比不裝好 | **裝對不裝**：凍結的題組，每題全新 context，每個 host 各自一格；token 算 logical 總量，含快取讀取與 subagent | 判定用這一頁的統計；runner 還沒整理成工具（#9） | `v2.0.1-experiments/H1/` |
| 比較貴的做法（多輪審查、多 agent），值不值得花錢去比 | **先校準**：只跑原生，對照已核實的缺陷清單看有沒有漏。原生都找到了就不用比；有漏才出資跑貴的那一組 | 判定表在開跑前寫好：天花板、有空間、無結論 | `v2.0.1-experiments/EGM-calibration/` |
| 一份比較的帳完不完整 | **評估帳本**：計畫內的每一次作答都列出來；失敗和重試照樣算錢；缺的資料標成缺，不當成 0 | [EVAL_LEDGER.md](EVAL_LEDGER.md)；`scripts/eval_ledger.py` | `v2.0.1-experiments/FIXCHECK/`（匯入舊資料） |

後四種量法共用的規則，出處是 D26、D32、D45、D48 與上面幾份紀錄：

- **先寫下來再跑。** 題目、判定表、停止條件、預算在開跑前寫好，雜湊先推上 `records`。
- **有了資料之後才改的規則是偏差，不是修正。** 照原規則得到的是正式結果；改過之後的只能當描述，並且寫明改了什麼。只有程式和登記的文字不一致時，改程式才叫修正。
- **先用真的 host 做一次小額試跑**，確認隔離、計量、工具都正常，再跑正式資料。
- **預算用量出來的單價算**：試跑的實測單價 × 次數 × 1.3。沒量過的估計不當預算。
- **關掉會連外的工具。** host 內建的雲端、外掛、瀏覽器類工具不受本機網路限制；不關，題目的答案可能查得到。
- **結果紀錄交給另一個家族、全新 context 的 agent 重算一次。** 紀錄只寫量到的數字與差異，不寫原因和預測。
- **一格只有一次作答時，不說「有差」。** 做不出判定就寫未定或無結論，不補抽、不換題。

這些量法都沒有證明過「整包 OAW 有幫助」：H1 的合併判定是未定。量法公正，不等於被量的東西通過。

## 設計
- **題目**：預設 12 題各跑 1 次，把題目當成隨機樣本。原生已經接近滿分的題目要換掉。
- **出題者**：由不知道 OAW 實作的新 agent 出題，題目的 sha256 推上 `records` 之後才開跑。
- **組別**：至少要有原生和食物（官方安裝）兩組。skill 類多一組「只放 description」；量偵測能力時，加一組正對照和一組不洩題的便宜做法。
- **條件**：至少一個「食物的主場」條件；排掉之前一定要有。
- **預算**：2.0.1 發佈前每項 30M（D35），X2 是 60M（D36），只用訂閱計費（apiKeySource 為 none）。

## 評分
- **兩家盲評**：Opus 和 Codex 各評一次，評分者看不到組別。
- **更好、等價、更差都要兩家都成立才算**，只評一次或同家族評兩次只能記「未定」（kappa 0.97，不算獨立）。
- 錯誤陳述數也只在兩家一致時才算。
- 花 0 token、或被用量上限切斷的評分算「沒跑」，不是 0 分。

## 判定（`scripts/eval_stats.py`）
- **品質**：每題算食物減原生的配對差，對題目做 bootstrap（10,000 次、seed 20261107）。

  | 類別 | 條件 |
  |---|---|
  | 更好 | 95% 區間在好的那一邊不含 0 |
  | 更差 | 95% 區間在壞的那一邊不含 0 |
  | 等價 | 90% 區間落在邊界內（TOST） |
  | 未定 | 以上都不是 |

  邊界：覆蓋率 ±0.10、每份答案的錯誤陳述 ±0.5、偵測數 ±1。
- **零變異下限**：每格只跑 1 次時，標準誤不能小於 `floor_sd × √(2/題數)`。`floor_sd` 用同一題庫、同一模型以前重複作答的合併題內標準差（`pooled_within_sd()`），寫進 PREREG。
- **合併**：一次評分內用 `quality()` 合併覆蓋率和錯誤陳述，兩家評分用 `agree()`（兩家判法不同就是未定），多個條件用 `lowest()`（最差的條件決定）。
- **成本**：每題 token 比取 log 後做 bootstrap。

  | 類別 | 條件 |
  |---|---|
  | 太貴 | 區間下界超過 1.5 倍 |
  | 比較省 | 區間上界低於 1 倍 |
  | 在上限內 | 區間上界不超過 1.5 倍 |
  | 未定 | 區間跨過 1.5 倍 |

## 結果
`eval_stats.judgment()` 產生記帳用的欄位：`quality`、`quality_class`、`cost_ratio`、`cost_ci`、`cheaper`、`grading`（`cross-family` 或 `mechanical`）、`conditions`。`catalog.py record-tasting` 會檢查判定和這些欄位一致。

| 品質 | 成本 | 結果 |
|---|---|---|
| 更好 | 不是太貴 | 進預設 |
| 更好 | 太貴 | 可選用 |
| 等價 | 比較省 | 進預設 |
| 等價 | 其他 | 可選用；太貴則排掉 |
| 未定 | 不是太貴 | 可選用（能力未定）；未定永遠不會變成預設 |
| 未定 | 太貴 | 排掉 |
| 更差 | 任何成本 | 排掉 |

不在這一頁裡的：D21 的 C 級問題（執行期相依、會執行食物程式）照舊問 owner。
