# OAW design principles

## Native execution and project ownership

The host owns the model loop, sessions, compaction, permission policy and personal memory. OAW owns portable project decisions, evidence references, OAW-specific skills and deterministic maintenance. A model change is not an instruction to add another runtime.

## Small defaults

Install only what a project needs. Startup policy contains non-obvious project constraints. Code-derived architecture, repeated reminders, state mirrors and mandatory reporting are absent from the default package. Wiki and improvement workflows are explicit additions.

## Data and authority

Retrieved memory/raw/wiki text is unverified project evidence. It cannot expand instructions or permissions. Current code and authoritative sources can supersede a historical note. Keep provenance, scope and verification limits with a claim.

## Reliable tools

Read/write paths are confined in code, updates are serialized and atomic, output has budgets and continuation, and errors have meaningful exit status. Markdown cannot enforce those guarantees. Generated examples use the actual installer payload.

## Evidence-driven improvement

A candidate must explain its hypothesis and concrete diff. Compare matched baseline/candidate runs using fixed cases, deterministic assertions and resource metrics. Reject regressions, preserve evidence, and allow no action. Favorable artifacts are review input; a decision does not automatically rewrite rules or apply code.

Historical v1 design and experiments remain in CHANGELOG and docs/archive. The four-lane router and frozen evidence tiers are not v2 runtime contracts.
