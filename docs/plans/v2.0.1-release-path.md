# OAW 2.0.1 發佈路徑（收斂版）

> 2026-11-12。依據 D45（records 分支 `records/digestion-2026-11-03/ingest/DECISIONS.md`）。
> 這份取代 `v2.0.1-execution.md` 裡 W5、W6 的排程，和 `v2.0.1-value-check.md` 第 6 節的「其他」。那兩份留作背景。

## 1. 一句話

從現在到發佈只做一條線：**先開三個平台的 CI → 修 H1 追到的五個缺陷 → 複查一次 → 文件 → 審查 → owner 合併、打 tag**。
其他的事排在發佈之後，或停放並寫明什麼時候重啟。發佈前不再開新實驗。

## 2. 現況：量到了什麼

每個數字只在自己的 protocol 內可比，不能互相並排。

| 量什麼 | 結果 | 對 2.0.1 的意思 |
|---|---|---|
| X4 裝了以後開場多花多少 | 過：Claude 上多 1,241 tokens（約 3.7%） | 裝著不用，成本很小 |
| X3b agent 會不會選對審查模式 | 過：Haiku 6/6、Opus 5/6、Sonnet 5/6 | 政策那一行留著 |

| X2 設計審查用哪一種 | 一次原生的全新 context 審查：找到 47/48 個埋的缺陷；EGM 貴 27–29 倍，沒有更準 | `auto` 維持原生一次 |

| H1 整包裝 對 不裝 | 合併「未定」：Codex 格有幫助，Claude 格未定；token 1.9–2.6 倍，幾乎都在大改動 | 見第 3 節 |

外部食物：graphify、codegraph、court-skill 排掉；TokenEconomizer 可選用。其中三項的判定還要重判（#15）。

## 3. D40 的決定（記為 D45）

H1 的結果落在「agent 不選邊，交給 owner 的 Fable 5.2」。owner 把這個 session 換成 Fable 5.2 之後，決定如下。

**預設不拿掉任何零件。** 合併結果是「未定」，不是「更慘」或「雞肋」。Claude 格輸的地方追得到原因，是規則寫法，不是零件本身。

**發佈前修五個缺陷**（證據在 records 分支 `records/v2.0.1-experiments/H1/AUDIT-D40.md`）：

| # | 問題 | 看到的證據 | 改法 |
|---|---|---|---|
| M1 | 筆記幾乎沒被寫 | 記憶 4 題，兩格都只有「明講要記」那題去寫。對照組的兩行規則沒有條件，4 題都寫、都記得 | 存的規則改成沒有條件：後面會用到、程式碼裡看不出來的決定和事實，session 結束前就存 |
| M2 | 專案筆記是空的，agent 查完就停 | Claude 格輸的兩題：原生自己會翻前面的紀錄，裝了 OAW 反而沒翻 | 查不到時明講「沒有紀錄」，接著用 host 自己的記憶和紀錄 |
| M3 | Codex 的沙盒寫不進筆記檔 | Codex 預設把專案裡的 `.agents/` 設成唯讀，`memory add` 失敗 | 寫不進去時改寫到 `.oaw/` 底下的待併檔，查的時候兩邊都讀。2.0.1 不搬既有檔案 |
| R1 | Codex 上的審查指令跑不起來 | `codex review --uncommitted` 在 Codex 的 session 裡 4 次都失敗 | 審查步驟改成開一個全新的 subagent |
| R2 | deep 的多輪審查很貴，沒換到分數 | design 題比原生貴 3.3–8.7 倍；「最多 3 輪」沒有量測支持 | deep 的 code review 預設一輪 |

**不做的**：把全新 context 審查整個移出預設（只減掉多出來的輪數）；加題重測之後才發佈。

## 4. 發佈路徑（milestone v2.0.1）

| 步 | 做什麼 | 完成條件 | 花費 | 追蹤 |
|---|---|---|---|---|
| 1 | **先開 CI**：PR #16 的 base 改成 `main`，每次 push 跑 Linux、macOS、Windows | 6 個 job 全綠 | 0 token | #18 |
| 2 | **修五個缺陷**。M3 動到筆記的存放，先給一個全新 context 審一次設計再寫 | 每項有不呼叫模型的測試；Codex 沙盒裡 `memory add` 成功；gate 通過 | 小 | #17 |
| 3 | **複查一次**：只跑 O 組、H1 凍結的 12 題、兩格、同一個 runner 和判定程式 | 下面的通過條件 | Claude 預估 9M 以內，到 12M 停 | #17 |
| 4 | **文件**：README 照實寫每個量測；`VERSION.json` 改 2.0.1；升級說明、CHANGELOG；吸收 SOP 併進 `docs/SKILL_INTAKE.md`；真實專案回饋的三件 | 每個宣稱都指得到一筆紀錄 | 小 | #10、#12 |
| 5 | **完整審查**：Codex，最多 3 輪 | 第 3 輪後只修會造成錯誤結果或資料損失的問題，其餘記成 issue | Codex | #11 |
| 6 | **owner 合併 PR #16**（用 merge commit，PR #4 會一起顯示為已合併）、在 `main` 打 tag `v2.0.1`、建 release | tag 存在 | owner | #11 |

**第 3 步的通過條件**（細節先寫進 records 再跑）：

- 記憶題：每格至少 3/4 題有執行成功的筆記寫入，而且記得的題數不比 H1 的 O 少。
- 小改動題：分數不掉；token 不超過原生平均的 1.2 倍。
- 大改動題：每題分數不比 H1 的 O 低超過 0.10；Codex 格審查步驟 0 次失敗；design 題的 token 比 H1 的 O 少。
- 記憶那兩條沒過：M1、M2 還原，照 H1 原本的結果發佈。不試第二次。

複查只能說「修正有生效、沒有變差」。同一批題目被拿來找缺陷，所以它不是新的效果證據。README 的主要宣稱仍然是 H1 凍結的結果。

## 7. 做事規則的調整

前面幾輪實驗花了很多 token，多數結果是「未定」或「可選用」，主因是題目對原生太簡單。往後照這幾條：

1. **一次一條線。** 一條線沒收掉，不開下一條。
2. **量得出來才量。** 試跑後不到一半的題目低於滿分，就不測「有沒有更好」；改成只測「有沒有變差、多花多少」，或不測並記「沒測：天花板」。
3. **預算照試跑的實際單價估**：單價 × 題數 × 1.3，不用計畫時的猜測。
4. **修正只驗一次。** 沒過就還原，不反覆調。
5. **審查最多 3 輪**（原本就有，照做）。

owner 可以對個別情況取消任何一條。
