## 1. 一句話

從現在到發佈只做一條線：**先開三個平台的 CI → 修 H1 追到的五個缺陷 → 複查一次 → 文件 → 審查 → owner 合併、打 tag**。
第一步要 owner 先同意改 PR #16 的 base（見第 8 節）；等的期間先做第 2 步。
其他的事排在發佈之後，或停放並寫明什麼時候重啟。發佈前不再開新實驗。

## 3. D40 的決定（記為 D45）

H1 的結果落在「agent 不選邊，交給 owner 的 Fable 5.2」。owner 把這個 session 換成 Fable 5.2 之後，決定如下。

**預設不拿掉任何零件。** 合併結果是「未定」，不是「更慘」或「雞肋」。事後讀紀錄的觀察支持先修規則和兩個 Codex 上的缺陷。這些觀察不是登記過的檢定，所以「保留預設」是 D45 的決定，整包的效果仍然是「未定」。

**發佈前修五個缺陷**（證據在 records 分支 `records/v2.0.1-experiments/H1/AUDIT-D40.md`）：

| # | 問題 | 看到的證據 | 改法 |
|---|---|---|---|
| M1 | 筆記幾乎沒被寫 | 記憶 4 題，兩格都只有「明講要記」那題去寫。對照組的兩行規則沒有條件，4 題都寫、都記得 | 存的規則改成沒有條件：後面會用到、程式碼裡看不出來的決定和事實，session 結束前就存。`oaw-evidence` skill 裡「明講要求才存」的限制一起改。不相干的任務做完不必寫 |
| M2 | 專案筆記是空的，agent 查完就停 | Claude 格輸的兩題：原生自己會翻前面的紀錄，裝了 OAW 反而沒翻 | 查不到時明講「沒有紀錄」，接著用 host 自己的記憶和紀錄 |
| M3 | Codex 的沙盒寫不進筆記檔 | Codex 預設把專案裡的 `.agents/` 設成唯讀，`memory add` 失敗 | 只在明確的唯讀或權限錯誤時，改寫到 `.oaw/` 底下的待併檔；查的時候兩邊都讀。2.0.1 不搬既有檔案 |
| R1 | Codex 上的審查指令跑不起來 | `codex review --uncommitted` 在 Codex 的 session 裡 4 次都失敗 | 審查步驟改成開一個全新的 subagent |
| R2 | deep 的多輪審查很貴，沒換到分數 | design 題整題比原生貴 3.3–8.7 倍（整題的成本，不是只算多出來的輪數）；「最多 3 輪」沒有量測支持 | deep 的 code review 預設一輪。這是省成本的假設，要靠複查驗。風險：修完第一輪的問題時新引入的缺陷，不會再被獨立審一次 |

**不做的**：把全新 context 審查整個移出預設（只減掉多出來的輪數）；加題重測之後才發佈。

## 4. 發佈路徑（milestone v2.0.1）

| 步 | 做什麼 | 完成條件 | 花費 | 追蹤 |
|---|---|---|---|---|
| 1 | **先開 CI**：PR #16 的 base 改成 `main`（等 owner 同意），之後每次 push 跑 Linux、macOS、Windows | 6 個 job 全綠 | 0 token | #18 |
| 2 | **修五個缺陷**。M3 動到筆記的存放，先寫設計、給一個全新 context 審一次再寫（設計要定的事見下） | 每項有不呼叫模型的測試；Codex 沙盒裡 `memory add` 成功；`oaw_mode.py` 印的輪數和說明文字一致；gate 通過 | 小 | #17 |
| 3 | **複查一次**：只跑 O 組、H1 凍結的 12 題、兩格、同一個 runner 和同一套機械評分 | 見「第 3 步」 | Claude 預估約 8M，上限 17M（獨立帳本） | #17 |
| 4 | **文件**：README 照實寫每個量測；`VERSION.json` 改 2.0.1；升級說明、CHANGELOG；吸收 SOP 併進 `docs/SKILL_INTAKE.md`；真實專案回饋的三件 | 每個宣稱都指得到一筆紀錄 | 小 | #10、#12 |
| 5 | **完整審查**：Codex，最多 3 輪 | 第 3 輪後只修會造成錯誤結果或資料損失的問題，其餘記成 issue | Codex | #11 |
| 6 | **owner 合併 PR #16**（用 merge commit，PR #4 會一起顯示為已合併）、在 `main` 打 tag `v2.0.1`、建 release | tag 存在 | owner | #11 |

**第 2 步，M3 的設計要先定的事**

- 兩個來源的排序：recall 會依來源順序累積後截取，舊檔先讀的話，舊決定可能把待併檔裡的新決定擠掉。
- 被取代的紀錄和 cursor 怎麼跨兩個檔案算。
- 只有明確的唯讀或權限錯誤才改寫待併檔。路徑限制、拒收憑證、上鎖的原子更新都保留。鎖檔建在目標檔旁邊，所以只檢查目標檔可不可寫不夠。
- 不呼叫模型的回歸測試：舊檔和待併檔同時存在、權限恢復後交替寫入、並行寫入。

**第 3 步怎麼做**（細節寫成 `FIXCHECK.md` 推上 records，Codex 審過一次才跑）

- **自己的 manifest。** 綁定修正後的 OAW commit、H1 原本的題庫和評分器的摘要、H1 原本 O 和 N 計分列的摘要。H1 的 `FREEZE.json`、帳本、判定都不動。
- **自己的帳本。** 複查是一個新的實驗，不用 H1 剩下的 5.94M。H1 的 O 組在 Claude 格實測 12.76M；R2 生效的話 design 兩題會少約 5M，預估約 8M。上限 17M（12.76M × 1.3，第 7 節規則 3）。
- **比較方式。** 逐題把這次的 O 跟 H1 的 O、H1 的 N 平均並排：分數、token、記不記得。不產生新的 owner 判定詞。條件由一支不呼叫模型的 script 算，Codex 核對一次。

每項修正要看到自己的事件。沒觸發的記「未驗到」，不算通過：

| 修正 | 算「驗到」 |
|---|---|
| M1 | 記憶題裡，學到那個事實的 session 用 `memory add` 成功存了它（看指令、結束碼、存的內容） |
| M2 | recall 回空之後，同一個 session 接著查 host 自己的記憶或紀錄。M1 生效後 recall 多半不會空，這項很可能「未驗到」；輸出文字另有不呼叫模型的測試 |
| M3 | Codex 格 `memory add` 結束碼 0、寫進待併檔，後面的 session recall 得到 |
| R1 | Codex 格每一題該審的都完成一次 subagent 審查，沒有失敗的審查指令 |
| R2 | deep 題實際做完的 code review 是一輪；design 題的 token 比 H1 的 O 少 |

回歸門檻：

- 記憶題：每格至少 3/4 題驗到 M1；H1 的 O 記得的題，這次不能變成不記得；記得的題數不比 H1 的 O 少。
- 小改動題：分數不掉；token 不超過原生平均的 1.2 倍。
- 大改動題：每題分數不比 H1 的 O 低超過 0.10。
- 每一筆分數下降、每一題「記得變不記得」都逐題列出來，包含是哪幾個隱藏測試變了。0.10 是留給單次作答的波動，所以掉一條需求也可能落在門檻內。

沒過怎麼辦：

| 情況 | 處置 |
|---|---|
| M3 或 R1 的缺陷還在 | 擋發佈。這兩項有不呼叫模型的重現方式（Codex 沙盒探針、測試），修到重現方式通過，不重跑整個複查 |
| 記憶題的門檻沒過 | M1、M2 一起還原，README 照 H1 原本的結果寫 |
| design 題分數掉超過門檻 | R2 還原，README 寫明多輪審查的成本 |
| design 題的 token 沒有變少 | R2 留著，記「沒有量到省 token」，README 照實寫成本 |
| 小改動題沒過 | 規則類的三項（M1、M2、R2）都還原 |
| 資料沒跑完 | 不宣告通過。額度中斷從帳本續跑；到預算上限就停，帶實測數字問 owner |
| 有任何還原 | 最後的 commit 重新過 gate 和 CI，README 的限制跟著改 |

結論只寫「這次作答符合事先定的回歸門檻」，不寫「已證明沒有變差」：每題只跑一次，而且同一批題目被拿來找缺陷，所以它也不是新的效果證據。README 的主要宣稱仍然是 H1 凍結的結果。複查不做第二次。

## 7. 做事規則的調整

前面幾輪實驗花了很多 token，多數結果是「未定」或「可選用」，主因是題目對原生太簡單。往後照這幾條：

1. **一次一條線。** 一條線沒收掉，不開下一條。
2. **量得出來才量。** 試跑後不到一半的題目低於滿分，就不測「有沒有更好」；改成只測「有沒有變差、多花多少」，或不測並記「沒測：天花板」。吸收外部食物時例外：同類食物已經用過的比較方式照做，不為了省 token 刪組或刪格（D31 第 4 點，同一把尺）。
3. **預算照試跑的實際單價估**：單價 × 題數 × 1.3，不用計畫時的猜測。
4. **修正只驗一次。** 沒過就還原，不反覆調。有不呼叫模型的重現方式的產品缺陷例外：修到重現方式通過。
5. **審查最多 3 輪**（原本就有，照做）。

owner 可以對個別情況取消任何一條。
