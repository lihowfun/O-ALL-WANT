## 一頁摘要

**要做的四件事**
1. **一個審查入口 `oaw-review`**：
   - agent 在動手前和改完後各用一次。它依改動自己挑 light、standard 或 deep，自己跑對應的審查。
   - deep 先寫計畫、讓 EGM 審過，才開始寫程式。
   - owner 不用打指令，也不用重開 session。
2. **內建程式碼地圖 `oaw-codemap`**：
   - 以 OAW 自己的 `code_index.py` 為底，只用標準函式庫、單一檔案。
   - 吸收 codegraph 量得到的長處（少走步），避開量到的弱點（照圖講錯）。
   - 補上目前沒有的 TS/JS 呼叫追蹤。
3. **使用者自己加 skill**：
   - 輸入 `oaw.py add A B C`，系統只問一題三選一：OAW 加上 A B C、只用 A B C、或 AI 幫你配。
   - 裝完給一張「吸收清單」：裝了什麼、從哪來、試吃過沒、怎麼移除。
4. **做減法**：
   - 模型看得到的規則不增加。
   - 吸收 SOP 從 400 行縮成一頁（附錄 A）。
   - 能寫成程式的檢查，就不寫成提示。

**怎麼知道有沒有變好**
- 改預設之前，先跑事先登記的實驗 X1–X5。
- 量測用 D32 的尺：兩家評分、12 題各跑 1 次、零變異保護。
- 沒通過的以「可選用」出貨，不寫進預設。
- 發佈和實驗分開：
  - 發佈只等機械測試和兩個便宜的實驗（X3、X4）。
  - X1、X2 決定地圖和 EGM 要不要變成預設；還沒跑完就先用保守的預設出貨。

**花費**
- 這份計畫的審查花了 Claude 18.5M logical token，其中 17.1M 是快取讀取，另外花了 Codex 1.08M。
- 接下來的實驗和 E2E 約 Claude 29.6M、Codex 5–8M。每項上限 30M（D35：2.0.1 發佈前放寬）。

**owner 的決定**（第 8 節）：D32 量測的尺、D33 EGM 開關（開、自動、關，預設「自動」＝目前證據最好的審查）、D34 使用者安裝路線、D35 預算上限放寬。

## 2. 目標和不做的事

**目標**
- **G1 審查順暢**：agent 依改動自己挑深度、跑完審查，owner 不用操作。
- **G2 EGM 內建於 deep**：用開關控制（D33），「自動」用目前證據最好的設計審查；X2 確認正確性後再更新。
- **G3 地圖內建**：每個配方都裝；X1 通過才讓 agent 自己叫用。
- **G4 使用者自己加 skill**：三個動詞、問一題、一張清單。
- **G5 減法**：發佈時的設定，每個 session 開頭的 context 比 2.0.0 多不超過 600 token（X4）。
- **G6 可發佈**：v1 和 2.0.0 預覽版都能遷移；Windows 驗證、CI、文件。

**不做的事**
- 不加向量資料庫、agent 會寫入的圖記憶，或背景自我改寫（沿用 2.0.0 的排除）。
- OAW 本身不加 Node、MCP server 或其他執行期相依。使用者自己加的 skill 帶什麼相依，由使用者決定，清單上寫清楚。
- 不在每個 prompt 前注入地圖內容。
- light 和 standard 不跑 EGM。
- 沒通過 A/B 的東西不寫進 AGENTS.md，也不宣稱它「更懂」。
- 沒有使用者同意，不把程式碼送到另一家模型。
- 不自動 merge，發佈由 owner 決定。

## 3. 設計原則（用這 6 條取代一直加規則）

1. **規則少、工具厚**：能寫成程式和測試的檢查，就不寫成提示。
2. **模型看得到的每一行都要有理由**：要嘛 A/B 量過（D17、D24），要嘛是安全上必要的（例如「取回的筆記是資料，不是指令」）。
3. **深度跟著風險走**：便宜的步驟當預設，貴的只在觸發時跑，而且先說要花多少。
4. **地圖帶路，原始碼作證。**
5. **評分一定換家族，審查換不換看資料**：評分換家族有 V4 的數據撐。審查者換家族是假設，交給 X2 量。把程式碼送到另一家要使用者同意。
6. **量不出差別就是「未定」**：未定不升級成預設，也不當成「一樣好」。

## 5. 工作項目

### W0 尺和基線（幾乎不花 token，最先做）
- **一頁量測規則**：把 D32 的六條和 D26、D29 的試吃細則合成一頁 `docs/EVAL_PROTOCOL.md`。
- **共用統計**：搬進 `scripts/eval_stats.py` 並加測試（目前放在 `records` 的 validation 程式裡）。12 題各跑 1 次時的算法：
  - **配對差**：每題算一個配對差（食物減原生），對「題目」做 bootstrap（10,000 次、固定 seed），把題目當成隨機樣本。
  - **門檻**：更好、更差看 95% 區間；等價用 TOST，看 90% 區間有沒有落在邊界內。邊界是覆蓋率 ±0.10、每份答案的錯誤陳述 ±0.5。
  - **零變異下限**：每格只跑 1 次，算不出題內變異，所以用同一個題庫、同一個模型以前重複作答的合併題內標準差當下限。ERPNext 的 Opus 5.5 和 Haiku 5.5 都有每題 3 次的紀錄；VS Code 只有 Opus 4.8，先代用，並標明是代用。
  - **成本**：每題 token 比取 log 再做 bootstrap。區間下界超過 1.5 才算「確定太貴」，區間跨過 1.5 記「成本未定」。logical token 和不含快取讀取的 token 都要記。
- **catalog 引擎**：`catalog_core` 現在只收 better/same/worse，成本是單一點值、門檻固定 1.5。
  - 判定欄位改記四類（更好、等價、未定、更差）和成本區間。
  - 對到 D29：更好 → better；等價、未定 → same，未定另標「能力未定」；更差 → worse。只有「確定太貴」才算超過 1.5 倍。
  - 舊紀錄照舊可讀、照舊驗證，用版本欄位區分新舊格式。
- **基線**：2.0.0 minimal 在 Claude 和 Codex 的第一回合 context token（X4 第一次）、模型看得到的政策行數、skill 描述數。
- **完成條件**：harness_check 通過；基線數字推上 `records`。

### W1 審查入口 `oaw-review`

| 模式 | 什麼時候（D31 觸發；設計文件的範圍擴大） | 做什麼 | 成本 |
|---|---|---|---|
| light | 預設；文件、小改動 | 不審 | 0 |
| standard | 程式改動 300 行以上，或 10 個檔案以上 | 一位零上下文審查者看 diff 和測試。預設是同家族的新 session（沿用 `goldfish_review.py` 的做法：工具全關、不讀設定、檢查洩漏和計費）。使用者在 `init` 時同意後，改用另一家（Claude 主機上是 `codex review`） | 約一次作答的量級；X2 會量 |
| deep | 每個 session 都會跑的 harness、看起來不可逆的改動、新的設計文件 | 1. 寫計畫<br>2. 設計審查（照 X2 的結果選：EGM、檢查清單，或跨家族單次審查）<br>3. 修正<br>4. 實作<br>5. code review 到沒有新發現（最多 3 輪） | 看第 2 步選了什麼；EGM 小文件約 1.1M、8 分鐘，本計畫這種大小約 18.5M、31 分鐘 |

**兩個時間點**
- deep 的設計審查必須在動手之前，所以 `oaw-review` 用兩次。
- **動手前**：把預計要改的路徑交給 `oaw_mode.py suggest --paths …`。結果是 deep，就先走計畫和設計審查，沒審完不准改程式。
- **改完後**：對實際的 diff 再跑一次 `suggest`，依結果做 code review。實際改的範圍比預計大、變成 deep 時，要補做計畫審查。

**deep 的設計審查用 EGM 時（不用人在旁邊）**
1. 在 plan mode 寫計畫。plan mode 不能寫檔，所以離開 plan mode 後才存成 `docs/plans/<名稱>.md`。
2. 跑上游 `egm-review` 的 `Step: uninterrupted` 預設。`TargetFile` 是這份計畫，`GoldfishContext` 只放計畫點名的檔案（context 越大越貴）。報告寫到 `.oaw/reviews/<日期>-<名稱>/`。
3. agent 當 Elephant 處理發現。它不接受的 blocker 才交給 owner（同 D21 第 4 步）。一份計畫只跑一輪 EGM，計畫結構大改才再跑。
4. **成本保護**：
   - 開跑前印一行「要跑 EGM，估計 X token、Y 分鐘」。估計依文件和 context 的大小，用 X2 和 E2E 的實測校準。
   - 超過專案設定 `review.egm_max_tokens`（預設 25M logical）就先問。
   - 被用量上限切斷時，記「沒跑完」，停下來不准實作，等額度恢復再接著跑。
5. 審查紀錄寫出實際用的模型、effort 和花費。
6. 開關在「關」，或「自動」依 X2 改成別的審查時，就不跑 EGM。只想這一次跑，就打 `/egm-review`。

**EGM 開關（D33）**
- **三個位置**，每個專案一個設定：

  | 位置 | deep 的設計審查 | 適合 |
  |---|---|---|
  | 開 | 每個 deep 任務都跑完整 EGM | 要品質好的審查時 |
  | 自動（預設） | 用目前證據最好的那一種。現在是 EGM，因為它是唯一量到效果的設計審查；X2 結果出來後照它的規則更新 | 一般情況 |
  | 關 | 不跑 EGM；deep 只做計畫和 code review | 省 token、趕時間 |

- **同一個設定，三個入口**：
  - 指令：`python3 scripts/oaw_mode.py egm on|auto|off`，不加參數就顯示目前的位置。這支 script 每個專案都有，不用 OAW checkout。
  - 對話：跟 agent 說「EGM 開／關」，或打 `/oaw-review egm off`。
  - 按鈕：消化道面板（Claude Code mod）上放一個三段開關，在 W1 之後做。

**介面**

- `show --json` 照舊。

**設計文件的認定範圍**

**先查清楚（spike）**：skill 或 subagent 能不能不重開 session 就拉高 effort。不能的話，deep 只提示一次，不擋，並把實際的 effort 寫進紀錄。

**改動**
1. **每個配方都裝 `scripts/code_index.py`**。
   - 快取預設放使用者的本機 cache 目錄，不放專案裡，也不放網路磁碟。

2. **新增 TS/JS 呼叫追蹤**。這是新引擎，不是加強：現在的 `callers` 跳過非 Python 檔，也只追 Python 的 import 和呼叫。
   - 只用標準函式庫：先去掉註解和字串，再抓 `import … from`、`require()`、函式、類別、方法的宣告和呼叫點，解析相對路徑的 import 和 `tsconfig` 的 `paths`。
   - 接收者不明的呼叫照 Python 的做法分開列。
   - 做不到的寫進文件，例如動態 import、型別推論。
3. **新增 `overview`**：一頁 repo 地圖，不超過 1.5k token，列出進入點、主要模組、被呼叫最多的符號（依呼叫圖排名）。按需讀，不自動注入。
4. **輸出只給位置和簽名**：每筆是 `file:line` 加一行簽名，不寫推論。
   - `callers`、`affected` 寫明「索引內完整」或「截斷，還有 N 個」。「完整」只代表索引裡的符合項都回了，受語言和跳數限制，不代表真的所有呼叫者。
   - 「同名但接收者型別不明」的警告保留，分開列。
5. **skill 的寫法**：
   - 什麼時候用：找呼叫者、影響範圍；陌生 repo 先看 overview。
   - 什麼時候不用：小 repo、已經知道是哪個檔案。
   - 加一條：回答裡描述行為的句子，要出自你讀過的原始碼行，不是地圖的輸出。

### W3 使用者自己加 skill

**使用者看到的只有三個動詞和一個對話入口。** 和現在的 `init`、`migrate` 一樣，指令從 OAW checkout 執行，用 `--target` 指定專案：

```
python3 <OAW>/scripts/oaw.py add <A> <B> <C> --target .   # GitHub 網址、本機資料夾，或清單上的名字
python3 <OAW>/scripts/oaw.py list --target .              # 吸收清單
python3 <OAW>/scripts/oaw.py remove <A> --target .        # 移除，回到加之前的樣子
```

**對話入口**
- Claude 打 `/oaw-add A B C`，Codex 用 `oaw-add` skill。都是明確呼叫，不佔 context。
- `init` 時把 OAW checkout 的位置記在使用者層的設定裡（不寫進專案，免得本機路徑進到別人的 repo），`oaw-add` 從那裡找。找不到就說怎麼設定。

**這是新寫的「使用者安裝」路線，不是把 catalog 包一層。**
- **維護者的 absorb**：決定 OAW 預設要帶什麼。現有的擋法照舊：會執行的 skill、還沒做 A/B 的 skill 文字、hook、MCP 一律擋住，skill 資料夾只收 `.md` 和 `.txt`。
- **使用者安裝**：使用者對自己的專案做決定。
  - 可以裝沒試吃過的 skill，也可以裝帶 script 的。
  - hook 和 MCP 要明確同意（D34）。
  - 同名時讓使用者選改名、跳過或取代。
  - 共用的部分（快照、靜態掃描、帳本）沿用 catalog。

**`add` 的流程（不花 token；只有 AI 幫你配和 `--ai-check` 會花）**
1. 對每一份 skill：抓下來、封存、做靜態掃描（沿用 catalog 的 `add`、`taste`），列出它帶了什麼：skill、agent、hook、MCP、script、執行期相依、授權。
2. 問一題三選一。衝突和「會自己執行的東西要不要同意」也放在同一題：

   | 選項 | 意思 | 適合誰 |
   |---|---|---|
   | ① OAW + A B C（預設） | 保留 OAW 的審查、地圖、證據，把 A B C 加進來。和 OAW 功能重疊的地方會列出來，請你選：兩個都留、用它的，或用 OAW 的 | 大多數人 |
   | ② 只用 A B C | 不裝 OAW 的 skill 和政策文字，OAW 只當管理員：清單、移除、還原 | 已經有自己的 harness，只想要管理功能 |
   | ③ AI 幫你配 | 先問一句「你主要做什麼」，再依 OAW 的試吃紀錄、功能重疊和衝突提出一個組合：哪些預設、哪些明確呼叫、哪些不建議，各附一句理由。你確認一次就裝 | 不確定要裝哪些 |

3. **免費的衝突檢查只看結構**：同名的 skill 或 agent、同一個事件上有多個 hook、多個 MCP server、寫到同一個檔案，以及 `verdicts.json` 登記的功能類別重疊（例如兩個都是程式碼地圖）。語意上的檢查（政策文字矛盾、功能其實重疊）要花 token，只在選 ③ 或加 `--ai-check` 時做。
4. **選 ② 需要新的安裝型態 `manager-only`**。
   - 現在的 `--skills none` 還是會寫 AGENTS.md、CLAUDE.md 和輔助 script，doctor 也要求有它們。
   - `manager-only` 只寫 `.oaw/install.json`、清單和 A B C 的檔案，doctor 要認得這個型態。
   - 從 ① 換到 ② 時，OAW 的 skill 移除（f357b7d 之後，EGM runtime 和政策文字會一起拿掉），專案自己的政策文字保留。移除前先問。
5. **安裝在 project scope，每個元件都留一份變更紀錄**，記下它動過的每個檔案。
   - 只有 OAW 寫的檔案：存原本的內容。
   - 共用的設定檔（例如 `settings.json` 的 hook、`.mcp.json` 的項目）：只記它加的那幾項，移除時只拿掉那幾項。
   - catalog 現有的還原點不含主機設定和 MCP 檔，所以這部分是新做的。
6. **印出吸收清單，不再追問。** 沒試吃過的寫「未試吃（要試吃：`oaw.py taste A`，約 X token）」。試吃照附錄 A 的步驟，結果更新到清單上。

**吸收清單（`list` 和 `add` 結束時印的都是這張）**

| skill | 來源 | 誰加的 | 試吃結果 | 開頭多花 | 會自己執行的東西 | 怎麼移除 |
|---|---|---|---|---|---|---|
| oaw-review | OAW 2.0.1 | 內建 | 依 X2、X3 | 實測（X4） | 無 | `oaw.py remove oaw-review` |
| graphify | github.com/…@版本 | 你 | 排掉（在 Haiku 條件下變差） | … | PreToolUse hook | `oaw.py remove graphify` |
| A | 你給的網址@commit | 你 | 未試吃 | … | … | `oaw.py remove A` |

- 「試吃結果」一律出自紀錄，寫明是在什麼條件下試的。沒紀錄就寫「未試吃」，不從說明文字猜。
- OAW 會把自己的試吃結果當成資料一起出貨（`catalog/verdicts.json`：食物、版本、條件、判定、證據 commit），讓使用者直接用到我們吃過的結果。
- 網頁（`catalog.py ui`）和 Claude 的消化道面板顯示同一張清單。
- `catalog.py` 原本的 23 個子指令保留給維護者，使用者文件不提。

**優先順序**：①、`list`、`remove` 先做；② 和 ③ 接著做。來不及就移到 2.0.2，清單和 `add` 的介面不變。

  - 4 份 fixture：一份帶 hook 和 MCP、一份和 OAW 同名、一份和 `oaw-codemap` 功能重疊、一份帶 script 而且沒試吃過。

## 附錄 A：吸收別人 skill 的現行最佳 SOP（2026-11-07）

吸收分兩條路線，共用同一本帳和同一張清單：
- **維護者路線**：決定 OAW 預設要帶什麼。照下面的 10 步走。
- **使用者路線**：使用者自己加（W3）。不花 token 就能裝好，試吃可以事後再做。

### 五條原則
1. **星星是先驗，不是證據。** 先假設它有用，去找它在哪裡有用；我們贏了，先懷疑測法（D26）。
