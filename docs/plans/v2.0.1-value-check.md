## 1. 吸收的兩種目的（D38）

owner 的原話（2026-11-10）：「至今 skill 吸收 有兩種目的 1. 對整體 OWA harness or 使用者 repo 有所幫助 2. 整體使用者的repo 可以新增一些過往沒有得能力，我們整理後打造起來，譬如可以是影片剪輯，可以是遊戲製作的相關skills」

| | 目的一：幫助型 | 目的二：能力型 |
|---|---|---|
| 是什麼 | 讓原本就會做的事做得更好、更省（記憶、審查、程式碼地圖、省 token） | 讓 repo 多一種原本沒有的能力（影片剪輯、遊戲製作…） |
| 比較對象 | 原生（什麼都不裝） | 原生加上同樣的底層工具（例如同樣裝好 ffmpeg），看 skill 的指引有沒有多做到事 |
| 可能的結果 | 預設／可選用／排掉（D29） | 可選用／排掉。**能力型永遠不進預設**：沒用到的人不該為它多付 token |
| 到目前吃過的 | graphify、codegraph、court-skill、TokenEconomizer、EGM、claude-mem（未吃完） | 沒有 |

這改了 D4：D4 的相關性過濾原本會把「和 coding agent 無關的東西（例如影片工具）」不經審查直接丟掉。D38 之後，這類東西改走能力型軌道，不再丟掉。

## 3. 公正評審機制：有什麼、缺什麼

**已經有、而且在用的**
- 先登記再跑：組別、題目、判定規則、預算寫進 PREREG，推上 `records` 才開跑；題目凍結並記 sha256。
- 題目由不知道 OAW 實作的新 agent 出；不合格的題目直接丟，不修。
- 隔離：每次作答一個乾淨的家目錄，看不到紀錄、其他 repo、之前的對話；只用訂閱計費（`apiKeySource: none`）。
- 評分：能機械判定就機械判定（隱藏測試、重播）。不能的，由 Opus 和 Codex 兩家零上下文盲評，兩家都同意才算數。
- 統計：`scripts/eval_stats.py`（bootstrap 信賴區間、等效檢定、全部同分時的下限）；`scripts/judge_calibration.py` 量評分者準不準。
- 判定：`catalog.py record-tasting` 會擋下和數字不一致的判定；結果只有預設／可選用／排掉（D29）；排掉之前要測過它的主場（D32）。
- 被用量上限切斷或花 0 token 的那次算「沒跑」，不算 0 分（D30）。
- 獨立單位：Codex gpt-6.1-sol 做例行獨立審查和最後照凍結規則判定；兩家不一致時以 Codex 為準；卡住時升級到 gpt-6-astra 和 Fable 5.1。

**Codex 稽核（2026-11-08）查出的問題**
- 過去有一部分判定是自審自裁。確認的兩例：codegraph 過關的規則被「做競爭零件的人」推翻；V5 的 p=0.048 混進了探索性的資料。
- 最可能判錯的五項：EGM 當 deep 預設（X2 已重做）、codegraph 對 OAW 地圖、TokenEconomizer、graphify、記憶檢查。
- 稽核提的六條規則：設計者不能是競爭零件的作者；題目由另一位盲出；runner 凍結；優先用可執行的檢查；判定由獨立單位套用，**OAW 自己也要過同一關**；報告要分清「政策排除／量到有害／沒有結論／沒測」。

**還缺的**
1. **OAW 自己沒過同一關。** 外部食物都要和原生比，OAW 整包沒比過。→ H1。
2. **沒有可重複使用的工具組（W5）。** X1、X2、I16 各寫各的 runner；X1 光出題就花 22M。→ H1 的 runner 做成工具組。
3. **審查不停手。** 規則寫最多 3 輪，2.0.1 實際審了 18 輪。→ H1 的登記審查硬性最多 3 輪。
4. **能力型沒有尺。** → 第 4 節。

## 4. 吸收 SOP（整合版）

共用的五條原則不變（`docs/SKILL_INTAKE.md` 一頁版）：星星是先驗、沒吃過不下判定、同一把尺、先便宜後昂貴、owner 只在入口和發佈出現。

| 步 | 幫助型 | 能力型（新） |
|---|---|---|
| 1 入口 | owner 貼網址或在 scout 清單勾選 | 同左。scout 不再丟掉非 coding 類，另列一張能力型清單 |
| 2 快篩（0 token） | 讀它的主張、主場、成本；最多挑 3 個單位 | 同左，另外寫下它需要的底層工具（ffmpeg、遊戲引擎…）和授權 |
| 3 封存、靜態掃描 | `catalog.py add`、`taste` | 同左。會裝 hook、MCP、可執行檔的照 D34 標出 |
| 4 登記 | 12 題 × 1 次，盲出題 | 6–12 個成品任務，盲出題；每題有機械檢查 |
| 5 組別 | 原生、食物；skill 類加「只放 description」；另加一組便宜做法 | 原生加同樣底層工具、食物；另加「只放 description」 |
| 6 條件 | 它的主場 + 我們的用途 | 它的主場就是唯一用途；另加「閒置」條件（裝著不用） |
| 7–8 跑 | 同模型、同 effort、同提示；記兩種 token | 同左 |
| 9 評分 | 機械優先，否則兩家盲評 | **只用機械檢查成品**：檔案存在、長度、解析度、音軌、剪接點（ffprobe）；遊戲能建置、無頭跑 N 幀、通過腳本化的操作測試。看畫面好不好這種主觀題不當判定依據 |
| 10 判定 | 預設／可選用／排掉 | **可選用**：成品任務通過數比原生多，而且閒置時開場 token 不增加超過 2%、一般任務不變差。否則**排掉**。不進預設 |

能力型的判定門檻（上表第 10 步）是 agent 的草案，照 D38 的方向寫的；owner 可以改。在 owner 勾選第一批候選之前不會跑任何能力型試吃。

## 6. 執行計畫

### H1：裝 OAW 對 不裝（這輪的主體）

**問題**：同樣的工作，裝了 OAW 2.0.1 預設配方，比什麼都不裝是更好、一樣、還是更差？多花多少 token？

- **組別**：N 原生（乾淨專案）；O（`oaw.py init` 預設安裝）；L 便宜對照（原生加兩行政策：「重要決定記在 NOTES.md、開工先讀」「大改動前先請全新 context 審一次」）。L 用來分辨好處是來自 OAW 的機制，還是任何兩行提醒都做得到。
- **兩格**：Claude Code + Opus 5.5（effort high）；Codex CLI + gpt-6.1-sol（reasoning high）。
- **語料**：`pallets/flask` @ `49943b5a`（不是我們的 repo；TokenEconomizer 試吃用過同一份）。
- **12 題，三類各 4 題**：
  - **A 一般小改動**：沿用已驗證的 Flask 題（原生已知全對），只看有沒有變差、多花多少。
  - **B 跨 session 記憶**：第一個 session 在對話裡講了程式碼裡查不到的決定，之後的全新 session 要用到。含「明講要記」「順口一提」「決定後來改了」「交接到一半」四種。
  - **C 有風險的改動**：會觸發 OAW standard／deep 流程的改動，規格裡有容易漏掉的要求。
- **評分**：全部機械判定。最後一個 session 結束後，測試資料夾回到原樣、放入隱藏測試、跑整套測試；隱藏測試全過而且既有測試沒有新失敗才算對。評分程式看不到組別。
- **出題**：B、C 由零上下文的 Codex 盲出（只知道要測哪一類能力，不知道 OAW 的做法和組別）；每題附參考改動，機械驗證（base 上隱藏測試要失敗、套上參考改動要通過）。不合格的直接丟。
- **判定（先寫死，細節在 PREREG）**：每格、每類各自判「更好／一樣／更差」，再合成四種結論之一：
  - **有幫助**：至少一類更好，沒有任何一類更差。
  - **更慘**：有一類更差。
  - **雞肋**：三類都一樣，而且 token 確定比較多。
  - **沒差**：三類都一樣，token 也沒有確定比較多。
- **誰做什麼**：Claude 寫登記和 runner、操作凍結後的 runner；Codex 審登記（最多 3 輪）、盲出題、最後照凍結規則判定。
- **預算**：Claude 上限 30M（D35），預估 18M 左右；到 27M 自動停。Codex 走 ChatGPT 方案，不算在上限。
- **紀錄**：`records/v2.0.1-experiments/H1/`。
- **已知限制（先講）**：每類只有 4 題、每題只跑 1 次，只能看出大的差別；A 類原生本來就全對，只能量「有沒有變差」；只測 Python 的中型 repo；沒測長期使用。差一題的結果會寫「沒有結論」，並列出要多少預算才能確認。

### H1 的結果會怎麼用（先講好）

- **更慘或雞肋**（任何一格）：列出是哪一類造成的，提案把對應的零件移出預設。發佈時由 agent 決定（D40）；兩格方向相反、退步追不到單一零件、或某格沒有結論時，交給 owner 開 Fable 5.2 決定。

- **沒差**：照實寫「沒有量到好處，也沒有量到壞處」，預設維持現狀，列出要更難的題目才分得出來。
