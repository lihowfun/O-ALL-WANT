# codegraph 試吃（ERPNext，agent 層）結果

依 `PREREG.md`（dde0cd8）、`ADDENDUM-NB.md`（cca583d、7ee10bd）、`ADDENDUM-WEAKER.md`（11408a7），三份都在對應的作答之前推上 records。2026-11-06，Linux，Claude Code 2.1.287，訂閱計費（每次的 `apiKeySource` 都是 none，init 回報的模型都和指定的一致）。

## 結論
- **品質：和原生一樣。** 4 個模型條件下，codegraph 的覆蓋率和原生差 −0.036 到 +0.011，沒有一個條件「更懂」。
- **工具呼叫：四組裡最少。** 是原生的 30% 到 56%。
- **token：比原生多。** 是原生的 120% 到 172%，不是它宣稱的少 62%。
- **照事先寫死的規則**：
  - Opus 5.5 判「一樣懂但比較省（工具呼叫）」，其他 3 個條件「沒有證明比原生好」，沒有任何條件「變差」。
  - 合併規則下，codegraph 字面上算「有提升」，但省的只有工具呼叫。
- **帳本判定：不收。**
  - OAW 自己的 `code_index.py` 在同一批題目、同一批評分上，品質差不多（弱模型上 codegraph 的覆蓋率高 0.03 到 0.05，在雜訊範圍內）。
  - 工具呼叫：OAW 有 3 個條件比原生少（codegraph 更少）。
  - token：4 個條件 OAW 都比 codegraph 少。
  - 接上 codegraph 要多裝 Node 執行環境、MCP server 和 hook，沒有量到比 OAW 已有的工具更好。
- **這次也查出 SOP 本身的問題。** 同一批答案重新評分，OAW code map 和 graphify 在 Opus 4.8 的判定都翻轉了，代表「變差」和「省」的分界落在 AI 評分的雜訊裡。見 `../SOP_AUDIT.md`。

## codegraph 本身有沒有真的跑
- **有裝、有作用。** 官方 project 安裝（`.mcp.json`、`.claude/settings.json` 的 hook 和權限、`.claude/CLAUDE.md` 段落）。每次 init 都顯示 codegraph 的 MCP server `connected`，工具清單有 `mcp__codegraph__codegraph_explore`。
- **它的 prompt hook 每次都把內容塞進開頭。** codegraph 組第一回合的 context 中位數約 13.2k token，原生約 5.2k；多出的約 8k 是 hook 注入的 `codegraph_explore` 結果，加上它的說明。
- **但 agent 從來沒有自己呼叫 codegraph。** 所有條件的 C 作答，呼叫 MCP 工具或 `codegraph` CLI 都是 0 次。agent 拿到 hook 給的位置之後，改用 Bash 的 `sed -n`、`grep` 直接讀那幾行來核對。codegraph 的說明寫「相信結果，不要再用 grep 核對」，這次的模型沒有照做。

## 判定（照事先寫死的規則）
- **Opus 5.5：一樣懂但比較省（工具呼叫）。**
  - 對 N：覆蓋率 +0.011，4 題都不低於 N；錯誤陳述 1 對 2；工具呼叫中位數是 N 的 50%，4 題都比 N 少。
  - token 中位數是 N 的 120%，所以省的只有工具呼叫，token 反而比較多。
  - 依 `ADDENDUM-NB.md`，正式判定取「對 N」和「對 NB」比較差的一個。對 NB 也是工具呼叫 52%、token 91%，結果相同。
- **Sonnet 5.5：沒有證明比原生好。** 錯誤陳述 6 個，N 是 4 個，沒過「錯誤陳述不比 N 多」；token 中位數是 N 的 131%。
- **Opus 4.8：沒有證明比原生好。** 覆蓋率 +0.011，4 題都不低於 N；工具呼叫 43%。但錯誤陳述 11 對 9，沒過「不比 N 多」；token 是 N 的 172%。
- **Haiku 5.5（只有 1 次）：沒有證明比原生好。** 覆蓋率 −0.036，工具呼叫 30%，token 148%，錯誤陳述 2 對 1。

**合併（4 個條件，和 graphify、OAW code map 同一把尺）**：codegraph 在 Opus 5.5「一樣懂但比較省（工具呼叫）」，其他 3 個條件「沒有證明比原生好」，沒有「變差」，所以字面上**算有提升**。同一批評分下的另外兩組：
- OAW code map：Opus 5.5「比較省（工具呼叫）」，其他 3 個「沒有證明」，字面上也算有提升。昨天它在 Opus 4.8 判「變差」，是另一批評分的結果，見「偏差」。
- graphify：Opus 4.8「變差」（覆蓋率 −0.103），**沒有提升**。

帳本判定是**不收**，理由見「結論」：codegraph 對原生的好處，OAW 已經有的工具同樣做得到。

## NB 對照：工具呼叫少，是不是因為有 Bash？
- 看資料時發現食物組有 Bash，原生組沒有。Claude Code 會自動放行唯讀的 shell 指令，食物組可以用一次 Bash 串好幾個讀檔。Opus 條件裡，C 的 Bash 50 次全是一般讀檔；S 有 32 次、G 有 21 次是一般讀檔。
- 所以追加 NB：原生加上同樣的唯讀 Bash。
- 結果：NB 的工具呼叫中位數 9.25，N 是 9.67，**幾乎沒有少**；8 次裡只用了 7 次 Bash，token 反而比 N 多 32%。
- 結論：**光有 Bash 不會讓原生少走幾步。** C 少掉一半工具呼叫，是因為 hook 先告訴它該看哪幾個檔案的哪幾行；S 也是因為地圖先給了位置。這個疑慮已經用資料排除，C 和 S 的「比較省（工具呼叫）」可以算在食物頭上。
- `judge()` 判 C、S、G「對 NB 更懂」是假象，**不採用**。原因：NB 只跑了 8 次，而「必要事實全對」比的是次數，12 次對 8 次自然多 4 次。換成比例，雙方都是 100%。這不影響 C 的正式判定：取兩者中比較差的，仍是「一樣懂但比較省」。

## 和 graphify、OAW code map 比（描述，不做判定）
- **比 graphify 好一點。**
  - Opus：覆蓋率 0.934 對 0.912；token 中位數 85k 對 91k；工具呼叫 4.8 對 8.5。
  - Sonnet：graphify 覆蓋率稍高（0.909 對 0.876），codegraph 的錯誤陳述多 1 個，token 多 7%。
  - 兩者都比原生花更多 token。
- **和 OAW 自己的 `code_index.py` 差不多。**
  - Opus：品質相同，token 85k 對 83k，工具呼叫 4.8 對 6.3。
  - Sonnet：OAW 的比較省（token 49k 對 71k），錯誤陳述一樣是 6 個。
  - codegraph 要裝 Node 執行環境、MCP server 和 hook；`code_index.py` 只用 Python 標準函式庫。
- **它宣稱的「token 少 62%」沒有重現。** 這裡的 token 是原生的 120% 到 131%。原因看得到：hook 每次在開頭塞約 8k token 的程式碼，之後每一回合都會再讀到這段 context；agent 又沒有照它的說明直接相信結果，還是用 grep 和 sed 再核對。它的 benchmark 用 Opus 4.8，題目是「X 怎麼運作」的單題架構題，量法也不同，不能並排比。

## 偏差
- **評分途中撞到訂閱的 5 小時上限。** Opus 有 18 筆、Sonnet 有 5 筆、Haiku 有 7 筆評分沒有真的跑（評分者回傳 0 token，結果記成 unparsed、覆蓋率 0）。
  - 這些不是評分結果。原樣留在各條件的 `grades-not-run-ratelimit.jsonl`，不計分。
  - 等上限恢復後，用同一個評分者和提示補評，評分程式沒有改。
  - 補評前的摘要，因為這些假的 0 分，曾經顯示 Opus 原生覆蓋率 0.695，那份摘要作廢。
- **同一批答案評兩次的差異。** N、G、S 的 36 個答案，昨天（d389fe9）和今天各評一次：覆蓋率 36/36 完全一樣、必要事實沒有任何翻轉，但錯誤陳述有差。
  - Opus：N 4→2、G 3→2、S 1→1。
  - Sonnet：N 4→4、G 4→5、S 5→6。
  - 錯誤陳述這一項，AI 評分本身會有 0 到 2 個的出入；「變差」的門檻是多 3 個，離雜訊不遠。
- **NB 放在自己的輸出資料夾、只跑 2 次。** runner 的預算守門會把同一資料夾裡沒有標 `seeded` 的列（C 的 12 次）都算進預算，所以 NB 改放 `out-nb-opus/`；跑完 2 次後，第 3 次的第 1 題估計會超過 1.2M 上限，照登記停下。
- **C 的副本放在本機 SSD**（PREREG 已寫明）。秒數不列入判定。
- **一次 Opus 4.8 作答失敗**：撞到上限時 runner 停下、沒有記錄；上限恢復後從同一題重跑。
- **使用者家目錄的殘留**：codegraph 在家目錄建了一個空的 `~/.codegraph/daemons/`，試吃結束後移除。使用者層的 Claude 設定和外掛沒有被改動（安裝程式在另一個 HOME 下執行，事後核對過）。
- **同一批答案重新評分，判定翻轉。** Opus 4.8 的 N、G、S 答案，fd1895c 那批和今天這批各評一次：
  - OAW code map 的錯誤陳述比 N 多 3 個（判「變差」）變成多 2 個（判「沒有證明比原生好」）。
  - graphify 的覆蓋率差距從 −0.091 變成 −0.103（從「沒有證明」變成「變差」）。
  - 覆蓋率差距在 0.10 門檻附近、錯誤陳述在 +3 門檻附近的判定，會隨評分批次改變。本頁一律用同一條件、同一批評分的數字。
