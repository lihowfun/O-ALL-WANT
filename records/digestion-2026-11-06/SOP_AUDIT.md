# 消化 SOP 公正性檢查（2026-11-06）

owner 問：「效率消化 SOP 已經公正建立了嗎？」以及「也要試試看好用的功能在這套消化系統能否被吸收……如果都被排泄，那要謹慎思考可行性」。

## 結論
**還沒有完全公正，但可行：現行 SOP 不是只會排泄。** 把 EGM 從 OAW V2 拿掉、當成食物重新試吃，現行 SOP 判它「更好 → 吸收」；故意做成有用的正對照也判「更好」。所以題目有空間的時候，好東西量得出來。

不公正的地方是**判定規則**，而且兩個方向都有：
- **便宜的小進步會被排掉。** 只看得出「省 30% 以上」或「覆蓋率高 0.10」；題目常常碰到天花板；「量不出來」被記成「不收」。graphify、TokenEconomizer、codegraph 都是在這種情況下判定的。
- **很貴的小進步會被吸收。** EGM 的進步只來自一個案例的一類缺陷（原生其實看到了，只是寫成「不確定事項」），每次審查卻花原生 28 倍的 token。現行規則只要「更好」就吸收，不看成本。
- **分界落在評分雜訊裡。** 同一批答案評兩次，就有兩個判定翻轉。

所以要改的是判定規則（見最後「建議」第 1 條，要你決定），量測流程本身（實際安裝、先登記、盲評）可以沿用。

## 已經做到、而且有東西在擋的
- **食物本身沒裝起來跑過，就沒有判定。** `record-tasting` 拒收食物組沒有評分過的執行的判定（D28）；court-skill 那次的錯誤之後加上。
- **先登記再跑**：每次試吃的題目、組別、判定規則都在任何計分的作答之前 commit 到 records，附 sha256。
- **盲評**：評分者零上下文、看不到組別，會洩漏組別的工具名稱先遮掉，順序打亂。
- **官方安裝**：食物照它自己的說明安裝（能選 project scope 就用），使用者層的設定事後核對或還原。
- **只用訂閱計費**，每次 init 檢查 `apiKeySource: none`。
- **機械限制不再擋食物**：50 MB 封存上限改成跳過並標旗（2026-11-06，27a5312）。
- **你問得到**：`catalog.py why`（2026-11-06，13dcbb1）。
- **疑慮用對照組驗證，不用猜**：懷疑「食物組有 Bash、原生沒有」造成不公平，就加跑 NB（原生＋同樣的 Bash），量出來不是這個原因（2026-11-06）。

## 還沒做到的：偏向把東西排掉
1. **只量得出很大的差距。** 同一組在同一題重複跑，token 就會差：Opus 5.5 每題 8%～18%，Sonnet 5.5 13%～24%（確認實驗的原始資料）。原生組自己跟自己比，中位數比值的 95% 範圍是 0.81～1.26（Opus）、0.74～1.35（Sonnet）。所以「比較省」的門檻定在 70%，省 10%～20% 的好處看不出來。
2. **天花板。** Opus 5.5 原生組在 ERPNext 題目 12/12 全對；court-skill 原生 4/4；TokenEconomizer 原生隱藏測試 12/12。「答得更好」沒有空間，只剩「省很多」這條路。
3. **試吃規則比 D21 嚴。** D21 說 B 級（模型會讀的文字）「齊平以上才吸收」。試吃規則要「更好」或「省 30% 以上」才收，齊平一律記成「沒證明比原生好（不收）」。兩邊沒對齊。
4. **「量不出來」被記成「不收」。** `not-shown-better` 在帳本上和 `decline` 一樣是「沒有待辦」，等於排掉。
5. **測的時間太短。** TokenEconomizer 的機制要累積幾個 session 才生效：後 4 題它每題都比原生省（合計 13.9%），但整條只有 12 個 session，不夠判斷。
6. **AI 評 AI。** code map 和 court-skill 用 Opus 評 Opus 的答案；只有 TokenEconomizer 用隱藏測試（第三方事實）。
7. **判定的分界落在 AI 評分的雜訊裡。** 同一批 Opus 4.8 答案評兩次，覆蓋率完全一樣，但錯誤陳述差 0 到 2 個，OAW code map 從「變差」翻成「沒證明」、graphify 從「沒證明」翻成「變差」。門檻（錯誤陳述 +3、覆蓋率 −0.10）離雜訊太近。
8. **評分者撞到用量上限時，會記成假的 0 分。** 今天 30 次評分沒有真的跑（評分者 0 token），原本的程式把它當成「答案全錯」。已補評、不計分；EGM 自測的評分程式已經改成「0 token 就是沒跑，不記分」。
9. **組別次數不同時，「必要事實全對」用次數比會出錯。** NB 對照只跑 8 次，規則用次數比，就把其他組判成「更懂」；應該用比例。
10. **每次都手工搭一套試吃工具。** 這次 codegraph 沿用 ERPNext 的題目和原生組，只新跑食物組，花費約三分之一；還沒變成通用的程式。

## 自測：EGM 拿掉，當食物照現行 SOP 跑
詳見 `egm-selftest/RESULT.md`（065f068 登記，7fec5e8 結果）。3 個凍結的設計審查案例 × 2 次（預算只夠 2 次）：

| 組 | 埋的缺陷抓到 | 沒有根據的指控 | 每次 token 中位數 |
|---|---|---|---|
| 原生（V2 拿掉 EGM） | 12/16 | 0 | 40,709 |
| EGM 官方 plugin（每次 6–10 個子 agent） | 16/16 | 0 | 1,137,230（28 倍） |
| 正對照（點名缺陷類別的清單） | 16/16 | 1 | 40,578 |

- 原生沒有碰到天花板（12/16），所以「更好」量得出來。EGM 和正對照都判「更好」。
- 差的 4 個全在 events 案的兩個主要缺陷：「Flux shim 沒有定義」和「計畫沒有可執行的範圍和完成條件」。原生兩次都有提到，但寫在「不確定事項」，凍結規則不算偵測。
- 兩種讀法：現行試吃規則兩者都「吸收」；D21「齊平以上」下，EGM 可以出貨，正對照因為多 1 個沒有根據的指控不能出貨。
- 自測順便發現 OAW 的 bug：照 D6 移除 EGM，`.oaw/integrations/egm` 的 66 個檔案還在，`AGENTS.md` 也還寫著包含 EGM。

## 建議（要你決定的只有第 1 條，其餘我直接做）
1. **判定改成三種結果，加上誤差帶和成本**（要你決定，會記成 D29）：差距要超過「同一批答案評兩次的差」才算「更好」或「變差」。
   - **進預設**：更好，而且 token 不超過原生的 1.5 倍。
   - **可選用**：齊平，或者更好但很貴（超過 1.5 倍）。裝進 OAW 但不設為預設，要用時才叫。EGM 在 V2 本來就是「明確叫用」，正好落在這一格。
   - **排掉**：變差。
   - 這和 D21 的「齊平以上」對齊，也不會再把「量不出來」記成「不收」。
2. 凍結題目前先讓原生試跑；原生已經滿分的題組，照事先寫好的規則換難一點的題。
3. 記憶、省 token 這類長效型食物，測 30 個 session 以上的串流。
4. 能用程式評分（隱藏測試、可執行的檢查）就不用 AI 評；必須用 AI 評時，同一批答案評兩次，只採兩次一致的部分。
5. 把試吃工具做成共用的：沿用凍結題組和原生組只跑食物組（codegraph 這次花費約三分之一）；runner 和評分程式內建「0 token 就是沒跑」、次數不同時用比例。
6. 修 D6 的 EGM 移除：移除後連執行檔和 `AGENTS.md` 的說明一起拿掉（另開一個任務）。
