## 一句話：它們各是什麼

**EGM：一套「人在裡面」的設計流程。** 大象帶著專案脈絡和你一起把設計寫成文件；金魚不帶先前的對話去讀這份文件；取捨由你決定。
它要的產物是一份設計文件，標準是：沒看過這個專案的工程師（或全新的 AI）照著做，第一次就做對，而且**不必再做任何設計決定**
（`resources/document_standards/implementation-readiness-standard.md` 的 Zero-Decision Rule）。

**Harness²：針對眼前這一題，用執行紀錄來改 harness 的迴圈。** 不看答案、不看分數。同一題先照原樣跑 → 兩個編輯者各提一份改法
（一個管「怎麼做事」，一個管「這一行的人該知道什麼」）→ 每份改法真的跑同一題 → 只留下執行紀錄撐得住的改動，可以一個都不改
→ 蓋住來源，挑最好的產出交出去 → 逐項記下每個改動「有幫助／有害／看不出效果／混在一起分不清」→ 下一題先讀這本帳。
每題的花費固定是 4k 次作答加 3k 次改進（k=1 時是 4 次作答、3 次改進）。

## EGM：我們用到哪裡

| | 上游的用法 | OAW 現在的用法 |
|---|---|---|
| 步驟 | `/egm-brainstorm` → `/egm-draft` → `/egm-review` → `/egm-resolve`，再給人審，然後才實作 | 只有 `egm-review`。其餘六個 skill 裝了，但沒有任何流程會帶到 |
| 開頭 | 多輪問答把問題問清楚，包含「怎樣算成功」；使用者說可以了才叫金魚 | 沒有。AI 自己寫計畫 |
| 做決定的人 | 有不只一種合理做法時，列最多三個選項（機制、取捨、什麼情況會失敗），**不排序、不標預設、不替作者選** | AI 自己決定 |
| 審查的預設 | 互動式：五個階段，每一階段停下來讓人決定 | 指定成「一次跑完不中斷」 |
| 處理審查發現 | 四種：反駁（要附審查者讀得到的證據）、上報給人、提修正、不修；人逐項同意 | AI 自己處理，只把「它不接受的阻擋項」交給人 |
| 停止條件 | 連續兩輪沒有新的阻擋或重大問題才算收斂；上限 5 輪；之後還要人審 | 一輪 |
| 審的東西 | 設計文件（給之後實作的人看） | AI 的計畫；實驗裡是埋了缺陷的短文件 |

上游自己講的限制，我們之前沒有當一回事：

- 「Completing the EGM workflow alone does not demonstrate a productivity improvement.」要比的是自己題目上的**總時間、有用的發現、重工**（`docs/faq.md`）。
- 小而清楚的修改不必走設計流程；審查「會給很多回饋，挑有關的用，其餘忽略」（`docs/getting_started.md`）。
- 審查是回饋的來源，不是計畫正確的證明。
- 上游 repo 裡**沒有任何量到的效益**（品質、缺陷、成本都沒有）；它自己的 19 份設計文件也沒有一份留下完整的「三步加修正」紀錄（Codex 的盤點）。

所以我們的 X2（短文件裡找埋好的缺陷，原生 47／48、EGM 沒有多抓、token 27–29 倍）量的是上游沒有宣稱的東西，而且用在上游說「可能不划算」的小文件上。
這個數字只對「單次審查當抓錯工具」成立。整套流程有沒有用，我們和上游都沒有量過。

## Harness²：我們用到哪裡

拿了的：評估帳本（它用來記每一次作答與花費的那一層），和幾條量測原則。測過不採用的：一張「最小改動」參考卡。

沒拿的，是它真正的內容。下面每一條都寫在 `harness2/core/prompts.py`，是它給編輯者的規定：

1. **常駐文字是最貴的形式。** 每個字每一輪都在 context 裡。新增指示的優先順序：skill（有明確觸發時機）→ 腳本 → 子 agent → hook → 最後才是常駐文字；加一句常駐文字就要刪一句來付。
2. **每個 skill 都要在常駐文字裡有一行觸發條件。**「An unnamed skill is never opened anyway」；沒被點名的 skill 是白裝。
3. **模型會跳過的事，只有 hook 管得住。**「Prose can be stopped reading; a hook cannot.」
4. **每個改動都要指得出是哪一次執行的哪個時刻。** 指不出來就是猜測。同一題多跑幾次，各次**不一樣的地方**才是訊號；只出現一次的毛病是雜訊。
5. **不改是正當的答案**（KEEP_BASE）。沒有證據的改動只是多佔 context。
6. **挑選時蓋住來源**，原樣的版本也混在裡面；編輯者從頭到尾看不到評分標準。
7. **被選中不等於那個改動有用。** 事後逐項記結論；一次改了好幾樣、或只有一次執行可看時，要記「分不清」，不准硬歸因。

論文的驗證方式（[paper-notes.md](paper-notes.md)）：三個題庫；每個數字是 3 次執行的平均與標準差，每次題目順序重排；拿掉 library／分工／組合各測一次；
把 skill、腳本、提示分別拿掉看掉幾分（skill 掉最多，平均 5.3 分）；跨題庫、跨模型、跨執行器轉移；成本把改進的花費算進去；列出 9 個變差的案例。
它自己也寫了限制：增益在較弱的模型上最大（GLM-5 最多 +11.5），強模型較小（Opus 5 是 +3.0 到 +5.5）；執行有隨機性；被採用不代表最佳。
實際執行要 API 計費，執行器只有 OpenCode 和 Codex。

## 檢討：我們的工都做在哪一層

把一個「別人的方法」分成四層來看：

| 層 | 內容 | EGM | Harness² |
|---|---|---|---|
| 1 檔案 | 裝進來、固定版本、雜湊、授權 | 做得很完整 | 不適用（沒有內附） |
| 2 單一機制 | 其中一個零件 | 拿了審查 | 拿了帳本 |
| 3 流程 | 零件怎麼串、人在哪裡做決定、證據怎麼流 | 沒拿 | 沒拿 |
| 4 判準 | 怎樣才算成功、什麼時候不該改 | 沒拿 | 拿了幾條量測原則；設計 harness 的七條沒拿 |

再看我們自己寫的東西（`main` fa4ae2a，`wc -c`）：

- 模型真的會讀到的文字：約 **16 KB**（常駐規則 1.4 KB，加上七個 `oaw-*` skill 的說明 14.8 KB）。
- 圍在外面的：程式 1,307 KB、測試 1,020 KB、文件 758 KB，合計約 **3,085 KB**。
- 程式依用途分：吃別人的 skill 44%、程式碼地圖 18%、安裝與檢查 13%、量測 11%、wiki 7%、審查模式 4%、**記憶 3%**。

唯一量到明顯差別的地方（記憶）佔程式的 3%；佔最多的那一塊（吃別人的 skill）到現在沒有一樣進預設，1 樣（darwin-skill）是可選用。

做事的順序也反了。EGM 的順序是：問清楚問題與「怎樣算成功」→ 列出做法讓人選 → 寫設計 → 審 → 人同意 → 才動工。
我們的順序是：先做出來 → 再量 → 量到沒有好處。例子：程式碼地圖（做完才量到 Opus 不用）、H1 之後的五個修正（三個還原）、
今天的入口選單（owner 一句話，幾分鐘內就交給 Codex 實作，沒有問清楚要解決誰的什麼問題，也沒有列第二種做法）。

## 之後怎麼改（提案，等 owner 決定；現在不動工）

**做事的規矩，四條：**

1. **動工前先走三步，而且照 EGM 本來的用法。** 先和 owner 把問題與「怎樣算成功」問清楚（一次只問一題）→ 寫出兩三種做法給 owner 選，lead 不替 owner 選
   → 金魚審 → owner 同意才動工。小修不用走。
2. **每個改動都要指得出是哪一次執行的哪個時刻讓我們想改**；指不出來就不改。改完記一行結論：有幫助／有害／看不出／分不清。
3. **改 OAW 自己時，先選最便宜的形式**：能做成 skill 就不寫常駐文字；每個 skill 在常駐規則裡要有一行觸發條件；模型會跳過的事用 hook。

4. **試吃要在它的主場。** owner（2026-11-17）：「skills 的吸收方向要正確，你不能打網球的高手你拿去打籃球，然後還說籃球效果沒有特別好」。
   流程文件早就寫了「主場題」，但主場是我們自己認定的，沒有對照它自己的說法。之後每樣東西試吃前，先照它自己的文件寫下三件事：
   它是用來做什麼的、什麼情況下用、它自己說怎樣算成功；題目要從這三件事出。不在主場量到的結果，只能寫「沒有照它的用途測過」，不能寫「沒有好處」。

   照這一條回頭看（哪些要重查，還沒有逐一查證）：

   | 東西 | 它的主場（照它自己的文件） | 我們實際量的 | 在主場嗎 |
   |---|---|---|---|
   | EGM | 有後果的設計：三步寫出一份「全新的實作者照著做、不必再做決定」的設計文件 | 短文件裡找埋好的缺陷（X2）；另一個 session 拿來檢查一道題的答案 | 不在 |
   | darwin-skill | 用對照實跑、盲評的迴圈去改一個 skill | 4 題情境問答（結果頁自己也寫了「完整改進流程沒有測」） | 只有一部分 |
   | 程式碼地圖（我們自己的） | 還沒有寫下來「哪種題目該用它」（#28 的後半） | 12 題一般題（X1） | 沒有定義過 |
   | codegraph、court-skill、graphify、TokenEconomizer、最小改動卡 | 要回頭對照各自的文件 | 各自的試吃紀錄 | 待查 |

**呈現的規矩，一條：** README、簡報、進度頁都照上面那張表：一句話、角色各一句、一張圖、一個一分鐘能試的入口、一張選用表、限制寫在旁邊、不放內部代號。

**建議的第一個題目：記憶。** 它是唯一量到明顯差別的地方，而且我們自己的整包輸給兩行規則。
用上面的三步走一次，同時記下總時間、有用的發現、重工，這也會是我們第一次照 EGM 本來的用法量它。

## 限制

- 兩個 repo 的程式沒有執行；Harness² 的迴圈沒有實跑。
- 論文附錄 B–G 只讀到摘要。
- 「用它的規定回頭看我們的數字」那張表是對照，不是因果；每一條都要另外測。
- 進度頁上同一天另有一組「圖形推理題」的試吃（另一個 session 做的）：EGM 審查 3 次都沒有改答案。照這次讀到的，EGM 的審查對象是設計文件，
  標準是「全新的實作者能不能照著做」；拿來檢查一道題的答案，也不在上游設計的用法裡。
