我建議**不要直接把 60 個 skill 全部丟進優化流程**。這樣成本很高，效果也不一定好。我會分三階段處理：

## 第 0 步：先盤點（成本低，不改任何東西）

我先試著看了一下你的環境：
- 專案目錄 `/home/dev/proj/.claude/skills/` 只有 `darwin-skill` 一個。
- 其餘的應該在 `~/.claude/skills/` 或 plugin 底下，但我目前**沒有讀取 `~/.claude` 的權限**，要請你授權。

盤點會列出每個 skill 的：名稱、description、檔案長度、來源（你自己寫的，還是第三方 plugin 裝的）。第三方 skill 直接改的話，一更新就會被覆蓋。這類我建議跳過，或先 fork 一份成自己的版本再改。

## 第 1 步：60 個全部做靜態快篩（便宜、收益最大）

這一步不實際執行 skill，只讀內容。60 個 skill 最常見的問題通常不在內文，而是在這幾點：
- **description 重疊**：好幾個 skill 搶同一類請求，模型不知道該用哪個。
- **description 太模糊或太窄**：該觸發時不觸發，或觸發太頻繁。
- **context 負擔**：每個 skill 的 description 每次對話都會載入，60 個加起來不小。
- **可合併或刪除的**：重複的、過時的、根本沒在用的。

產出是一份分級清單：可刪除/合併、只要改 description、需要深度優化、維持現狀。

## 第 2 步：只對重點 skill 用 `darwin-skill` 深度優化

`darwin-skill` 的做法是讓每個 skill 跟沒裝 skill 的裸模型對照實際跑一遍，再盲評結果，只保留確實有幫助的修改。這套流程很嚴謹，但每個 skill 都要跑好幾輪，所以我會：
- 挑**最常用、而且第 1 步發現有問題的 5～10 個**優先跑。
- 一次處理一個，每個都在檢查點停下來讓你確認。
- **先準備 git**：`darwin-skill` 靠 git 回滾，但目前 `/home/dev/proj` 不是 git repo，你的 skills 目錄也要先 `git init`（或確認已經在版控中）。

剩下的 skill 如果快篩時沒發現問題，就不用花成本做深度優化。

## 開始前想先請你確認幾件事

1. **可以授權我讀取 `~/.claude/skills/`（或你的 skill 實際所在位置）嗎？**
2. 你最在意的是哪個問題：skill 不觸發或觸發錯、輸出品質不好，還是 context 太肥？
3. 哪些是你最常用的？
4. 第三方 skill 要一起處理，還是只處理你自己寫的？

確認後我就從第 0、1 步開始，這兩步只讀不改。產出清單後再一起決定哪些要進第 2 步。
