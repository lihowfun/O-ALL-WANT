我的判斷是：**還不能直接合併。** 這不是說新版不好，而是目前的證據不足以證明它比舊版好。

## 為什麼兩位同事說好還不夠

依照 darwin-skill 的證據等級，「人讀兩版 SKILL.md 後投票」屬於 **E1 讀評**。它能告訴你哪裡可能有問題、該先改哪裡，但不能拿來決定留不留。決定合併至少要 **E2 實跑**：讓 agent 真的照兩版去做同一件事，再盲評兩邊的產出。

原因有三個：

1. **讀起來好，不代表照著做會更好。** NVIDIA 在實際上線的 skill 上量過，讀文件給的分數和真正跑出來的效果幾乎無關（相關係數約 −0.03）。darwin-skill 自己的紀錄裡，也有評審 3:0 通過的改動，實際跑起來 agent 多繞了 33 次工具呼叫。
2. **不是盲評。** 同事知道哪一版是新版，而且很可能知道是你改的。這就是黑名單第 1、2 條提到的偏差。
3. **少了和「不用 skill」的對照。** 如果模型本身就很會寫 PR 摘要，新舊兩版可能都沒有帶來增益，甚至都在幫倒忙，讀文件看不出這件事。

另外，darwin-skill 對平手的規則是：兩版打平，只有在新版比較短時才保留新版。「寫得比較清楚」往往也代表寫得比較長，這一點也要確認。

## 下一步（最小可行版）

不需要跑完整的進化流程，只要對「這一個改動」做一次 E2 驗證：

1. **準備測試集（約 4 條，存成 `pr-summary/test-prompts.json`）**
   - 2 條 dev、2 條 holdout。最好用真實的 PR diff，特別是過去摘要寫壞的那幾次，例如漏掉 breaking change、把 refactor 寫成新功能、diff 太大時抓錯重點。
   - 每條寫上可以客觀核對的 checks，例如「有提到 `config.yaml` 的欄位改名」「標出了 breaking change」「沒有虛構 diff 裡沒有的檔案」。
   - 題目要挑模型不帶 skill 時有可能做不好的。太簡單的 PR 看不出差別。
2. **建立快照**：把舊版和新版的 skill 目錄分別複製到暫存目錄，例如 `W/s0/` 和 `W/s1/`，並拿掉測試檔，避免執行者看到 checks。
3. **實跑**：每條 dev 測試派獨立的子 agent，分三組各跑一次：舊版、新版、不帶 skill。三組的產出放在彼此看不到的目錄。
4. **盲評**：用 `darwin.py pair` 打亂 A/B 順序並去掉版本資訊，交給 3 位獨立評審（新版對舊版），再用 `darwin.py tally` 計票。
5. **依結果決定**：
   - 新版勝多於負，而且 checks 沒有退步，就保留。
   - 平手而且新版比較短，也保留。
   - 平手但新版沒有變短，或新版較差，就先不合併。
6. **在 holdout 上驗收一次**，確認新版不是只剛好適合 dev 那幾題，通過後再合併。

這樣大約需要 15–20 次子 agent 呼叫。如果預算有限，最少也要做第 1–5 步，並在 PR 說明裡寫清楚「只驗證過 dev 集，共 N 條」。
