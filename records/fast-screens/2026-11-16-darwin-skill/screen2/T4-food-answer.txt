## 簡短回答：不會把 60 個 skill 全部最佳化

darwin-skill 只把「實際跑出來比較好」的改動算數。完整最佳化一個 skill 大約要派 23 次子 agent，60 個就是約 1,400 次，成本太高，而且大多數 skill 不值得花這個代價。我會分三層處理：

### 第 1 層：60 個全部體檢（E0，幾乎不花 token）

```bash
python3 .claude/skills/darwin-skill/scripts/darwin.py check <放 skill 的上層目錄>
```

這一步只用腳本讀檔，不呼叫模型。它會產出一張排序表，檢查這幾類硬傷：

- **格式**：frontmatter、name 和 description 的規範
- **路由**：description 有沒有寫「何時用」，觸發詞是不是放得太後面。裝了 60 個 skill，**彼此搶同一類請求**很可能是最大的問題
- **體積**：正文有沒有超過 500 行
- **引用**：references、scripts 的路徑能不能找到
- **安全**：有沒有密鑰、個人路徑、沒有確認步驟的破壞性指令

### 第 2 層：由你挑 3～5 個做完整進化

挑選原則是「**警告最多**」和「**你最常用**」的交集。每個挑中的 skill 都走完整流程，下面每個 🔴 標記的地方我都會停下來等你確認：

1. **備份**：如果在 git repo 裡就開一個分支，不在的話就複製一份帶時間戳的備份。
2. **建測試集** 🔴：至少 2 條開發集加 2 條留出集。最好用你**真實用過的請求或踩過的坑**，從文件反推出來的題目測不出文件本身沒寫到的缺口。
3. **基線實跑** 🔴：同一題派兩個獨立子 agent，一個帶 skill，一個不帶，再請評審盲評兩邊的產出，算出這個 skill 到底有沒有幫上忙：
   - 多數輸：skill 在幫倒忙，先刪減內容，還是輸就建議停用
   - 多數平手：模型本身已經會了，由你決定要縮減、瘦身還是收手
   - 多數贏：從沒通過的檢查項裡找可以改進的地方
4. **進化循環**：最多 3 輪，每輪只驗證一個假設。三位評審盲評，**平手而且沒有變短就回滾**。
5. **留出集驗收**：確認改動不是只迎合了開發集。
6. **人工審核** 🔴：給你看 diff、每輪的結果和留出集結果，最後產出報告和成果卡片。

### 第 3 層：其餘五十幾個只修 E0 的硬傷

- 密鑰外洩、引用斷掉、description 缺少觸發情境這類問題直接修。這些改動也會動到檔案，所以動手前會先讓你過目。
- 改了 description 的，再做一次觸發測試，確認這個 skill 該被選中時會被選中，也不會去搶隔壁 skill 的請求。
- 低頻使用、又被體檢標出一堆問題的 skill，可以考慮直接停用，不一定要修。

之後換了基礎模型，可以對已經有測試集的 skill 做「複測」。模型變強以後，skill 帶來的好處常常會縮水，甚至變成反效果。
