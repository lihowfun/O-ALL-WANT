下面是我會採用的做法：

## 1. 先備份，再盤點
- 你的工作目錄不是 git repo。動手前我會先對 skills 目錄做 `git init` 加一次 commit，或者整份複製一份備份，這樣每個修改都能看 diff，也能回復。
- 把 60 個 skill 整理成一張表：名稱、description 長度、SKILL.md 行數、有沒有 `references/` 或 `scripts/`、最後修改時間。
- 如果你允許，我也會掃一下過去的對話紀錄，看哪些 skill 真的有被觸發過、哪些從來沒用過。

## 2. 先講好「最佳化」指的是什麼
通常是下面幾個目標，優先順序要你決定：
- **觸發準確**：該用的時候有被叫到，不該用的時候不會誤觸發。
- **省 context**：所有 skill 的 description 每個 session 都會載入。60 個加起來成本不小，也更容易互相搶觸發。
- **內容正確**：裡面提到的指令、路徑、API 要還存在。
- **減少重疊**：功能相近的 skill 考慮合併或刪掉。

## 3. 分流處理
先把 skill 分成四類：
- **刪除**：沒在用的、已經過時的。
- **合併**：功能重疊的。
- **改寫**：description 寫得含糊，或內容太長的。
- **保留**：已經沒問題的。

這一步只出清單給你確認，不會直接改。

## 4. 每個 skill 用同一份檢查清單
- **description**：要寫清楚「做什麼」和「什麼時候用」，給具體的觸發詞，必要時也寫「什麼情況不要用」。避免空泛的形容詞，長度要克制。
- **本文**：只放核心流程。很長的參考資料拆到 `references/`，需要時才讀。結果要固定的步驟改寫成 `scripts/`。
- **可驗證**：裡面提到的檔案、指令、旗標都實際檢查是否還存在。

## 5. 先試點，再批次
- 先挑 3 到 5 個有代表性的 skill 改好，你看過、確認風格之後再改其他的。
- 剩下的按同一份檢查清單分批處理，每批都給你看 diff。

## 6. 改完要驗證
- 每個 skill 準備幾句「應該觸發」和「不應該觸發」的測試 prompt，改之前和改之後各跑一次比較，特別注意功能相近的那幾組 skill。
