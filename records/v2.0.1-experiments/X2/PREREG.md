## 問題
deep 工作在寫程式之前做設計審查。下列四種做法，哪一種比原生多抓到埋下的缺陷、沒根據的指控不多於原生、乾淨案例不誤報，而且成本最低？
- 原生（N）
- 原生加一張不洩題的檢查清單（R）
- 另一家的單次審查（X）
- 完整 EGM（E）

結果寫進 EGM 開關「自動」那一格（D33、D37），每個主機各自決定。沒有一組合格，就維持 N，也就是一次原生、全新 context 的設計審查。這不代表設計審查沒有用：N 本身就是一次明確要求的審查。

- 每個有缺陷的案例埋 3 個缺陷（嚴重和主要交錯，2+1 或 1+2，各屬不同類別）和 2 個陷阱；乾淨案例埋 4 個陷阱。

**只描述的 2 個**：`evals/egm-local` 的 `events` 和 `clean`。
- rubric 照 2026-10-29 凍結的 `spec.json`，不改。

- `events` 是當初因為 EGM 表現好才被挑出來的案例（Codex 審查意見），放進判定會有選擇偏差。

**校準 3 個**（`categories-2.json` 裡標 `calibration` 的案例）：
- 每格只跑 N，每案 3 次，兩家都評分。
- 只用來量每個主機的雜訊下限，不進主分析。

**核實**：每個新案例由 Opus 和 Codex 各核一次（`x2_case_tools.py verify`）。核實者只看檔案，以及 rubric 指出的位置，看不到出題者寫的理由。
- 埋的缺陷要兩家都判 real 才留。
- 陷阱要兩家都判 correct 才留。
- 任一家報出 rubric 以外的嚴重或主要缺陷，就請原出題者修一次（`revise`），再核一次。
- 修過還是沒過，就刪掉那一條。乾淨案例如果還有缺陷，整個案例不用。

- 校準案例要剛好是計畫的 3 個，少一個就不凍結。
- 刪掉或修改的都寫在本頁「核實結果」。

**凍結**：核實結果和最後的 `spec.json` 推上 records 之後才開跑。`spec.json` 包含：
- 25 個案例的 rubric；
- 每個案例檔的 sha256（`case_digests`）；
- `order`、`descriptive`、`calibration` 三份清單。

`orders` 是天花板，不計分，只拿來試跑。

## 四組（每格）
每次作答都用全新的工作區，複製案例檔（README.md、docs/、src/）。

- **R**：N 加上 `checklist_R.md` 兩個標記之間的文字，一字不改，接在提示裡。
- **E**：案例檔，加上 `oaw.py init --host <格>`，預設配方，含內建 EGM。
  - OAW 版本：`claude/oaw-2` f1c9573 的 `git archive`，跟試跑同一版。
  - 提示要求讀已安裝的 `egm-review` skill 檔，照它指向的上游入口跑：TargetFile `docs/design.md`；GoldfishContext 是 README、全部 ADR 和 src；Step uninterrupted。最後照同一份 JSON 格式寫報告。
  - D37 只改 `auto` 的預設，E 的提示直接指定 EGM，所以不受影響。
- **X**：另一家的 N，也就是同一案例、同一提示、全新 session。claude 格的 X 就是 codex 格的 N，反之亦然，不另外跑。
  - 和計畫的差別：計畫寫的是唯讀的 `codex exec`，這裡用 workspace-write，因為報告要寫進 `review_out/`。其他都和 N 相同。
- **提示**：`x2_run.py` 的 `TASK`，和 EGM 自測的 `taste_run.py` 逐字相同，`{treatment}` 換成上面的文字。
- **E 有沒有照流程跑**：一次 E 實際啟動的審查子 agent 少於 5 個，就記成沒照流程（`e_compliant: false`）。
  - claude 格：主 session 裡 Agent 工具的呼叫次數。
  - codex 格：這次 thread 樹裡的子 thread 數（rollout 的 `parent_thread_id`）。`wait` 呼叫不算。
  - 每個子 agent 的名稱或 `agent_path` 都記下來，只描述。
  - 這次照樣評分，token 照算。沒有合規資料的，當成沒照流程。
  - 一格的 20 次主分析 E 裡，超過 2 次沒照流程，E 在那一格不能被選。
  - 只檢查有沒有啟動夠多的審查者，不檢查各階段的內容。

## 共同設定
- **claude**：

  - 工具 Read、Write、Glob、Grep、Agent、Skill，`--permission-mode acceptEdits`。
  - `--setting-sources project`、`--strict-mcp-config`、`--no-session-persistence`。
  - 計費來源必須是 `none`。
- **codex**：
  - `codex exec --json`、`--sandbox workspace-write`、`--ignore-user-config`、`--skip-git-repo-check`。
  - 計費必須是 ChatGPT 方案，環境裡沒有 `OPENAI_API_KEY`。
  - token 加總這次的 thread 樹：根 thread（`thread.started` 的 id），加上 `parent_thread_id` 一路連到它的子孫。只看工作資料夾等於這次工作區的 rollout 檔，全部移進 raw 資料夾。
  - 找不到根 thread 的 rollout，或它沒有用量紀錄時，用串流事件裡根 thread 的用量，加上子 thread 的 rollout，不會只剩子 thread。沒有用量的子 thread 數另外記下。
- **逾時**：每次上限 3,600 秒。逾時也算一次作答，有報告就評；token 用串流事件加總，記成下限。
- **次數和順序**：
  - 主分析加描述：每格 22 案 × 3 組 × 1 次。
  - 案例照 `order.json` 的順序；組別順序依案例位置輪替：第 i 個案例從 `["N","R","E"]` 的第 i mod 3 個開始。
  - 校準：每格 3 案 × N × 3 次（`--arms N --reps 3`），寫在另一個輸出資料夾。
  - 兩格平行跑；每格的主分析分成兩個程序，交錯各跑一半案例，用同一份順序和組別輪替，最後合併成一份作答列（`run_x2.sh`）。每個程序各分一半剩下的預算。
- **不算作答（D30）**：碰到用量上限、花 0 token（逾時但 0 token 的也算）、在結果前就出錯、計費來源不對。
  - 這些寫進 `deviations.jsonl`，token 照算。
  - runner 停下，重跑時接著跑。
  - 每次嘗試有自己的編號（`{組}-{案}.a{n}`），舊的紀錄不會被蓋掉。
- **版本綁定**：
  - 每列記 `prompt_sha256`、`runner_sha256`、`spec_sha256`，以及 E 用的 OAW 原始碼的 sha256。
  - 續跑時遇到不同版本寫的列，runner 拒絕繼續，不混用。
  - 開跑前檢查每個案例檔的 sha256 和 `spec.json` 一致；判定時再核一次每列記的案例 digest。
- **原始檔被改**：記在 `sources_changed`，報告照樣評分，在 RESULT 列出來。
- **讀到工作區以外**：作答的 agent 有讀檔工具，理論上讀得到 records（含 `spec.json` 的 rubric）。跑完後掃描每份 transcript 和 Codex rollout，找工作區以外的路徑，特別是 `OAW-records`、`spec.json`、`frozen/`；有就記成偏離並在 RESULT 列出，判定時由 Codex 決定那次要不要排除。
- **記錄**：
  - logical token：Claude 含快取讀寫，Codex 是 input 加 output。
  - 不含快取讀取的 token、秒數、子 agent 數。

## 判定（`x2_judge.py`，統計只用 `scripts/eval_stats.py`，sha256 `6ad7a60f…`）
每格、每家評分各算一次：
- **偵測率**：16 個有缺陷的案例，`detected / 埋的數量`。用 `compare(組, N, margin=0.10, floor_sd)`。
- **沒根據的指控**：20 個案例，每份報告的 `unsupported_claims` 數。用 `compare(組, N, margin=0.5, lower_is_better=True, floor_sd)`。
- **多重比較**：每格比三組（R、X、E 各對 N），用 Bonferroni 校正。區間用 `eval_stats` 的 bootstrap、分位數和下限規則，只把信賴水準改成校正後的值。
- **合格**：下面四條都要成立。
  1. **兩家都確立更好**：每一家「組 − N」偵測率的單邊 (1 − 0.025/3) 區間下界都大於 0。
  2. **兩家都確立不比 N 差**：每一家「組 − N」沒根據指控的單邊 (1 − 0.05/3) 區間上界都小於 0.5。只是「沒顯著變差」不算。
  3. 乾淨案例（4 個）沒有任何一份報告被兩家都判有誤報（沒根據的指控，或違反陷阱）。
  4. E 另外要滿足：沒照流程的次數不超過 2。
- **選哪一組**：
  - 合格的組裡，偵測率（兩家平均）最高的是「最好」。最高分平手、又不是兩家都判等價時，這一格記成未定，不照組別順序選。
  - 再看哪些合格的組和最好那組，兩家都判「等價」（`compare(組, 最好, 0.10)`）。
  - 從最好那組和這些等價的組裡，選每次 logical token 中位數最低的；成本也平手就記成未定。
  - X 跑在另一家，token 計法不同，不跟本機的組比成本：候選裡有本機的組時只比本機的組，只有 X 時才選 X。
- **都不合格**：這個主機維持 N（D37 的暫時做法變成正式結論）。
- 不管結果如何，使用者都能把開關撥到「開」，強制跑 EGM。
- **不完整**：任何一組缺任何案例、缺任何一家的評分，或缺作答列，這一格就不判定（記成未定），不會只用剩下的組做決定。
- **輸入核對**：判定程式先核對以下各項，有任何一項不符就整個拒絕判定。
  - 主分析案例等於凍結計畫減去核實時依規則刪掉的。
  - 每列的 spec、案例 digest 和版本都一致。
  - 每筆評分評的就是那一列的報告（報告 sha256），且同一家的評分程式版本一致。
  - 沒有重複的列或評分。
- **零變異下限**（`x2_calibrate.py` → `floor-final.json`）：
  - 每格、每家評分各算一個值：校準案例上 N 重複 3 次的 pooled within-case SD。
  - 實際用的下限取這個實測值和下表借來的值（`floor.json`，2026-11-08）兩者較大的。校準只能把下限調高，不能調低。
  - 比較裡有 X 的時候，取兩格中較大的下限。
  - 每個「格 × 評分家族 × 案例 × 第 1–3 次」都要剛好一筆評分，而且有對應的作答列；缺任何一筆，下限就算不出來，X2 不判定。
  - **敏感度分析**：整個判定用較高的下限重算一次；選出的組變了，這一格就記成未定。
    - 「更好」的偵測率下限乘 1.5（自由度 6 時，SD 約 85% 信賴上限）。
    - 「不比 N 差」的下限用 max(1.5 × 實測值, 借來的值)。借來的值出自原生和 EGM 的重複審查，已經涵蓋各組的變異；只有自由度 6 的 N 實測值需要多留餘裕。
    - 等價（選便宜的組）用原本的下限。
    - 全部乘 1.5 的不比 N 差結果另外列出，只描述。
  - 3 案 × 3 次只是粗略的雜訊篩檢：每格只有 6 個自由度，SD 的 95% 區間約是實測值的 0.64–2.20 倍。

  | 評分 | 偵測率（借來的） | 沒根據指控（借來的） |
  |---|---|---|
  | Opus | 0.1318 | 0.1826 |
  | Codex | 0.1318 | 0.6146 |

  - 借來的值都出自 Opus 審查者，案例是舊的、每案埋 4 個缺陷。這只是保守的起點，校準結果會一起列出。
- **誰下判定**：最後的資料交給 Codex gpt-6.1-sol（沒參與實作 N、R、E 的獨立評估者，稽核規則 5）。由它核對凍結的 `spec.json`、版本和完整性，執行 `x2_calibrate.py` 和 `x2_judge.py`，寫下判定。Claude 只負責跑作答和評分。
- **只描述、不判定**：
  - 「有提到」率：`detected` 加 `mentioned_only`。
  - 各案的分數，以及依出題家族分開的偵測率。
  - E 開的子 agent 數、秒數。
  - `events` 和 `clean` 兩個描述案例，包括在 claude 格重現 V5 的 E 對 N。
  - 兩個便宜評分者和 Opus、Codex 的一致率。

## 檢定力（事先算好，借來的偵測率下限 0.1318）
- 16 個有缺陷的案例：標準誤至少 0.0466。
- 等價（margin 0.10）判得出來：兩組完全相同時，90% 區間是 ±0.077，小於 margin。8 案時是 ±0.108，判不出。
- 校正後的「更好」：單邊 z = 2.394。下限起作用時，平均至少要多抓約 11 個百分點才可能判「更好」；要有八成機會，約要多 15 個百分點。敏感度分析下限乘 1.5 時，至少要多約 17 個百分點。這還沒算進兩家都要一致，實際門檻更高。比這小的好處可能判成未定。
- 沒根據指控的門檻（20 案）：兩組完全相同時，Codex 評分的上界約 0.41，離 0.5 不遠。所以一組平均每份報告多出約 0.08 個沒根據的指控，就可能過不了。
- 合成資料檢查（`x2_judge.py`、`x2_calibrate.py`）：
  - 校準雜訊低時，E 每案多抓 1/3 → 選 E；各組相同 → 維持 N；E 只在 5 案多抓 → 維持 N；R 和 E 平手 → 未定，或兩家都判等價時選較便宜的 R。
  - 校準雜訊高時（沒根據指控 SD 約 0.47），同樣的 E 會因為「不比 N 差」在敏感度分析下確立不了而記成未定。這是樣本量的極限，不是程式錯誤。
  - 報告被改過、下限出自另一份 spec、校準評分對不上報告，都會拒絕。

## 預算（D36）
- **Claude**：X2 合計 60M logical token。

## 事先寫明的限制
- 每案只跑 1 次。偵測率要多約 13 個百分點才有八成機會判「更好」；比這小的好處可能判成未定。
- 4 個乾淨案例沒誤報，只是否決條件，不代表誤報很少。就算 0 次，誤報率的 95% 單邊上界仍約 53%。
- 評分者和作答者都是 AI。兩家一致只代表判定不是某一家的偏好。
- 案例由 Opus 和 Codex 出題，可能偏向自己家族的審查者，所以依出題家族分開列出（只描述）。
- R 的清單來自 EGM 的公開審查準則，所以 R 對 E 不算完全獨立。
- 只測 headless 的 uninterrupted，不測 EGM 的互動式修正迴圈。
- 案例很小（每案 7k 字元以內），不代表大型設計文件。
- 不量下游的實作結果，也不比「完全不審查」。
- 兩家的 token 計法不同，成本只在同一個供應商裡比；X 只在它是唯一候選時才會被選。
- E 是否照流程跑，只看啟動的審查者數量，不檢查各階段內容。
- 呼叫出題或核實工具失敗時，工具直接停下，不寫失敗列（`x2_case_tools.py` 已凍結，沒改）；評分程式會寫。

## 凍結時仍有的爭議（Codex 第三輪，`review-3.md`）
沒有照 Codex 的建議改，理由寫在這裡，最後判定時由 Codex 一起看：
- **E 是否照流程跑**：只看啟動的審查者數量（≥5），不看各階段內容、完成回報或 context 是否全新。各階段的名稱（Codex 的 `agent_path`、Claude 的 Agent 描述）都記下來，RESULT 列出，但不當門檻，因為名稱是模型自己取的。
- **核實綁定**：核實結果和案例內容只靠 ledger 的先後順序綁定，沒有記核實當下的 digest。`x2_case_tools.py` 在出題前已凍結，不改。
- **出題和核實工具失敗**：工具直接停下，不寫失敗列，也不留原始輸出（同上，已凍結）。評分程式失敗時會寫失敗列，但模型呼叫本身失敗時沒有原始輸出可存。
- **「不比 N 差」的敏感度**：Codex 認為不該豁免借來的下限。這裡採 max(1.5 × 實測, 借來的)，理由見「零變異下限」。最後判定一律照凍結的規則；Codex 若仍認為不妥，在判定紀錄寫明，連同全部乘 1.5 的結果（RESULT 一定列出）交給 owner，不自行換規則。
