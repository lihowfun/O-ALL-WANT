# 能力型試吃：可行性檢查（不呼叫模型）

照 `PLAN.md` 第 9 節和第 12 節，凍結前要做完。PPT 的部分已做完（第 1 到 3 節）；影片的部分等 ffmpeg。

## 平台

- Linux server，沒有畫面。系統 Python 3.10，python-pptx 1.0.2。
- LibreOffice 7.3.7.2；Poppler 22.02.0（pdftotext、pdftoppm）；字型 Noto Sans CJK TC。
- 沒有 numpy；原型的像素比對用純 Python。
- 沒有 ffmpeg：影片的部分還不能做（`PLAN.md` 第 10 節的前置條件）。

## 1. PPT 工具鏈（2026-11-10）

程式：`feasibility/make_deck.py`。

- python-pptx 做出帶中文、表格、圖表的簡報，存檔、重開都正常，讀得到圖表類型、數列值和類別。
- 改一個表格儲存格，存檔、重開、LibreOffice 轉 PDF，新的值出現在 PDF 的文字裡。
- pdftotext `-bbox-layout` 給的是字詞框；中文沒有空格，一行常常被當成一個字詞。塞太多字的文字框，字詞框落在框外，看得出溢出。
- **LibreOffice 跟 PowerPoint 的算繪不完全一樣**：python-pptx 做的文字框，LibreOffice 置中顯示，PowerPoint 預設靠左。算繪結果只能當近似，結論要寫明是用 LibreOffice 算繪檢查的。

## 2. 完整看得見的檢查（`PLAN.md` 第 5 節）

程式：`feasibility/ink_proto.py`。每個文字框做四個變體（整張、整張拿掉這個框的文字、只有這個框、只有這個框拿掉文字），畫布四邊各加大 2 吋；「只有這個框」的兩張解除裁切、去掉框的底色和框線、文字改黑色、底改白色。轉 PDF 後用 pdftoppm 以 72 dpi 灰階算成圖，逐像素相減。

|---|---|---|---|---|---|---|

| 塞太多字、超出框的下緣 | 3,090 | 1.000 | 1,383 | 0 | 不過 | 不過 |

- **墨跡只取筆畫中心**：「只有這個框」相減後變暗 128 以上的像素（字覆蓋了一半以上）。第一版用「變化超過 40」連字的邊緣也算進去，深色底白字的邊緣在整張圖裡只差 40，覆蓋率 0.812，誤判成不過；改成筆畫中心後是 1.000。

- **LibreOffice 不理會「裁切」設定**（`vertOverflow="clip"`），超出的字照樣畫出來，所以這一例是被「框外」抓到，不是被覆蓋率抓到。

### 3.1 檢查程式和手造反例

`checks/ppt_fixtures.py` 造一份 15 頁、59 個框的簡報，跑 `ppt_check.py`（一次約 34 秒；凍結前修正 2 之後的版本，見 `AMENDMENTS.md`），每個框的結果都要符合預期。全部符合。

| 類別 | 手造案例 | 結果 |
|---|---|---|

- **規則**（門檻在 `ppt_check.py` 的 `THRESHOLDS`，`setup` 時跟程式一起鎖住）：144 dpi 算繪；筆畫中心 128；看得見 40；整框覆蓋率 0.95；每個配對字詞 0.9（筆畫少於 12 個像素的字詞不單獨判）；框外容許 2 點；頁外容許 0.5 點；圖表改值後圖形變化至少 0.1%（原本 0.5%，修正 2 調低：細折線圖實測只變 0.26%–0.32%）。
- **字詞配對**照 `PLAN.md` 第 5 節：字詞取頁面的繪製順序（`pdftotext -raw -bbox`），每個框的文字要等於一段連續、整字、沒被別的框用過的字詞；段落前的項目符號或編號算在這一段裡。表格逐儲存格配對，字詞框要在那幾欄的左右邊界內。
- **「拿掉文字」的頁不動版面**：把那個框的文字設成全透明（LibreOffice 照樣排版、只是不畫），不是把字刪掉。刪字的話表格的列會縮、下面的東西往上移，長英文表頭的第二行就量錯（實測覆蓋率掉到 0.57）。項目符號和編號不算進筆畫（單獨那一頁把它們設成白色）。
- **圖表文字**也進檢查（修正 2 之後的量法）：LibreOffice 不理會圖表文字的透明度，但會照指定的顏色畫。所以一次只處理一張圖表，把它的文字強制成黑色和白色各算繪一次，兩次不一樣的像素就是它的文字筆畫，格線、長條、框線不會算進來。看得見的條件有兩個：交付頁上那個筆畫真的畫出來（沒被蓋住）；它原本的顏色跟緊鄰的底色差超過 40（底色取 12 個像素內不是筆畫的像素的平均）。圖表字級只看實際顯示的文字在檔案裡寫的字級，並跟算繪回報的整數核對。
- **繼承來的字級**：run、段落、形狀的清單樣式、版面配置和母片的版面配置區、母片的文字樣式、簡報預設，依序找。檔案推算的字級和算繪出來的字級差超過 1.5 點時以算繪為準（兩個方向都是）。實測：版面配置區自己的段落寫 60，LibreOffice 仍照母片算繪成 44，推算的 44 是對的。
- **已知限制**（照實記）：
  - 中文沒有空格，一行常常是一個字詞。一行裡只有一個字被遮掉一半時，整框覆蓋率 0.98、該字詞也在 0.9 以上，照凍結的規則抓不到（`onechar` 案例）。`PLAN.md` 第 5 節「一個字被遮掉下半部也抓得到」只在那個字自己是一個字詞時成立。
  - `pdftohtml` 回報的字級是整數、無條件捨去（44 回報 43）。只在檔案和算繪差超過 1.5 點時才用到它。
  - LibreOffice 不理會「裁切」設定，裁切的案例是被「框外」抓到。
  - 投影片編號這類欄位：變體簡報裡換成同一個數字的一般文字再量（複製出來的頁位置不同，不換的話數字會變）。LibreOffice 排「帶欄位的一行」和「同樣數字打成文字的一行」行高略有不同（實測約 4.5 點），所以同一個框裡除了編號還有別的字時，溢出判斷可能有幾點出入；純編號的框沒有差別。帶欄位的段落不做逐字配對，筆畫照量。
  - `word-out` 用的是字詞的行框（字型的上緣到下緣），不是筆畫。行距設得比文字框高的標題，筆畫全部在框內也可能因為行框多出幾點而不通過（校準時實際遇到兩題，見 `CALIBRATION.md`）。對各組一樣。
  - 開得起來、但量不出來的簡報，分三步判斷是誰的問題：磁碟還有沒有空間；轉檔程式在這裡能不能把一份對照簡報轉成 PDF；交付檔單獨轉不轉得出來。只有「對照簡報轉得出來、交付檔轉不出來」才算簡報本身不合格；其他都算評分環境的問題（這次 run 不計分、重跑）。合成測試四種情況都驗過。
  - 項目符號不認中文自動編號（「一、」「①」）；python-pptx 幾乎不會產生，遇到的話那一段會配對不到。
  - 圖表裡 2 到 3 個字的斜放標籤偵測不到（4 個字以上才看得出來）；直立的抓得到。對各組一樣。
  - 表格改值用的標記字在窄欄會折行：改成把那一格欄界內的字詞照繪製順序串起來找，折行也認得。

### 3.2 沙箱和隔離

- 沙箱從空的根目錄開始，只掛：系統目錄（`/usr`、`/bin`、`/sbin`、`/lib*`、`/etc`、`/opt/google`、字型快取、CPU 資訊）唯讀、全新的 `/tmp` 和 `/dev`、兩個 CLI 的工具副本、全新的工作目錄和家目錄、該組的安裝樣板（唯讀，掛在安裝後會在的路徑）、登入檔。
- 探針在每一組的沙箱裡列出看得到的東西：根目錄只有上面那些；`/home` 底下只有沙箱的家目錄和一個工具副本的掛載點；找不到任何主機的 socket；環境變數只有 runner 給的。題庫、參考成品、其他 run、候選樣板的來源、主機家目錄都不在裡面。runner 每個指令開頭檢查這些路徑不在沙箱看得到的目錄裡，反方向也檢查。
- **共同工具一致**：每一組掛同一個共同工具資料夾（python-pptx、lxml、XlsxWriter）；Pillow、LibreOffice、Poppler、字型來自系統；Node 和兩個 CLI 來自同一份工具副本。候選的掛載不能碰到共同工具、工具副本、系統目錄、工作目錄、登入檔（`template_problems()`），掛載來源要完全在樣板裡（樣板的摘要涵蓋掛進去的每個檔案）。
- **plugins、MCP、hooks**：Claude 格每一組啟動時都是同樣 4 個內建 plugin、0 個 MCP server、同樣 11 個工具、同樣 5 個 agent；Codex 格每一組同樣 11 個工具、同樣 4 個內建 skill。跑完後 `checks/run_check.py` 逐筆再核對一次。
- **啟動清單**（探針，2026-11-12，凍結用的那一輪）：

  這是一行提示（「只回 OK」）量到的；閒置題的提示比較長，比值會再小一點。
- **發現並處理的一件事：Claude Code 啟動時列出的東西不是只由組別決定。** 同一組、全新的家目錄，啟動 token 量到過 12,232、12,319、12,453 三種。原因有兩個，都跟候選無關：
  - 三個指令（其中 `schedule` 是模型看得到的 skill，約 134 token）受遠端旗標控制，session 開始時旗標到了沒有，決定它們在不在第一次呼叫裡。
  - 兩個用量指令（合計約 221 token）看 CLI 快取的帳號狀態；全新家目錄的第一個 session 沒有這份快取。

  - 每個 Claude 家目錄一開始都放同一份 CLI 狀態檔（`warm` 指令用原生組的兩個一行 session 產生；裡面是 CLI 對帳號的快取，沒有候選和題目的東西）。
  - 每個 session 啟動時列出的 skill 和指令要跟該組凍結的清單完全一樣；不一樣就在第一次呼叫之前停掉重來（不花 token，另外計數，最多 10 次）。
  
  歷次探針都留在狀態資料夾的探針紀錄裡。`PLAN.md` 第 7 節「這個數字幾乎不變」的前提在這個 CLI 版本不成立，這是實作上補的，記在偏離裡。

### 3.3 網路

- 沙箱自己沒有網路（獨立的 network namespace，只有 loopback）。沙箱裡一個轉送程式聽 `127.0.0.1`，把連線原樣交給沙箱外的 proxy；proxy 只接受白名單主機的 `CONNECT`，其他一律 403，每筆記錄。
- 白名單：Claude 格 `api.anthropic.com`、`console.anthropic.com`、`platform.claude.com`；Codex 格 `chatgpt.com`、`auth.openai.com`、`api.openai.com`（都只開 443）。
- 探針（每一格、每一組都跑）：curl 抓 npm、PyPI、GitHub（走 proxy 和不走 proxy）、純 HTTP、直接連 IP、Python urllib、Python socket 直連、pip download、npm view、Node fetch、git ls-remote、DNS 查詢、主機 socket，共 14 項，全部失敗才算過。8 組探針全過；proxy 記到對 `registry.npmjs.org`、`pypi.org`、`github.com` 的請求都回 403。模型呼叫正常（Claude 的計費來源 `none`，Codex 是 ChatGPT 登入）。
- session 期間被 proxy 擋下的其他主機：Claude 的遙測主機、Codex 的實驗和圖片主機。擋掉不影響作答。
- 正式 run 用的就是探針驗過的設定：每筆探針記著啟動設定、proxy 程式、該組樣板、工具副本、暖機檔的摘要，凍結時逐組核對。

### 3.5 判定、帳本、磁碟

- `checks/judge_check.py`：合成的結果列 37 項，涵蓋 `PLAN.md` 第 6、7 節每個邊界和合併表的先後順序（剛好 1.02 倍算過、略高就不過；兩格同一題 N 對 S 錯才是不通過；未完成先於不採用等）。37/37。
- `checks/run_check_test.py`：合成帳本，「先失敗、第二次才計分」的 run 對得起來；多一筆計分列、少一筆嘗試、順序不對、token 對不上、計分列跟嘗試不一致、題目摘要被換掉、題庫檔跟凍結的不一樣，各自都被抓到。
- 帳本規則：每格每個 tag 只能有一支 runner（執行鎖）；每筆 run 先寫開始紀錄；中斷的算一次嘗試；第一筆合格的結果就採用，寫入前在鎖裡再查一次；Codex 最多同時 2 個 session。
- 時間和 token 上限：每個 session 7,200 秒（照 H1）、Claude 每個 session 3M token（H1 是 8M；這裡每個領域的上限只有 30M，所以收緊）。到上限就切斷，成品照當下的樣子評分。
- session 結束時暫存磁碟剩不到 1G 的話，這次 run 不計分（agent 在沙箱裡寫不進去，runner 看不到）。
- 預算：所有 Claude session（暖機、探針、作答、閒置）共用同一個檢查，已花加上下一次預估的 1.25 倍超過 27M 就照序列停下。到凍結前，Claude 的探針和暖機一共花了多少，記在 `RESULT.md`。
- 磁碟：這台機器的本機磁碟只剩約 11G，達不到 15G 安全量。做法是把 session 進行中的工作目錄和家目錄放本機（跑完清掉），保留的東西（原始串流、成品、算繪圖、結果）放空間充足的另一個磁碟；15G 安全量算在保留的那一顆上，本機那一顆要求「量到的單次峰值 × 2」。峰值是 run 進行中每 10 秒量一次暫存目錄取最大值；選題時把選上的題在校準時量到的最大峰值寫進凍結檔。空間不夠就不開跑；跑到一半寫不進去記成沒跑成，不算候選失敗。
- 評分環境失敗（量不出來、轉檔逾時、空間不夠、題目的檢查器自己丟例外）不會被算成候選沒過：這種 run 不計分，重跑。驗題時每題的檢查器要對 3 份沒有人出的簡報都答得出來，否則這題不合格。
