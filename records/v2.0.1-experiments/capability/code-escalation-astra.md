以下是另外確認的問題。

**34. 阻擋｜轉檔失敗仍可能被錯誤歸因給成品。**

位置：`ppt_check.py:877`、`ppt_check.py:1284`、`cap_run.py:854`。

`grade()` 在量測失敗後，用「交付檔單獨轉檔是否成功」區分環境問題與成品問題；但單獨轉檔也可能遭遇環境故障。`convert()` 把逾時變成普通錯誤字串，非 `ENOSPC` 的 `OSError` 則被轉成 `alone=False`，最後回傳 `pass=False、infra=""`。runner 會接受這筆失敗分數。

純記憶體故障注入確認：找不到轉檔工具，以及量測例外後單獨轉檔逾時，都能得到上述可計分結果。**第二次轉檔失敗並不能證明簡報不合格。**

建議保留結構化的轉檔失敗原因；逾時、工具啟動失敗、資源不足應一路傳成 `infra`。只有能確定屬於檔案內容的失敗，才判成品不合格。

**35. 阻擋｜表格改值驗證要求測試標記恰好是一個 PDF 字詞。**

位置：`ppt_check.py:743`、`ppt_check.py:1141`。

檢查器固定向第一個可寫儲存格填入 `ZQ7XK`，隨後要求某個單獨字詞滿足 `norm(text) == MARK`。標記分成兩行時，即使完整保存、完整顯示在正確儲存格，仍會得到 `editable=False`。這把測試標記的排版條件混進了成品的可編輯性判定，對窄欄或較大字級的表格不公平。

已用真實 python-pptx 表格物件與替身 PDF 字詞重現：單一 `ZQ7XK` 判 `True`；同欄內兩行 `ZQ7`、`XK` 判 `False`，保存的儲存格內容相同。這是控制流程重現，未宣稱重跑過 LibreOffice 換行案例。

建議在隔離的表格中，核對實際修改儲存格內的連續字詞序列，容許跨行；或選擇能可靠容納的短標記。補上窄欄、大字級的實際算繪測試。

**36. 提醒｜對帳器把目前題庫檔當成凍結題庫，未驗證其凍結摘要。**

位置：`checks/run_check.py:65`、`checks/run_check.py:97`。

目前從 `units_ppt.json`、`units_idle.json` 計算 unit 摘要，但沒有先比對 `FREEZE.json` 的 `units_ppt_sha256`、`idle.units_sha256`。

記憶體案例確認：修改題庫內容，再同步修改 starts／attempts／rows 的 unit 摘要，即使題庫檔已不符合凍結摘要，對帳仍回傳 0。正常 runner 的開跑前核對有保護，因此這是對帳保證不完整，沒有另列為開跑阻擋。

建議先驗證兩份題庫檔的凍結摘要，再逐筆比對 unit。
