Codex 判「先改再跑」：第 2 次的 14 點裡 13 點關閉，第 28 點還有兩條路徑沒關；另提 29–33。三輪用完，照 owner 的規則，改完之後交給 gpt-6-astra 和 Fable 5.1 各自判斷（`code-escalation-*.md`）。

| # | Codex 指出 | 怎麼改 |
|---|---|---|
| 28a | 改值驗證把空間不足等例外吞掉，變成「不可編輯」 | `round_trip()`：`OSError` 和子程序錯誤往外丟，由 `grade()` 判成 `infra`（空間不足直接停）；只有簡報本身造成的例外才記成不可編輯 |
| 28b | 題目檢查器丟例外時，runner 仍當成候選沒過 | runner 把 `check_error` 當成評分失敗：這次 run 不計分。另外從源頭擋：驗題時多跑 3 份沒有人出的簡報（一頁空白、14 頁只有標題、3 頁各有一格的表和兩張圖表其中一張沒有類別），題目的檢查器對每一份都要回答、不能丟例外，否則這題不合格。brief 也寫明檢查器對任何簡報都要回答 |
| 29 | 左上格空白的表格被誤判不可編輯 | `edit_table()` 回傳實際寫入的列、欄、跨欄數；驗證用那一格的欄界（`frame.grid` 存每一欄的左右邊界），不再拿「第一個有字的格子」。反例 `corner-table` |
| 30 | 圖表用灰階對比找筆畫，會誤殺彩色字 | 改用 RGB：任何一個色頻跟字詞框的中位數顏色差 64 以上就是筆畫；白底黑底的比較也用 RGB。反例 `colour-chart`（灰底 `#808080` 上的紅字 `#FF0000`，該過，過了） |
| 31 | 欄位文字（投影片編號）整個被排除 | 只有欄位的框也是 frame，照樣量筆畫（覆蓋率、框外、頁外）和字級。帶欄位的段落不做逐字配對（欄位顯示什麼只有算繪器知道，檔案裡的快取可能是舊的）；其他段落照常配對。投影片編號欄位在變體簡報裡換成同一個數字的一般文字（複製出來的頁在變體簡報裡的位置不同，不換的話數字會變），交付頁、拿掉文字的頁、單獨的頁三者一致。`s.has()` 不含欄位顯示的內容，brief 寫明用 `s.rendered()`。反例 `page-number`、`page-mixed`、`page-covered` |
| 32 | `hMerge="0"` 被當成合併 | 只有值是 `1` 或 `true` 才算被併掉。反例 `false-flags` |
| 33 | 對帳只核對 root 關聯 | `checks/run_check.py`：計分列要跟它的嘗試紀錄整筆相同；嘗試要帶著開始紀錄的識別欄位和摘要；正式 run 的題目摘要要等於凍結的題庫檔算出來的摘要。合成帳本多兩種竄改（改掉計分列的結果、換掉題目摘要），都被抓到 |

實作過程另外記下的一個限制：LibreOffice 排「帶欄位的一行」和「同樣數字打成一般文字的一行」行高略有不同（實測差約 4.5 點）。帶投影片編號的框是照「數字打成一般文字」量的，這類框的溢出判斷可能有幾點的出入；純編號的框沒有差別。寫進 `FEASIBILITY.md` 的已知限制。
