29. **阻擋｜`ppt_check.py:1044`、1046：左上格留白的表格會被誤判不可編輯。**

    修改的是第一個可寫儲存格，但驗證位置取自 `item.frame.cells[0]`；後者是「第一個有文字的儲存格」。兩者不一定相同。

    已用真實 python-pptx 記憶體表格重現：左上格空白、右上格有年份，修改後左上格確實保存 `ZQ7XK`，但驗證拿右上格欄界查找，得到 `editable=False`。這會誤殺常見的空白角落表頭。

    建議讓 `edit_table()` 回傳實際修改的列、欄與合併範圍，再使用該格的欄界驗證；不要依有文字儲存格清單的位置推定。

30. **阻擋｜`ppt_check.py:873`、979：圖表用灰階對比找墨跡，會誤殺可區分的彩色文字。**

    不透明圖表底色走「與灰階中位數差至少 64」的分支，RGB 色彩差異已經丟失。

    合成像素反例已確認：`#FF0000` 紅色文字放在 `#808080` 灰底上，灰階差只有 52，`chart_ink()` 得到零墨跡；相同像素用程式自己的 RGB 可見性規則，卻有 651 個可見像素。後續圖表字詞覆蓋率因此成為零。brief 沒有限制這種配色，計畫也不評美感。

    建議保留 RGB 資訊，以各色頻差異建立圖表墨跡，或採用保留文字排版的差分基準；補上彩色文字與底色灰階相近的合規案例。

31. **應修｜`ppt_check.py:153`、464：欄位文字被整個排除，既漏驗，也可能漏算正確內容。**

    `paragraphs_of()` 只讀 `a:r`，忽略 `a:fld`；沒有一般 run 的框隨後直接被跳過。

    已用真正的 `slidenum` 欄位物件重現：python-pptx 讀到文字 `"1"`，檢查器卻建立零個 frame，`s.has("1")` 也為假。這類文字不會接受字級、溢出或遮擋檢查；混合一般文字與欄位的段落也會缺字。

    建議將欄位納入文字框量測，透過算繪結果取得實際顯示內容；不要直接將可能過期的欄位快取當成真值，也不要整個略過。

32. **應修｜`ppt_check.py:674`：合法的假值合併屬性會讓普通儲存格無法改值。**

    `first_cell()` 以屬性是否存在判斷合併，而非屬性的布林值。因此 `hMerge="0"`、`vMerge="0"` 也被當成合併延續格。

    記憶體重現中，python-pptx 判定該格 `is_spanned=False`，但 `first_cell()` 找不到儲存格，`edit_table()` 回傳 `False`。合法但採不同 XML 序列化方式的表格會被誤判。

    建議只在屬性值為 `"1"` 或 `"true"` 時排除延續格，並加入明寫假值的案例。

33. **提醒｜`checks/run_check.py:80`、106：對帳只核對 root 關聯，沒有核對內容及 unit 摘要。**

    已用純記憶體帳本確認：保留同一 root，把 counted row 的 `passed` 改成與 attempt 相反，再放入錯誤的 `unit_sha256`，對帳器仍回傳 0、沒有問題。

    建議比較 counted row 與對應 attempt 的完整內容，核對 start 的識別與來源欄位，並依凍結的 unit 檔驗證 `unit_sha256`。
