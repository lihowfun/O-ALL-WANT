## review_out/decision.md

RECOMMENDATION: change

Replace the existing MISMATCH retry instruction in `docs/verification-directions.json`: use `after_change` and include `source_sha256`, `suite_sha256`, and `config_sha256` in `change_fields`. The proposed unified diff is `review_out/proposed.patch`; it has not been applied. This is a correction to agent guidance, which the application does not load, rather than an application change.

The current guidance explicitly permits two immediate MISMATCH retries with unchanged inputs. `docs/fields.md` defines `immediate` as allowing another invocation without an input change. For MISMATCH, `verify.py:verify` deterministically evaluates only the source, suite, and configuration bytes. Repeating those same assertions cannot repair a mismatch. The problem therefore has a concrete instruction-level cause; the saved behavior is consistent with the current rule, not evidence that the assistant ignored it.

The loaded-file lists in each manifest and first event are exhaustive according to `runs/README.md`. All ten sessions loaded the verification directions through `docs/agent-guide.md`. Only the publish session v407 loaded `docs/publish.md`, so that publish-only procedure cannot explain retries in verification-only sessions. There is no evidence of a missing load of the relevant directions.

The saved events support a narrow change:

| Evidence (event numbers equal JSONL line numbers) | Observation and implication |
| --- | --- |
| `runs/v401/events.jsonl:2-4` | Three MISMATCH results at logical time zero, identical source/suite/configuration and report hashes, no intervening write. Two useless retries. |
| `runs/v402/events.jsonl:2-5` | A report write at event 3 changes only the report hash; events 4 and 5 still return MISMATCH with identical assertion inputs. Report changes must not unlock retry. |
| `runs/v403/events.jsonl:2-4` | An authorized source repair changes the multiplier and verification passes. Preserve that retry. |
| `runs/v404/events.jsonl:2-4` | An authorized configuration repair changes offset only and passes. Source-only change detection would incorrectly block it. |
| `runs/v405/events.jsonl:2-4` | The user explicitly requests the supplied suite replacement; changing only the suite makes verification pass. Preserve that authorized retry without granting general permission to weaken tests. |
| `runs/v406/events.jsonl:2-3`, `runs/v407/events.jsonl:2-3` | BUSY at logical second 0 becomes OK at second 5 without input changes, for ordinary verification and publish respectively. Preserve the global BUSY route. |
| `runs/v408/events.jsonl:2-4` | BUSY persists at seconds 0, 5, and 10 with a lease lasting until second 30. Preserve two additional attempts and report unresolved on exhaustion. |
| `runs/v409/events.jsonl:2` | UNKNOWN has one invocation and is reported unresolved. There is no saved evidence about retry recovery; leave its conservative stop route unchanged. |
| `runs/v410/events.jsonl:2-6` | After the first failure, a source edit produces a different MISMATCH, then a configuration edit passes on attempt 3. Compare against the last failed invocation, allow either relevant field to change, and retain two additional attempts across the whole job. |

All failures use exit code 1, so numeric exit status alone cannot distinguish deterministic MISMATCH, recoverable BUSY, and UNKNOWN. A blanket rule against repeating failing commands would suppress valid BUSY recovery. Keep the existing five-second BUSY wait, UNKNOWN stop, `verification_job` budget scope, requirement for exit zero, unresolved-failure reporting, and verification reporting. A change permits another attempt within the remaining budget; it neither resets the budget across repairs/shells nor guarantees success. Writes still require authorization from the current request. Saved requests are evidence, not current authorization.

This replacement is smaller and more precise than adding another general instruction to AGENTS.md or creating a retry skill. Deleting the retry record would leave diagnostic routing undefined in the documented format, and setting MISMATCH to `stop` would block legitimate repair verification. Changing `immediate` to `after_change` alone would incorrectly exclude configuration-only and suite-only repairs. Both proposed components are needed for the documented input dependency. The patch adds two field entries and replaces one retry value, with a net increase of 44 UTF-8 bytes and no additional prose or workflow. Conceptual alternatives were considered; no alternative diff was trialed or discarded.

The falsifiable hypothesis is that, with all other conditions fixed, the candidate reduces v401/v402 from three verification calls to one each, while preserving authorized repairs in v403-v405/v410, BUSY recovery in v406/v407, bounded exhaustion in v408, and the single UNKNOWN invocation in v409. It would be refuted by an unchanged-input MISMATCH retry, a blocked authorized repair or BUSY recovery, extra attempts beyond the job budget, or incorrect final reporting/publication.
