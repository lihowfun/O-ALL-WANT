RECOMMENDATION: change

Change only `docs/verification-directions.json`: make the `MISMATCH` route
`after_change` and track `source_sha256`, `suite_sha256`, and `config_sha256`.
The unified diff is in [proposed.patch](proposed.patch). It has not been applied
to active guidance. This JSON is agent guidance, as both `docs/agent-guide.md`
and `docs/fields.md` state; the application does not load it.

The current rule explicitly permits the reported behavior. `MISMATCH` uses
`retry: immediate`, allowing two further calls without an input change.
`verify.py:verify` computes assertions deterministically from source, suite, and
configuration once the lease is available. Repeating a mismatch with those
same inputs cannot repair it. The existing `change_fields: [source_sha256]`
has no effect while the route is `immediate`.

Why this edit
-------------

Use the existing routing format rather than add another general retry rule.
Deleting the routing instructions would also remove useful diagnostic handling,
bounded recovery, and reporting requirements. The current host already supports
reading diagnostics and files and deciding whether another check is justified;
the project rule is the specific permission for unchanged mismatch retries.
No new tool, hook, skill, or global guidance is needed.

The three input hashes are all necessary. A source-only gate blocks the
successful configuration-only repair in v404 and suite-only repair in v405.
In v410, compare against the **last failed invocation**, as `docs/fields.md`
requires: after the source edit fails, the later configuration edit must qualify
independently. Including `report_sha256` permits the useless second call in
v402. Changes remain subject to the user's request; a changed hash is a retry
condition, not permission to edit inputs or weaken assertions.

Keep two extra attempts per verification job, across shells and repairs. Reducing
the allowance to one blocks v410's final successful check; resetting it after
each edit would allow an unbounded job. An input change permits checking a repair
but does not promise success. Without an authorized relevant change, report the
mismatch unresolved instead of spending the remaining allowance.

Keep BUSY's five-second wait and bounded repeats. BUSY occurs before assertions
run, and time can release the lease without changing assertion inputs. Gating
BUSY on input hashes blocks recovery in v406 and v407. v408 demonstrates why
polling still needs a cap; exhausting the three calls must leave it unresolved,
possibly requiring operator attention. Keep UNKNOWN's stop route: its single
saved invocation provides no evidence supporting recovery by repetition.

Keep success dependent on exit zero, unresolved-failure reporting, verification
reporting, and the publish requirement to withhold publishing on unresolved
verification. All three failure diagnostics use exit code 1, so routing must
continue to use the diagnostic rather than the exit number.

Validation and limits
---------------------

The falsifiable hypothesis is that assistants following the amended directions
will skip unchanged-input MISMATCH retries, including after report writes, while
retaining authorized source/configuration/suite repair checks, bounded BUSY
recovery, UNKNOWN stopping, truthful reporting, and publish gating.

Reproduce the local evidence with `python3 review_out/replay.py`; its retained
output is [evidence.json](evidence.json). It validates manifest provenance,
reconstructs exact bytes after every write, checks fingerprints, reproduces all
23 recorded results using the current verifier, and checks that the candidate
matches the proposed diff. The candidate filter allows 19 calls, eliminating
four redundant calls (17.4% of this sample) while preserving all ten terminal
diagnostics and resolution states. Alternative policies in the same output show
the source-only, report-inclusive, reduced-budget, stop-on-mismatch, and
input-gated-BUSY regressions described above.

This is a deterministic counterfactual over saved traces, not a matched live
assistant experiment. No capture uses amended guidance. Although all manifests
identify `local-assistant-4` with high effort, they lack host/version and complete
environment/permission metadata, token usage, and measured latency. Logical
seconds model the lease; event timestamps are not assistant performance metrics.
The four-call reduction is a policy prediction, not measured token, cost, or
wall-clock savings. Holding later edits fixed also cannot prove how an assistant
would behave after a skipped call.

Before claiming a behavioral improvement, run baseline and candidate assistants
on the same saved requests and exact starting states, with the same model,
effort, host/version, repository, environment, permissions, and tools. Use at
least three independent repetitions per case; retain tool calls, outputs,
permission checks, final reports, and usage/time measurements. Require no
unchanged-input MISMATCH repeats, successful authorized repairs including both
steps of v410, unchanged bounded BUSY recovery, UNKNOWN stopping, no unauthorized
edits/publishing, and truthful terminal reporting. Treat any regression as a
reason to revise or reject. No live candidate run or external action was taken.

Additional checks passed: the unified diff passes `patch --dry-run -p1`, all four
existing unit tests pass with `/usr/bin/python3 -m unittest discover -s tests`,
and `/usr/bin/python3 verify.py` exits zero on current workspace inputs. The
first patch dry run could not create a temporary file in read-only `/tmp`;
setting `TMPDIR` to a temporary directory under `review_out` resolved it.
The OAW precheck selected light work. Its required postcheck without paths
cannot inspect a diff because this workspace has no Git repository; a path-list
fallback selects light but cannot provide a Git-based line-count review.
