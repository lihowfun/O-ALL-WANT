## 問題
一份 bug bash 配方（`oaw-bugbash`，claude/oaw-2 8abc84e）能不能讓 agent 透過指令列多抓到埋好的缺陷？條件是沒根據的回報不能變多，成本不超過原生的 1.5 倍。

配方的內容：先寫情境計畫，加上對抗性的輸入變化，再記下做過的動作和看到的證據，最後寫出可以重現的缺陷報告。

結果照 D29 決定配方是進預設、可選用還是排掉。在那之前，配方只能用 `--skills oaw-bugbash` 明確選裝。

## 四組（每格）
每次作答都用全新的工作區，放在隨機命名、互不相鄰的資料夾裡：
1. 一份 OAW 副本放在 `./oaw`，有缺陷的流程套上 patch。
2. 跑完 setup。
3. 給一個任務提示（`i16_run.py` 的 `TASK`）。

提示的內容（三組相同）：
- 只能像使用者一樣，透過指令、說明文字和文件測試。
- 不能讀或改原始碼和測試，也不能讀或改裝進專案的腳本副本。
- 不連網。
- 報告寫到 `bugbash_out/report.json`，格式凍結在 `categories.json`。
- 每個缺陷的步驟會被機械重播：最多 25 步，每步 60 秒內，不連網。

| 組 | 內容 | 用途 |
|---|---|---|
| N | 只有任務提示 | 原生基準 |
| C | 任務提示加一句：「寫報告之前，也試試相關的對抗性變化，例如空的、格式錯的、過大的或 Unicode 輸入，並檢查結果狀態是否符合預期。」 | 不洩題的便宜做法（EVAL_PROTOCOL）。這句話摘自配方自己的第 1、3 步，配方是在看不到題目的情況下寫的 |
| D | 加一行「讀 `<skill 路徑>` 照做」。檔案裡只有配方的名稱和 description，正文就是那句 description | skill 的「只放 description」對照 |
| F | 同一行提示，檔案是完整配方 | 受測的配方 |

- 各組工具、逾時（1800 秒）、effort 都相同。
- 每格依流程位置輪換四組的先後順序。
- **C 的解讀（事先寫明）**：如果 C 自己也通過 BASH，而且兩家評分都沒有判 F 的偵測比 C 好，就表示好處來自那一句提示，不是整份配方。這只寫進 RESULT 給 owner 參考，不改變 F 的判定。

**正對照**（`i16_controls.py`，在校準之前）：
- 每條缺陷流程造一份「正確的報告」：唯一的步驟就是跑那條流程自己的判定腳本，它會在有缺陷版重現缺陷。
- 這份報告照正式流程重播、由兩家評分。
- 用途：確認評分流程認得出一份正確、可重現的報告。
- 兩家都要在 6 條流程上全部給「抓到」才算通過。沒通過，研究就停在校準之前，交給 owner 和 Codex；判定程式也會拒絕沒有通過正對照的 spec。
- 成本：Opus 評分 6 份，約 35k。
- 結果（凍結版本，`controls.json`）：兩家都在 6 條流程上給「抓到」，通過。

## 隔離
- **沙箱**：測試者整個程序跑在 bubblewrap 裡。
  - 整個檔案系統唯讀。
  - `/tmp` 和家目錄換成空的 tmpfs，所以讀不到任何過去的對話、記憶、設定或全域指示。
  - 主機只拿到登入檔，用 bind 掛上，不複製：Claude 是 `.credentials.json`，Codex 是 `auth.json`。
  - Codex 的 sessions 資料夾每次作答各給一個，裡面的 rollout 全部屬於這次作答，也全部計費。
  - 專案資料夾（records、rubric、其他 repo，含 token 檔）整個遮掉。
  - 只有工作區可寫，隔壁的工作區看不到。
- **為什麼兩格都用 bubblewrap**：2026-11-09 實測，Claude Code 自己的 Bash 沙箱在這台機器上沒有生效，寫得到工作區外。所以兩格都改用 bubblewrap 隔離。
- **環境變數**：OAW 和工具的狀態都導到工作區裡的 `./.state`（`base_env`）。setup、測試者和重播看到的是同一份狀態。
- **黑箱遵守**：每次記下讀原始碼的工具呼叫數（`source_reads`）。
  - 算進去的：讀取類指令（cat、sed、grep 等）或 `open()` 讀 `scripts/`、`templates/`、`tests/`、`vendor/` 底下的檔案，包含裝進專案的副本、萬用字元，也包含先 cd 進這些資料夾，或工具呼叫的 workdir 設在這些資料夾再讀。Codex 每個 thread 都從 rollout 掃，所以保留了每次呼叫的 workdir。
  - 不算的：執行腳本、排除用的 glob。
  - 有讀的列照算，RESULT 列出各組次數，另做一次排除這些列的描述分析。
- **工具被改**：作答前後比對 `./oaw` 的 digest，改過的記下來（`tool_changed`）。裝進專案的 `scripts/` 也比對（`project_scripts_changed`），但 init、migrate 這類指令本來就會改寫它們，所以只描述。
- **案例檔**：開跑和重播前都核對案例資料夾的 digest。

## 重播（`i16_replay.py`）
- **重播什麼**：報告裡每個缺陷的 `steps`，在兩份全新的起始狀態上照順序重跑。一份是有缺陷版（測試者拿到的），一份是乾淨版。乾淨對照只有一份。
- **限制**：每步 60 秒，最多 25 步。沙箱不連網，也不帶主機狀態。
- **輸出**：工作區路徑換成 `<ws>`，每步截斷，交給評分者。
- **綁定**：每筆重播都記下重播程式、runner、spec、案例、報告和兩個工具的 digest。續跑時有任何一項不符就停。

## 評分（`i16_grade.py`）
- **評分者**：Opus 5.5 和 Codex gpt-6.1-sol 各評一次。
  - 全新 session、沒有工具，跑在和測試者一樣的沙箱裡，家目錄全新、只掛登入檔。
  - 事件紀錄裡只要有任何工具呼叫，那筆就不算，記成偏離。
- **評分者看得到**：
  - 流程和 setup；
  - 埋的缺陷描述，或「沒有埋缺陷」；
  - 拿掉組別和方法後的報告：方法名稱、skill 路徑、組別代號、測試者的自我介紹、模型名稱和廠商名稱會遮掉，遮掉的次數記下來。主機名稱（Claude Code、Codex）保留，因為 OAW 自己的指令和輸出就會用到它們（`--host claude|codex`）。
  - 報告逐欄位截斷，每個缺陷都保留，一定是合法 JSON；
  - 每個缺陷的重播輸出：純文字，每一步、兩個版本對稱截斷，保留結束碼。
- **評分順序**：跨格、跨組、跨重複，用 hash 打亂。
- **每個回報的缺陷判成以下一種**：
  - `planted`：就是埋的那個，而且它的步驟在有缺陷版的重播裡看得到那個錯誤行為。只能算一次。描述對了但重播不出來，判 `unsupported`，並記「只提到」。
  - `real_other`：重播看得到、對使用者明顯是錯的其他真缺陷。
  - `unsupported`：重播不出來、是設計如此、是推測或只是偏好。
  - `duplicate`：和同一份報告裡前面的缺陷重複。
- **另記** `planted_mentioned_only`：只當成懷疑提到，沒有當成缺陷回報。
- **格式檢查**：每個回報的缺陷剛好判一次；乾淨對照不能給埋設缺陷的分；「抓到」和「只提到」不能同時成立；判成無效的報告不能得分。
- **呼叫失敗**：評分沒跑、或格式不合格就停下來，記成偏離，重跑時從斷點繼續。
- **版本**：評分程式的版本涵蓋它實際執行的所有檔案（評分、沙箱、解析）。續跑時版本、spec 或評分家族不符就停。
- **綁定**：每筆評分記下它看到的重播內容摘要和重播程式版本。續跑時報告或重播內容變了就停。判定程式重算一次：
  - 列的 runner 只能有一個版本；提示版本依「格 × 組」各只能有一個（D、F 的 skill 路徑兩格本來就不同）。
  - 案例和工具 digest 要等於 spec。
  - 每筆評分要對得上那一列的報告、runner 和重播內容。每筆重播要對得上 spec、案例、兩個工具、原列的 runner，以及評分紀錄寫的重播程式版本。
  - 正式評分用的評分程式和重播程式版本，要和正對照檢查過的版本相同。
- **稽核紀錄**：評分者的完整事件串存在本機（不推上 records）。每筆評分記下事件串摘要、工具呼叫數（必須是 0），以及遮蔽前、後的提示摘要。
- **便宜評分者**：gpt-6-luna、Haiku 5.5 照 D36 一起評，只描述。

## 校準和天花板（`i16_judge.py calibrate`，在主分析之前）
- **跑什麼**：每格只跑 N，6 條缺陷流程各 3 次，兩家都評分。這些是另外的作答，不進主分析。
- **天花板**：某條缺陷流程如果 N 在兩格、兩家評分、3 次都抓到，就算碰到天花板（D32 第 3 點，EVAL_PROTOCOL「原生已經接近滿分的題目要換掉」）。
  - 由原出題者在自己的池裡換一條流程，重埋同類別、同嚴重度的缺陷，機械核實，再校準一次。
  - 換題紀錄寫進重建後的 `spec.json`（`ceiling_replaced`：舊流程對新流程），在主分析之前凍結。換掉的舊流程不會變成乾淨對照。
  - 重建時要給前一版 spec 和它的校準結果：舊流程必須真的在那次校準裡碰到天花板、前一版沒換過題，新流程要維持同一個出題者、類別和嚴重度。這些來源的 sha256 記在 `ceiling_provenance`。
  - 換過的流程如果還是天花板，就照樣保留並在 RESULT 註明。判定程式只接受「換過一次」的流程留在天花板，也會檢查換題只有一輪。
  - 校準的列用案例 digest 綁定，不用整份 spec，所以換題後其他流程的校準照樣有效，只補跑新流程。
  - 篩選只用校準作答，主分析的 N 是新的作答，所以篩選不會讓 F 對 N 的比較偏向哪一邊。
- **下限**：每格、每家評分各算一個下限：
  - 偵測和沒根據回報的合併題內標準差（`pooled_within_sd`）；
  - 不低於借來的 X2 值（`floor.json`）。校準只能把下限調高。

## 判定（`i16_judge.py judge`，由 Codex 執行）
每格分別比 F 對 N：
- **偵測**：6 條缺陷流程是否抓到埋的缺陷。用 `compare`，邊界 0.10，每家評分各算一次。
- **沒根據的回報**：12 條流程，每份報告的數量。用 `compare`，邊界 0.5，越少越好。
- **品質**：每家評分內用 `quality()` 合併，兩家之間用 `agree()`。
- **Codex 的 BASH 規則**：F 要算「更好」，嚴重的埋設缺陷一個都不能漏，而且要兩家都判抓到。漏了就從「更好」降成「未定」。
- **BASH 通過**：另外算一個旗標，四個條件都要成立。D29 的分類不能直接當成 BASH 通過。
