## 問題
同一個 repo、同一份工作，裝了預設的 OAW 2.0.1 之後：
1. 做出來的東西有沒有比較好、一樣、還是比較差？
2. 跨 session 的記憶有沒有變好？
3. token 多花多少？

OAW 對自己的說法有三條，各對一類題目：
- A　一般小改動：不礙事，多花的 token 很少。
- B　跨 session：之前講過的決定，之後的 session 還記得。
- C　大改動或先寫設計的改動：照比例加審查，少漏需求。

## 三臂
| 臂 | 工作區內容 |
|---|---|
| N 原生 | flask 的 base commit，其他什麼都沒有 |
| O 裝 OAW | N 加上 README 快速開始那一行：`python3 OAW/scripts/oaw.py init --target <專案> --host both`，來源是 `claude/oaw-2` 8f25a81。裝完的檔案先 commit 成一筆，像真的專案一樣 |
| L 兩行規則 | N 加上一份兩行的 `AGENTS.md`（下面）和內容只有 `@AGENTS.md` 的 `CLAUDE.md`，也先 commit |

L 的 `AGENTS.md` 全文：
```
# Project guidance

- Write decisions and facts that later work will need in NOTES.md at the repository root. If NOTES.md exists, read it before starting work.
- For a large or risky change, have one fresh-context reviewer (a subagent with no view of this conversation) check the plan before you start and the diff and test results when you finish, and resolve the justified findings.
```

- N 每個 unit 跑兩次（N1、N2），各自全新的工作區和家目錄。第二次用來估原生自己的雜訊，也併進 N 的平均。
- L 只在 codex 格跑，只跑 B、C 類（8 個 unit）。A 類的 L 沒測。Claude 格不跑 L：預算留給 N1、N2、O。
- L 只當對照，不進判定詞。8 題分不出「等價」（見「先講的限制」），所以它只能回答「看不看得出 O 比兩行字好或差」，不能證明「兩行字拿得到一樣的效果」。

## 隔離
每個 session 都在 bubblewrap 裡跑：
- 整個檔案系統唯讀。`/tmp`、`/home`、以及所有資料磁碟區共同的掛載根目錄（專案、紀錄、別的使用者的資料夾都在它底下）都換成空的 tmpfs，所以看不到題目、隱藏測試、參考解、別的臂、別的 repo。只有兩樣東西另外唯讀掛回來：放兩個 CLI 的資料夾，和 `.venv` 連結到的 Python 執行環境。
- 這兩個資料夾在建臂（`h1_run.py arms`）時各複製一份到狀態資料夾，沙盒掛的是複本（掛在原來的路徑上），不是原本的資料夾。所以凍結之後 CLI 自動更新、或原資料夾多出快取檔，都碰不到 run。兩個複本的全部內容各算一個摘要，寫進凍結。
- 自己的 PID namespace：`/proc` 裡只有沙盒內的 process，不能經由別的 process 的 `/proc/<pid>/root` 或 `cwd` 繞出去（探針見文末）。
- 工作區掛在 `/home/dev/proj`，家目錄掛在 `/home/dev`。每一臂看到的路徑完全一樣。
- 登入檔只掛進去，不複製。
- **隔離的單位是（格、臂含第幾次、unit、第幾次嘗試）**：每一個都是從臂的樣板重新複製的工作區、全新的家目錄、全新的暫存。N1 和 N2 互相看不到。
- 同一次嘗試裡，一個 unit 的各個 session 共用工作區和家目錄。家目錄整個留著，包括 host 自己寫的記憶檔和對話紀錄，跟真的使用者電腦一樣；對話不續接（每個 session 都是新的 `claude -p` 或 `codex exec`）。
- 例外是 B 類的 handoff 型：每個 session 換全新的家目錄，只有工作區留著。這一型量的是「只靠 repo 裡的東西交接」。
- 跑之前探過（文末「探針」）：Claude Code 在 `-p` 模式會自己把「記住這個」寫進家目錄的記憶檔，下一個 session 讀得到；Codex 的 `memories` 功能預設是關的，維持預設。
- 評分在另一個沙盒裡跑，不給網路、不掛登入檔、家目錄是空的。

## 題目：每格 12 個 unit
corpus：`pallets/flask` @ 49943b5a94413a530761350f04e896f76e8d620e，測試用 repo 自己的 `.venv`（base 是 494 個測試全過）。

每個 session 的 prompt 都套同一個模板：「You are working in the repository in the current directory.」＋題目＋「Make the change in the source code and verify it with the project's tests. Do not commit.」

**A 一般小改動 ×4**（每個 1 個 session）
- 沿用 `../../digestion-2026-11-03/taste-tokeneconomizer/tasks.json`（sha256 0ecc8d51…b37c6）裡凍結順序第 1、4、7、10 題：t01、t04、t09、t12。這四個題號寫死在 runner 裡，凍結 A 類時給別的題號會被拒絕。
- 這套題目原生是 12/12（Claude Code 2.1.310，Opus 5.5）。所以 A 類是**安全和成本的檢查**：只看得出「弄壞了」和「多花多少」，看不出「變好」。

**B 跨 session 記憶 ×4**（每個 2–3 個 session）
- 四型各一：明講要記（explicit）、順口一提（passing）、決定後來改了（superseded，3 個 session）、做到一半交接（handoff）。
- 最後一個 session 的 prompt 只說「照之前講好的」，不重講內容。內容是任意的（設定鍵名、不尋常的預設值、錯誤訊息用字），猜不到，前面的 session 照 prompt 做也不會把它寫進程式碼。
- 隱藏測試分兩種：`test_recall_*` 要記得那個決定才會過；`test_base_sK_*` 檢查第 K 個 session 做的東西還在，跟那個決定無關。最後一個 session 之前的每個 session 至少一個 `test_base_sK_*`。
- 出題：`AUTHOR_BRIEF_B.md`，每型 2 題備選，共 8 題。
- B 類不篩天花板：原生本來就全記得，本身就是答案。

**C 大改動 ×4**（每個 1 個 session）
- 兩型各二：large（正確做法至少改 300 行非文件程式碼）、design（先在 prompt 指定的 `docs/designs/<名稱>.md` 寫一份短設計再實作）。這兩型正好是 OAW 的 `oaw_mode.py` 會升到 standard、deep 的條件，是 OAW 的主場。
- 每題 8–12 條編號的需求。**一條需求是一個計分項**：它底下的隱藏測試函式（`test_rNN_*`，一條可以有好幾個）全過才算這條做到。
- 出題：`AUTHOR_BRIEF_C.md`，每型 3 題備選，共 6 題。

**出題和驗題（全部在計分的 session 之前，全部不經過 Claude 的判斷）**
1. 出題者是零脈絡的 Codex session。它只拿到 brief 和一份 flask，不知道 OAW、不知道有哪幾臂、不知道在比什麼。
2. 機械驗題（`h1_run.py verify`）：
   - 隱藏測試在 base 會失敗。
   - 參考解 `git apply` 得上去。它只能動 `src/` 底下的檔案；design 型另外允許 prompt 指定的那一份設計檔，其他路徑一律不合格。
   - 套上參考解後，隱藏測試每個函式的每個 case 都過、既有測試沒有退步（見「評分」3）。隱藏測試只能是測試檔裡的一般函式：收集到任何類別裡的 test method 或別的模組的 node，整題不合格。這時收集到的**完整 node ID**（函式名稱加上參數化的 case 名稱）凍結下來，之後評分照這份清單逐一核對。
   - B 類另外查：`facts` 列的每個字串在前面的 session 裡出現過、在最後一個 session 的 prompt 裡找不到、在 base 的 repo 裡找不到、在參考解新增的行裡找得到；函式命名和數量符合上面的規定；`facts` 和 `superseded_facts` 裡沒有任何一個字串包含另一個。repo 和參考解這兩項用「整個 token」比對（前後不緊接字母、數字或底線），prompt 那兩項用純文字比對。
   - B 類的**改值檢查**，每一項都要過：
     - 把參考解裡的 `facts` 全部換成錯的值：每個 `test_recall_*` 都要失敗、每個 `test_base_*` 都要照樣通過。
     - **一次只換一個 fact**（其他保持正確），每一個都做：至少一個 `test_recall_*` 失敗，每個 `test_base_*` 照樣通過。這證明每一項決定都有測到，只記對一半的答案不會被算成「記得」。
     - superseded 型的第 2 個 session 把決定的每一項都換掉（`facts` 是新值，要在第 2 個 session 裡找得到；`superseded_facts` 是舊值，要在第 1 個 session 裡找得到，每一項都跟新值不同）。它另外做：把新值全部換回舊值，每個 `test_recall_*` 都要失敗；一次只把一項換回舊值，每一次至少一個 `test_recall_*` 失敗。這兩種換回舊值的情形，每個 `test_base_*` 都要照樣通過。
   - C 類另外查：需求 8–12 條，每條在 prompt 裡逐字找得到、至少有一個函式；每個函式都對得上一條列出的需求。
   - C 類 large 型的「至少改 300 行」用凍結版 `oaw_mode.py` 自己的算法：參考解裡**不是文件**的檔案（不在 `docs/` 底下、副檔名不是 `.md .markdown .rst .txt .adoc`）新增加刪除的行數，跟它的 `STANDARD_LINES`（300）比。design 型的參考解必須**新建** prompt 指定的那一份設計檔，而且有內容。
3. B 類「全記得」檢查：另一個零脈絡 Codex session 一次拿到該題所有 session 的 prompt（等於記憶完美），在乾淨的 flask 上做；做出來要通過全部隱藏測試。不過的題目代表 prompt 沒講清楚，丟掉。這一項跟改值檢查兩個都要過。
4. C 類「需求有講」檢查：另一個零脈絡 Codex session 逐一核對每個隱藏測試函式檢查的東西 prompt 有沒有講。**只要有一個函式對不上，整題丟掉**，不刪函式、不修題。它的回覆照固定格式機械檢查：一個 JSON 物件，`functions` 列表對每個凍結的函式剛好一筆，`name` 是字串、`stated` 是 true 或 false（字串 `"false"`、數字都不算）、名稱不重複、跟凍結的函式完全一致。格式不對的回覆記下來、這題重新核對；3 次都不對，這題算不合格丟掉。
5. C 類校準（只在 codex 格）：通過前面檢查的備選題在 codex 格用 N 各跑**一次**（runner 的 tag 固定是 calibration、只能 codex 格、只能 N1、只能跑 `units_C_calibration.json` 裡的題）。分數 1.0 的算「頂到天花板」，不選。每型照出題順序取前 2 題沒頂到的。一題有兩筆計分的校準結果、或結果不在嘗試紀錄裡，凍結就拒絕；不能換個 tag 重跑再挑。校準的 run 不計分、不進分析，而且在 `FREEZE.json` 之前跑（它決定 C 類題庫，題庫定了才能凍結）；它用的 runner 和評分程式跟正式的同一份。
   - Claude 格不另外校準（預算不夠，見「預算」）。所以 **Claude 格的 C 類有沒有鑑別力，事先沒有確認**；Claude 格 N 兩次都滿分的 unit 會在結果裡標「頂到天花板，只看得出變差」。
   - 照驗題 6 的 C 類例外補上的題，codex 格校準時 N 已經滿分；正式作答 N 兩次都滿分時同樣標「頂到天花板，只看得出變差」（判定程式照 N 兩次的分數自動標），結果另外列出哪幾題是補上的。
6. 不合格的題目一律丟掉，不修。B 類每型取出題順序裡第一題合格的。某一型合格的題目不夠，就請同一份 brief 的新出題者整份重寫，只取缺的那一型，照它的出題順序接在後面。最多補兩次；還是不夠就停下來回報 owner，不拿頂到天花板或不合格的題目補滿。C 類後來由 owner 改了一處（凍結前的修正 2，D42）：補完兩次後某一型沒頂到天花板的題不到 2 題，就用這一型頂到天花板的合格題照出題順序補到 2 題；不合格的題永遠不拿來補，合格的題還是不夠就照樣停下來回報 owner。
7. 這些規則由 runner 強制，不靠操作的人：
   - **出題帳本**（`authors.jsonl`）：每次出題在開始前和結束後各記一筆（brief 和 runner 的摘要、補哪幾型、產出檔的摘要）。名字不能重用；中途斷掉的算一次，以「沒跑」結束的不算；每類最多 3 次（第一次加最多兩次補題）。補題只有在 `freeze` 寫下「缺哪幾型」之後才能開始，而且只取它缺的那幾型。
   - `verify`、`solver`、`audit` 都用出題者的名字找固定位置的檔案；`freeze` 照帳本順序讀全部出題者，每份備選檔和 brief 都核對帳本記的摘要。改過的備選檔、別版的 brief 一律拒絕。
   - **每份報告都綁摘要**：驗題報告記著備選檔、runner、既有測試基準和 `oaw_mode.py` 的摘要；「全記得」的結果和「需求有講」的結果記著那一題備選內容、那份驗題報告和 runner 的摘要；校準結果記著那一題凍結內容和 runner 的摘要。任何一項對不上就拒絕，不用題號沿用舊結果。runner 改了就要開新的狀態資料夾重做。

## 凍結
任何計分的 run（包括 A 類）開跑之前，一次凍結下面全部，寫成 `FREEZE.json` 推上 `records`：
- 本文、兩份 brief、`h1_run.py`（跑、驗題、評分、解析 token 都在裡面）、`h1_judge.py`、`eval_stats.py`、`oaw_mode.py` 的 sha256。
- 三臂樣板的 commit 和 tree、OAW 來源 commit，加上**每個樣板全部內容的摘要**（`.git`、`.venv`、被 ignore 的檔案、快取都算在內）。run 複製的就是整個樣板，所以每個檔案都在摘要裡。
- 兩個工具資料夾複本的全部內容摘要（見「隔離」）。系統執行檔（git、bash、python3、bwrap、timeout）記版本和 sha256；它們載入的作業系統函式庫不算摘要。
- 既有測試基準（見「評分」3）的摘要、預算基數（見「預算」）。
- A、B、C 三份題庫的 sha256。A 類只能從上面那份題庫（sha256 寫死在 runner 裡）取那四題。題庫本身（含隱藏測試和參考解）等全部跑完才推上去，免得跑的時候在公開的地方找得到。每份題庫檔裡記著選題依據：每位出題者（名字、補哪幾型、brief、備選檔、驗題報告的摘要）、B 類「全記得」、C 類「需求有講」和校準結果的摘要，每一題的凍結內容裡也記著它的備選內容摘要。
- 兩個 CLI 的版本（從複本讀）、實際啟動的執行檔在哪個複本的哪個位置、它最後指到的檔案和那個檔案的 sha256，和 `h1_run.py launch` 印出的完整啟動參數、權限模式、關掉的工具、環境變數、掛載清單、評分指令。本機設定（遮掉和掛回的資料夾、`H1_BIN`）另算一個摘要。
- **任何正式 run 一開始（有開始紀錄）之後，題庫和 `FREEZE.json` 都不能再寫**，就算還沒有任何計分列。
- Codex 審查時核對這份啟動清單，結果在凍結之前記進「審查紀錄」。`FREEZE.json` 寫出之後本文不再改動（改了摘要就對不上，runner 會拒絕跑）。

`h1_run.py run` 在正式的 run 開始和續跑時都重算這些摘要，跟 `FREEZE.json` 對不上就拒絕跑。

## 一個 unit 怎麼跑
- 照順序送出各 session 的 prompt（逐字，各臂相同），最後評分一次。
- 臂的順序照 unit 的序號輪轉，避免某一臂總是先跑。
- **每個 session 上限 120 分鐘，每一臂、每一類都一樣，不因為超時重跑**。Claude 格另有每個 session 8M logical token 的上限，也是每一臂一樣。這個上限管的是**串流裡看得到的用量**（邊跑邊加總）；子代理有些用量要到 session 結束才回報，所以結束時的總量可能超過 8M。這種 session 照常計分、不重跑，在結果裡標「含子代理超過上限」。
- 正常作答到超時或撞到 token 上限：那個 session 在那裡切斷，**算作答結果**。後面的 session 照送，最後照常評分，花掉的 token 全部算。
- 候選程式讓測試超時、當掉、或沒留下報告，是作答的結果：隱藏測試那一部分算沒過，既有測試算退步（0 分），不算沒跑、不重做。只有評分環境本身壞掉（沙盒或腳本起不來、沒記下結束碼）才重試評分。
- 只有基礎設施出問題才算「沒跑」（D30），依序檢查：預算上限、計費來源不是訂閱、碰到用量上限、0 token、Codex 的 provider 不是 openai、主執行緒的模型缺少或不對（見「兩格」）、CLI 以錯誤結束、評分步驟本身壞掉（評分重試一次還是壞）。那一個（格、臂、unit）整個從全新的工作區重跑，最多 3 次嘗試。3 次都沒跑成，這一格就停下來，不由操作的人挑著跑。
- 用量上限只看 CLI 的結構化欄位，不搜尋 agent 自己寫的答案：Claude 是 `rate_limit_event` 的狀態為 rejected、主執行緒回覆的 `error` 是 rate_limit、或結束事件是錯誤且狀態碼 429；Codex 是它的錯誤事件和 stderr。漏判也不會被當成作答：那種 session 會是 0 token 或沒有主模型，照樣算沒跑。
- 每個 session 的完整輸出邊跑邊寫進檔案；機械解析（例如「需求有講」的 JSON）用完整的最後回覆，不截斷。
- 碰到用量上限或預算上限時，這一格先停下來，等額度恢復（或 owner 放行）再從同一個地方續跑。這兩種停不算在 3 次嘗試裡，花掉的 token 照算進預算。
- 每個 run（包括「全記得」檢查和校準）開始前先記一筆開始紀錄，裡面有格、類、題、臂、第幾次，以及這一題凍結內容、題庫、runner、`FREEZE.json` 的摘要；「需求有講」檢查在開始前先存一筆嘗試。runner 被停掉或中斷、沒留下結果的那一次，算一次沒跑成的嘗試（interrupted），計入 3 次，所以不能靠中斷 runner 換一次重來。
- 嘗試紀錄先寫、計分列後寫。兩者之間被中斷時，續跑會先把那筆已經算數的嘗試補進計分列，不會再跑一次。凍結時，一題有兩筆算數的嘗試、或算數的嘗試和計分列對不上，就拒絕。
- token 的算法：預算上限算全部嘗試；成本比較只算有計分的那一次；沒跑成的嘗試每一臂各花多少另外列出來。
- Claude 格一次只跑一個 process。codex 格可以同時跑。

## 評分（全部機械，看不到臂）
最後一個 session 結束後：
1. 拿一份全新的 base（乾淨的 checkout 加上沒被動過的 `.venv`），**只把 agent 工作區的 `src/` 整個資料夾放進去**；design 型另外放進 prompt 指定的那一份設計檔（只有那一個檔，必須是工作區裡的一般檔案，不能是連結）。agent 改的 `tests/`、`conftest.py`、pytest 設定、`.venv`、其他檔案都不進評分環境。
2. 放進隱藏測試，跑它；拿掉，再跑整套既有測試。
3. 一個函式算通過 = 收集到的 case 名稱（完整 node ID）跟凍結的清單**完全一樣**，而且每個 case 都過。skip、xfail、error、沒收集到、多出或少了 case 都算沒過。收集失敗不會把題目刪掉或把分母變小：分母永遠是凍結的計分項數。
   - 既有測試的**基準**在建臂時量：全新的 N 樣板跑兩次整套測試，兩次都要全過、每個 case 的狀態要一樣，記下每個 case 的完整 node ID 和狀態。評分時，基準裡通過的 case 只要有一個這次沒通過（消失、失敗、error、skip、xfail 都算），或整套結束碼不是 0，就是**退步**。
4. 計分項：A、B 類一個函式一項；C 類一條需求一項（它的函式全過才算）。
5. **unit 分數** = 通過的計分項 ÷ 全部計分項，存完整的值，不四捨五入；判定程式用列上的通過數和計分項數重算。**既有測試只要退步（或整套跑不起來），這個 unit 記 0 分**，並列出退步的 case 數和前 5 個。
6. B 類另外記「記得」= `test_recall_*` 全過（既有測試有新失敗時算沒記得）。
7. 另外記但不算分：token、工具次數、有沒有用到 OAW 的 skill 或 script、有沒有 subagent、家目錄和工作區裡多出來的記憶或筆記檔、啟動時列出的 skill 和工具、沙盒擋下的寫入次數。
   - skill 有沒有用：Claude 看 Skill 工具的呼叫，加上工具呼叫裡讀了哪個 `SKILL.md`；Codex 看 rollout 裡的工具呼叫讀了哪個 `SKILL.md`（Codex 沒有 Skill 工具）。讀不到（沒有啟動事件、沒有主執行緒的 rollout、或串流回報了工具呼叫但 rollout 裡認不出任何一筆）就記「未知」，不記 0。

## 判定
輸入固定成「unit → 這一臂各次的值」：O 一個值，N 兩個值（N1、N2）。品質和成本裡 N 都用兩次的平均。每格分開算。**一格要 12 個 unit 的 N1、N2、O 全部到齊才出判定詞**；缺任何一個就寫「未完成」，只列已完成類別的數字。

**第一步　品質**
- 整體：`eval_stats.compare(O, N, margin=0.10, floor_sd=F)`，12 個 unit。每類 4 題，所以這個平均就是 A、B、C 各占三分之一。
- 各類：同一個函式、同一個 `F`，各算自己的 4 題。
- `F` = max（這一格 N 兩次作答的合併題內標準差 `pooled_within_sd()`，0.1318）。前者是這個題庫自己量的雜訊；0.1318 是借來的保守下限（見例外 3）。
- 這一格的品質類別 `Q` 照下面的順序定，先符合的算：
  1. 任何一類是「更差」→ `Q` = 更差，寫明是哪一類。
  2. 整體是「更差」→ 更差。
  3. 任何一類的平均差 ≤ −0.10（還沒到「更差」）→ `Q` = 未定，寫「類別不一致」。整體就算是「等價」或「更好」也一樣。
  4. 其他 → `Q` = 整體的類別。

**第二步　記憶（B 類，另外判）**
- 每個 unit 的值是「記得」（1 或 0）。`compare(O, N, margin=0.10, floor_sd=max(N 的合併題內標準差, 0.1318))`，4 題。
- 「更好」→ 記憶變好；「更差」→ 記憶變差；其他 → 未定，列出兩邊各記得幾題。兩邊都全記得時寫「都記得，這組題目分不出來（天花板，未證等價）」。
- 4 題不可能判出「等價」，所以這一步不會得到「記憶沒變」這個結論，最多是「看不出差別」。

**第三步　成本**
- 給 owner 的詞用的是**整批的總 token**（logical，一個 unit 所有 session 加總，含 subagent）：`T` = O 的 12 題總和 ÷ N 的 12 題總和（N 每題取兩次平均）。
- 原生自己的波動 `B` = N1 總和和 N2 總和相除，取大於 1 的那個方向。
- `T` > max(1.10, `B`) →「token 變多」；`T` < min(1/1.10, 1/`B`) →「token 變少」；其他 →「沒有確實變多」。這是事先定的描述性門檻，不是檢定。
- 並列回報：各類的總量比、不含 cache read 的同一組數字、沒跑成的嘗試花掉的 token。
- protocol 的成本指標照舊算：`eval_stats.cost(O, N)`（每題 token 比的幾何平均和 95% 區間；太貴、比較省、在上限內、未定）。它只用在第五步。

**第四步　owner 的詞（每格一個）**

| `Q` | token | 詞 |
|---|---|---|
| 更差 | 任何 | 更慘 |
| 更好 | 任何 | 有幫助（另外寫 token 有沒有變多） |
| 等價 | 變多 | 雞肋 |
| 等價 | 沒有確實變多、或變少 | 沒差 |
| 未定 | 任何 | 未定。附上點估計、95% 區間、`compare()` 給的最小可偵測差，和 token 那一句 |

**第五步　照 EVAL_PROTOCOL 結果表的對應（每格一個）**

| `Q` | `cost()` | 對 OAW 自己的意思 |
|---|---|---|
| 更好 | 不是太貴 | 留在預設站得住 |
| 更好 | 太貴 | 該改成選配 |
| 等價 | 比較省 | 留在預設站得住 |
| 等價 | 在上限內、未定 | 該改成選配：列出可以搬出預設的零件 |
| 等價 | 太貴 | 提案移出預設 |
| 未定 | 不是太貴 | 能力未定：不能拿這次結果說預設站得住 |
| 未定 | 太貴 | 提案移出預設 |
| 更差 | 任何 | 提案移出預設 |

搬不搬由 owner 在發佈時決定。

**第六步　兩格合併**
- 成本不跨格相加，每格用自己的。
- 合併的詞 = 兩格的詞裡比較差的那個，順序固定：更慘 < 未定 < 雞肋 < 沒差 < 有幫助。兩格不同時兩個都寫出來。
- 合併的第五步結果 = 兩格裡比較差的那個，順序：提案移出預設 < 該改成選配 < 能力未定 < 留在預設站得住（D29：最差的條件決定）。
- 有一格「未完成」時，合併結果寫「未完成」，另一格的結果照寫並註明只有一格。

**分類細目（次要，用來講「差在哪」，不改判定詞）**
- 每格、每類 4 個 unit：O 的分數減 N 兩次的平均，差 ≥ +0.10 算贏、≤ −0.10 算輸。贏減輸 ≥ +2「方向：較好」；≤ −2「方向：較差」；±1「差一題，不下結論」；0 而且有贏有輸「勝負抵銷，未證等價」；0 而且沒輸沒贏「看不出差別，未證等價」。
- 不做跨格的檢定。同一題在兩格的結果是同一題，不是兩個獨立樣本；跨格只逐題描述兩格方向一不一致。

**L 的對照（次要，只有 codex 格）**：B、C 共 8 個 unit，`compare(O, L)` 和 `compare(L, N)`，同樣的邊界和 `F`。只回報類別、點估計和區間，不進判定詞。

**判定程式讀什麼**：`h1_judge.py` 必須拿到 `FREEZE.json`、三份題庫、計分列、**全部嘗試紀錄和開始紀錄**。每一筆嘗試都要有開始紀錄；有開始紀錄卻沒有嘗試的，當成中斷的嘗試列進「沒跑成的嘗試」，token 記「未知」（那一欄的總數變成下限）；同一筆給了兩次就拒絕。沒跑成的嘗試花了多少，不管這一格完不完整都列出來。開始前先核對：三份題庫、載入的 `eval_stats.py`、判定程式自己的摘要都跟 `FREEZE.json` 一樣；每一列和每一筆嘗試（含 L）都是 tag main、同一份 `FREEZE.json`、同一份題庫和 runner、那一題凍結內容的摘要，而且（題、臂）在凍結的名單裡（Claude 格 N1、N2、O；codex 格 N1、N2、O，B、C 類另有 L）。每一筆計分列都要在嘗試紀錄裡，每一筆算數的嘗試也都要在計分列裡；有計分列卻沒給嘗試紀錄，就拒絕判定（寫「未提供」）。任何一項對不上就拒絕。

## 角色
- Claude（本 session）：寫本文、寫 runner、操作已凍結的 runner。Claude 這邊做了 OAW 2.0.1，所以不出題、不評分、不判定。
- Codex gpt-6.1-sol：審本文（最多 3 輪，意見跟 Claude 不同時以 Codex 為準）；核對啟動清單；零脈絡 session 出題、做兩種驗題檢查；最後拿凍結的本文和結果列，用自己的 script 從原始紀錄重算 token 和判定。
- 安裝、啟用、成本各有獨立檢查：runner 記下每個工作區的安裝內容摘要（N、L 沒有 OAW 檔）、每個 session 開始時列出的 skill 和工具、用到的 OAW 零件、原始 token 事件。

## 預算
- Claude 格上限 30M logical token（D35），**所有嘗試都算**，包括探針和試跑（到目前 1.39M）。codex 格不佔這個上限，token 照樣回報。
- Claude 格的固定設計：12 個 unit × N1、N2、O。順序 A → B → C。不因為花費去掉任何一臂或任何一次。
- 估計（每個 session 的 logical token，沒量過，只是起點）：A、B 類 N 0.35M、O 0.45M；C 類 N 2.5M、O 3.5M。照這個算：A 4.6M、B 10.4M（9 個 session）、C 34M。**也就是說，照估計 A、B 跑得完，C 類放不進 30M**。
- 所以 C 類在 Claude 格開跑前有一道關卡，只看花費、不看分數：
  - 推估 = codex 格 C 類 12 個 run 的總 token × `r`；`r` = Claude 格 A、B 類全部 run 的總 token ÷ codex 格同一批 run 的總 token。
  - 已花的 + 推估 × 1.25 ≤ 上限 → 開跑。否則不跑，帶著這些數字問 owner 要不要加額度（D35）。owner 放行的數字寫進紀錄之後才跑。
  - owner 不放行：Claude 格是「未完成」，只報 A、B 兩類的數字，不出判定詞。
- 硬上限：每個 run 開跑前，已花的加上這個 run 的估計（有量過的用同類同臂量到的最大值）超過上限就不開。跑到一半累計碰到上限，當下的 session 立刻切斷，那一次算沒跑，這一格停下來。跑到一半的累計和被切斷的 Claude session 的 token 數靠的是串流裡的用量事件，是下限（子代理的用量要到 session 結束才完整）；正常結束的 session 用結束時回報的完整數字。
- **每個 session 結束、拿到完整用量之後再檢查一次**：已花的超過上限，這個 run 算沒跑（預算上限），這一格停下來。下一個 session 開始前也檢查。
- 預算的記帳由 runner 強制：
  - 預算基數（上限 30M、決定 D35、在這個狀態資料夾之前已花的量）由 `h1_run.py budget` 寫一次，之後不能改；寫進凍結。run 的指令沒有改上限或已花量的參數。
  - 加額度只能用 `budget --raise-to <新上限> --decision D<編號>` 記一筆，必須寫出 owner 的決定編號，而且新上限比現在大。
  - 每個 Claude session 開始前在帳本（`ledger-claude.jsonl`）記一筆「開始」和預留量，結束後記一筆實際用量。輸出邊跑邊寫進檔案。runner 中途死掉時，那個只有「開始」的 session 照「預留量和輸出檔裡已看到的用量取大的」算進已花的，不會漏掉。
  - Claude 格同一個狀態資料夾一次只能有一個 process（檔案鎖）。
  - C 類關卡第一次在資料齊全時做出的決定存起來：開了就一直開（續跑時由硬上限管）；沒開的只有在記錄了加額度之後才重算。
- 跑到一半停下來的格：已經有的資料留著、照實列出，不拿來出判定詞。

## 先講的限制
- 每類 4 題、每格 12 題、O 跑 1 次。只分得出大的差別。用最小的 `F`（0.1318）算：12 題的標準誤至少 0.054，最小可偵測差 0.151；要判「等價」，平均差要在大約 ±0.012 以內。量到的 N 雜訊如果 ≥ 0.149，12 題連完全同分都判不出等價。所以**最可能的結果是「未定」加上一個區間**；「雞肋」和「沒差」只有在兩臂分數幾乎一樣時才判得出來。
- 各類 4 題和 L 的 8 題在任何情況下都判不出「等價」。
- A 類已知頂到天花板，它只會把整體平均往「沒差別」拉。
- C 類 4 題裡有 2 題是用校準時頂到天花板的題補上的（凍結前的修正 2）。codex 格這 2 題看出「更好」的能力可能比較弱，C 類和整體平均可能被往「沒差別」拉。校準只跑了 N 一次，正式作答 N 不一定再滿分；正式作答 N1、N2 都滿分的題，才只看得出持平或變差。
- 一個 Python repo，題目是出題者寫的，不是真實的工作紀錄。
- headless：agent 沒辦法回頭問使用者。
- 沒量長期使用（幾十個 session、證據越積越多之後）。
- 只量預設安裝。沒裝的選配（wiki、improve）不在內。
- Claude 格用 2.1.287；A 類原生 12/12 是在 2.1.310 量的。
- `test_base_sK_*` 檢查的是哪個 session 的東西，靠的是出題者的命名和「全記得」檢查，沒有另外的機械證明。
- Codex 的 workspace-write 沙盒在每一臂都把工作區的 `.agents/`、`.git`、`.codex` 設成唯讀（試跑的 rollout 看得到）。O 臂的 OAW 記憶小工具要寫 `.agents/`，在 Codex 格會被擋。這是預設安裝在 Codex 上的產品限制，照實量，不替 O 單獨放寬；每個 session 記下沙盒的唯讀路徑和被擋下的寫入次數。
- Codex 沒有 Skill 工具，「用了 skill」只能從讀了哪個 `SKILL.md` 看出來；讀不到時記「未知」。
- 工具資料夾和樣板都算了全部內容的摘要；系統執行檔只算檔案本身，它們載入的作業系統函式庫沒有算。

## 跟 EVAL_PROTOCOL 不同的地方
1. A 類已知原生接近滿分，沒有照規定換掉。它在這裡是安全和成本的檢查。
2. C 類只在 codex 格校準；Claude 格沒有。
3. `floor_sd` 的下限 0.1318 是借來的：它是 EGM 設計審查偵測率的重複作答標準差（X2、I16 用過的最小值），不是這個題庫、這個分數的雜訊。這裡把它當保守的下限，這個題庫自己量到的比較大就用自己的。結果裡另外列出「只用自己量到的雜訊」會得到什麼類別，當敏感度，不當判定。
4. owner 的詞用整批總 token 比，不用 `cost()`。理由：`cost()` 是每題比例的幾何平均，小題省、大題貴的時候它可以小於 1，總花費卻變多。
5. 評分是機械的（隱藏測試），不做兩家盲評。
6. 一類有問題時會把整體類別往下拉（第一步的規則 1、3），這比 protocol 嚴。
