## 機制事件是怎麼稽核的

- 每個事件只有「觀察到／該發生而沒發生／未驗到」三種，從原始紀錄配對指令、工具結果、寫入內容和後續讀取來判，
  不看 skill 名稱、agent 數量或 agent 自己的總結。
- Codex 格 12 題由 Codex 稽核（執行當時的紀錄，90 筆證據引用）。Claude 格 12 題也交給 Codex 稽核，
  不由執行這一格的 Claude 自己稽核；摘要在 [AUDIT-CLAUDE.md](AUDIT-CLAUDE.md)。
- Claude 格的稽核結果由一支腳本併入私有的事件檔：重新計算 12 個計分列的雜湊、33 筆證據所在檔案的雜湊，
  檢查每個行號範圍存在，並確認 Codex 的 12 列逐位元不變。Claude 另外對照原始紀錄抽查了 3 筆
  （`superseded` 的 M1、`explicit` 的 M2、`design-3` 的 R2），與稽核一致。
- 一個照字面的判讀要說明：Claude `superseded` 題兩個學習 session 都把事實存進了 Claude 自己的記憶資料夾，
  後面的 session 也讀回來了，但沒有執行 OAW 的 `memory add`。凍結條件寫的是「成功 `memory add`」，
  所以記為「該發生而沒發生」，不擴張成觀察到；它確實存了，只是不是存在 OAW 的筆記裡。
- 公開的只有狀態、雜湊和摘要；原始對話紀錄、私有路徑和題目裡要記的事實不放進這個 repo。

## 限制

- 每格 12 題、每題一次，同一批診斷題。看不出小的差別，也分不開波動和效果。
- 兩格之外沒有別的模型或 host；題目只有一個 Python repo。
- 舊 O 與原生的數字是 2026-11-11 跑的；後端模型版本和系統函式庫沒有完全凍結，跨兩天的比較有這個限制。
- 事件稽核能確認「有沒有發生」，不能確認內部的 context 隔離或 effort 設定。
- 數值門檻通過與否，不能取代離線測試、CI 和發佈前的完整審查。
