## 判定（照事先寫死的規則）
- G：沒有證明比原生好。覆蓋率相同，必要事實都全對；每題 token 中位數多 38%（總量多 43%），不符合「一樣懂但比較省」。

## 觀察
- 換到 54 萬行的陌生 repo，仍然有天花板效應：原生 agent 只靠 Grep、Read，4 題的必要事實全對，工具呼叫 5 到 33 次。OAW 那次的結論在大型 repo 上重現。
- G 每題都照它的 CLAUDE.md 規則，先跑一次 `graphify query`（4 次中 4 次），回傳約 5 到 7 千字元、截斷過的子圖，之後回到 grep 和讀檔。q1 問 `update_bin_qty` 的呼叫者，查詢只顯示 102 個節點裡的 49 個，6 個真正的呼叫者只列出 1 個；agent 是靠 grep 找齊的。
- 錯誤陳述：N 2 個（q3 說 GL 分錄直接掛在發票上，q4 把 fallback 迴圈講成依客戶取 selling），G 1 個（q2 標題寫「2 個方法」，實際列了 3 個）。兩題影響題 N 0 個、G 1 個（只是數錯）。OAW 那次「地圖組的錯誤集中在影響題」沒有在這裡重現；每格只有 1 次，兩邊的差都在雜訊範圍內。
- 回合數：N 34／10／6／11，G 25／7／6／9。graphify 自己的 benchmark 限 14 回合，在這裡只有 q1 會被切斷。

## 不能這樣解讀
- 這不是 graphify 宣稱的 70.8% → 82.0% 的重現或反駁。它的設定是 Claude Opus 4.8、最多 14 回合、它自己的 grep／read／list 工具和 Kimi 評分；這次是 Claude Opus 5.5、Claude Code 原生工具、不限回合。兩邊的數字是不同 protocol，不能並排比。
- 也不能和 OAW 那次的工具層數字（39 題的前 5 名命中率）比，那是另一種量法。
- 樣本小：4 題、每格 1 次。

## 偏差
- G 有 Bash（只登記 `graphify`），Claude Code 會自動放行唯讀指令（sed -n、grep），所以 G 也用了 shell 讀檔；N 只有 Grep、Read、Glob。兩邊功能上等價，和 OAW 那次相同。G 試了 2 個需要核准的指令（python3、awk），都被拒絕，算在 G 的工具呼叫裡。
- 其餘差別見 `PREREG.md` 的「和 OAW 那次的差別」。

## 花費
- graphify 這份食物：OAW 那次 3,790,470 + 這次 982,659 = 4,773,129，剩約 5.2M。
- 消化開銷：出題 1,518,689、盲評 44,711、隔離探測 2,531。
