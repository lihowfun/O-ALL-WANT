## 判定（照事先寫死的規則）
- **Opus 4.8**
  - G：沒有證明比原生好。覆蓋率低 0.091，離「變差」的門檻 0.10 只差 0.009；必要事實全對少 4 次。規則只看覆蓋率、錯誤陳述和切斷次數，所以沒有判成「變差」。
  - S：變差。錯誤陳述比 N 多 3 個，達到門檻。
- **Haiku 5.5**：G 和 S 都沒有證明比原生好。S 的工具呼叫只有 N 的 48%，4 題裡 3 題比 N 少（另 1 題一樣多）；token 則是 N 的 127%。S 沒有判成「一樣懂但比較省」，是因為錯誤陳述 2 個，比 N 多 1 個，而這個判定要求錯誤陳述不比 N 多。

## 四個條件放在一起
Opus 5.5 和 Sonnet 5.5 的數字取自確認實驗在本機的 `summary.json`。那個 session 還沒發布結果頁，最後以它的 `RESULT.md` 為準。下表依原生組的覆蓋率由高到低排列：

| 條件 | 每格次數 | N 覆蓋率 | G−N | S−N | G 判定 | S 判定 |
|---|---|---|---|---|---|---|
| Opus 5.5 不限回合 | 3 | 0.923 | −0.011 | +0.010 | 沒有證明比原生好 | 一樣懂但比較省（工具呼叫 66%） |
| Sonnet 5.5 限 14 | 3 | 0.897 | +0.012 | −0.002 | 沒有證明比原生好 | 沒有證明比原生好 |
| Haiku 5.5 限 14 | 1 | 0.891 | −0.036 | −0.031 | 沒有證明比原生好 | 沒有證明比原生好 |
| Opus 4.8 限 14 | 3 | 0.833 | −0.091 | −0.034 | 沒有證明比原生好 | 變差 |

依 PREREG 的合併規則，一個 code map 至少要在一個條件判定為「更懂」或「一樣懂但比較省」，而且所有條件都沒有「變差」，才算有提升：
- **graphify**：4 個條件都沒有證明比原生好 → 沒有提升。
- **OAW code map**：在 Opus 5.5 是「比較省」，但在 Opus 4.8 是「變差」→ 不算有提升。

假設的方向是「原生越弱，地圖幫得越多」。實際上方向相反：原生覆蓋率最低的 Opus 4.8，兩個地圖組的差距反而都是最負的。這只是描述，4 題、沒有做統計檢定。

## 觀察
- **這題組上最弱的是 Opus 4.8，不是 Haiku。** Haiku 只跑了 1 次，原生覆蓋率 0.891，和 Sonnet 差不多，但每次的 token 是 Opus 4.8 的 2 倍左右。
- **G 在 Opus 4.8 上掉分的地方是影響題。**
  - q1 要列出 `update_bin_qty` 的所有呼叫者。G 列出 Sales Order 的只有 1／3 次，Material Request 和 Work Order 各 2／3 次；N 和 S 都是 3／3。q1 的 3 次，G 都先跑 `graphify query`，查回來的子圖是截斷過的，Opus 4.8 比較常照著它作答，沒有再用 grep 補齊。
  - q2 的「Stock Entry 不受影響」：G 1／3 次，N 和 S 都是 3／3。
  - 在 Opus 5.5 上，同樣是截斷的查詢結果，agent 會回頭 grep 補齊（`../taste-graphify/erpnext/RESULT.md`）。OAW 那次「地圖組的錯誤集中在影響題」這個訊號，在 Opus 4.8 上出現了。
- **q4（cost center 的優先順序）三組都難。** 在 Opus 4.8 上，三組的必要事實全對都是 0 次。錯誤陳述也大多出在 q4（N 6、G 5、S 7）；S 比 N 多的 3 個，2 個在 q1，1 個在 q4。
- **14 回合上限沒有切斷任何一次。** 有 4 次的 `num_turns` 超過 14（最多 22），但 `--max-turns` 算的是「回應幾次」，一次回應可以同時呼叫好幾個工具，`num_turns` 算的則是工具結果的數量。另外用 5 個小檔案驗證過：上限設 2 時，回應 2 次後就以 `error_max_turns` 結束；設 14 時，正常讀完 5 個檔案。48 次裡，回應次數最多的一次是 11 次。所以這兩個條件實際上等於沒有回合上限。確認實驗的 Sonnet 條件用的是同一套設定，情況應該相同。

## 不能這樣解讀
- 不能和 graphify 宣稱的 70.8% → 82.0% 並排比較。這次的 Opus 4.8 限 14 回合最接近它的設定，但工具（Claude Code 原生工具）和評分者（Opus 5.5，它用 Kimi K2.6）都不同；上限實際上也沒有切斷任何一次。
- 跨條件比較時有評分批次的差別：這兩個條件和確認實驗分批評分（同一個評分模型、同一段提示）。
- 樣本小：4 題，每格 3 次，Haiku 只有 1 次。

## 偏差
- **Haiku 只跑完 3 次裡的第 1 次。** Haiku 每次大約用 15 萬 token，是原本估計的 2.5 倍。跑完第 1 次時已經用了 1,861,420，估計下一題還要約 596K，會超過 2.4M 的上限，預算保護就停了。照 PREREG，只評已跑完的題目。
- `claude-haiku-5-5` 會讓 CLI 印出 `unrecognized_model` 警告，但回答正常。`--effort high` 對 Haiku 有沒有作用，從輸出看不出來。
- 跑的期間 owner 的訂閱曾經碰到用量上限，之後已重置。48 次都正常結束，沒有空白的答案或錯誤；runner 遇到失敗會直接停下，不會記錄。48 筆評分都有。
