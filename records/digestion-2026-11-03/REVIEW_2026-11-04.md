# 消化系統審視（2026-11-04，owner 用 CLI 跑的只讀審視，摘要）

這份審視由 owner 在 WSL 的 Claude Code CLI（plan mode、只讀）產生，原文貼在對話裡。以下是 Claude 核對過的摘要。抽查屬實的三點：`ROUND_V1_PICKS.md` 的「只挑 A 級」、「D13 每輪 10M」誤寫（實際是每樣食物 10M）、backlog 的 PRE-01／PRE-09 狀態過期，都已在 records 更正。

## 主要結論
- 消化系統其實有兩條：catalog 原型 v0（有程式，吸收數 0，因為 skill 文字要 A/B 但沒有 runner），以及 D21 流程（第一輪吸收 8 個 A 級）。D21 的快篩和分級完全靠 agent 判斷，沒有程式約束，所以規則會不知不覺漂移（B6 就是例子）。
- graphify 的兩個角色：(1) 結構化程式碼地圖和排序導航，(2) 文件到程式碼的引用和 affected。已吸收的只有 (2) 的標準函式庫版（OAW-21、OAW-22）；(1) 從來沒量過，沒被證明，也沒被推翻。
- 真正的硬卡點只有兩個：沒有 level 2 沙箱、D13 每樣 10M 對上 HOLD-04 估的 36–54M。24 KB skill 限制對程式碼地圖是理由誤植；graph memory 禁令需要 owner 界定；標準函式庫規則只擋 graphify 套件本身。

## 建議的驗證（C3）
- **Stage 0-α（0 model token，不執行 graphify）**：OAW repo 固定 commit 上 30–40 題，分四類各自計分：概念找定義（題目不含名稱）、誰呼叫 X、改動影響（用 git 歷史的 commit message 當題、改過的檔案當答案）、模組間路徑。比 R（模擬原生搜尋）、S（標準函式庫索引，延伸 `wiki_sync.py` 既有的 ast 收集）、G（graphify，等 level 2）。量 top-1／top-5 命中、precision／recall、MRR、輸出 bytes。先寫死通過條件：任一類 top-5 比 R 高 0.15 以上、輸出不比 R 多，才進付費。
- **Stage 1（≤ 10M，只跑 Claude）**：6 題 × 2 組 × 1 次 = 12 run；量到第一個正確答案的 tool call 次數和 token；先登記大效果門檻；原生組每題 3 次內解決就停；順便校正每 run 的估算。

## 建議的修改（M1–M5）
- M1 快篩照 D21 原文：依價值挑、挑完才分級，C 級整理成一頁給 owner，每輪最多 3 題。
- M2 解開死結：stdlib 索引成為 HOLD-04 裡獨立的一組，先跑 Stage 0-α（R 對 S）；依賴縮成 OAW-03、OAW-04 和題庫。
